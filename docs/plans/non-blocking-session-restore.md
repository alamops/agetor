## 1. Objective & success criteria

Sending a message to a long-idle claude task restores its session. Today that restore **freezes the whole Bun main process** — `attachSubagentWatcher` rehydrates every subagent row the task ever had and runs one unindexed `run_events` scan per row, synchronously, inside the spawn path (~1.1 s per subagent on the owner's 4.56 GB DB; 105 s for 96 subagents). While it runs, no HTTP route, SSE stream, tmux op or pipeline runner makes progress, so other task panels sit on `Loading messages…`, the board stops updating and pipeline views don't render.

Success, as the owner set the bar (grill #3, #4, #8):

1. **No single main-thread block over 100 ms** during a claude resume, fresh start or boot reattach, **and the `claude session … ready` status within 2 s of the spawn**, for a task like the owner's 208-subagent / 596 MB one on a DB that size. Every other panel, the board and the pipeline views answer in normal time throughout.
2. Three regression guards: (a) an `EXPLAIN QUERY PLAN` guard over every `run_events` query (no `SCAN run_events`), (b) an integration test that attaches the **real** watcher over ~200k seeded events + ~180 MB of transcripts and asserts timer drift stays under the bar, (c) a fake-driver seam that attaches the real watcher plus an e2e where another task's panel, the board and a pipeline view load during a restore.
3. Observability: an event-loop-lag monitor (one line per ≥1 s stall naming the labelled operation, plus a status line on the task's run) and a `watcher` stage in the launch breadcrumb.
4. Client honesty: an app-level "Agetor is busy — waiting for the core…" banner from a `/health` probe; the `No runs yet for this task.` line waits for `runsLoaded`.
5. `POST /runs/:id/input` never holds its response past `SPAWN_RESPONSE_BUDGET_MS` for *any* pre-dispatch work (teardown wait, worktree restore, codex version floor, `@`-expansion, liveness probe) — `pending: true` past the budget; a late failure re-stashes the message and toasts.
6. Archived-history retention in this change: `tool_result` payloads over 4 KB on tasks archived ≥ 30 days are trimmed (automatic after boot + daily, `archivedHistoryRetentionDays` preference with Off, `agetor config`), a manual **Compact database** button + `agetor compact` (VACUUM, refused while any run is active), every trimmed row keeps valid JSON and renders a muted note in RunPanel, `agetor logs` and the TUI.
7. Verified on a `.backup` copy of the production DB in `~/.agetor-dev` with a headless attach (no claude launch); max block time, `ready` latency, first-pass duration, the first retention pass duration and the VACUUM time are recorded in §10.
8. Docs updated (`CLAUDE.md`, the #230 plan's §2 / §8 Q1 pointer).

## 3. Approach & key decisions

| # | Decision | Rests on |
| --- | --- | --- |
| A | **Task-scoped rewrite, no migration.** Both queries take `(taskId, subagentId)` and are spelled `FROM runs r JOIN run_events e ON e.run_id = r.id WHERE r.task_id = ? AND IFNULL(e.subagent_id, '') = ? AND e.line_uuid IS NOT NULL` so the planner uses `run_events_run_sub_line_uuid` as a covering SEARCH (the `IFNULL(subagent_id, '')` spelling must match the index expression exactly). | evidence (grill §0 spikes); owner #1 |
| B | **Cooperative seed + first pass, `ready` after the seed.** The rehydrate loop and the first-cycle replay become two cooperative jobs (`SeedJob`, `FirstPassJob`) stepped in ~20 ms slices with `await` yields between slices in production; `pump()` drains both synchronously in `manual` mode so the 101 existing test call sites keep working unchanged. `attachSubagentWatcher` still returns the handle synchronously; the handle gains `ready` (seed done) and `settled` (seed + first pass done) promises. `attachTailer` becomes async and awaits `ready`; the spawn IIFE emits `ready` after it; `reattachSession` and the held-task re-arm await it too. `cycle()`/`discover()`/the dir watcher never run while a seed is in progress; the seed skips rows already present in the maps (idempotent), `detach()` aborts a job, and `ready`/`settled` never reject. | reasoning over the code (§2.1, §8 A2) + owner #2, D9 |

Suspended while a Compact request is in flight (that block is expected). | owner #6 |
| F | **Retention trims in place, JSON stays valid, marker first.** A trimmed payload is re-serialized as `{"retention":{"trimmed":true,"originalBytes":N,"trimmedAt":ms},"toolUseId":…,"content":<trimmed>,"isError":…,"attachments":…}` — the `retention` key FIRST so the SQL prefilter `substr(data, 1, 13) != '{"retention":'` skips trimmed rows without parsing (idempotency + crash resume for free). Per-shape rule for `content`: string → cut to 4096 bytes on a code-point boundary + `…`; array of blocks → keep `{type:"text"}` text in order until the 4 KB text budget is spent, drop later blocks, replace every non-text block (image/document/unknown) with `{type:"text",text:"[<type> block removed by retention]"}`; plain object (cursor `tool_call`, gemini/fx object results) → the whole-payload fallback: `JSON.stringify(content)` cut to 4096 bytes as a string; anything else untouched. `toolUseId`, `isError`, `attachments` and `line_uuid` are never touched, so unarchive + resume never re-imports and the sent-files / TODO parsers keep working (their anchors sit in the first bytes). | owner R1–R2, RD2; §8 A1 |
| G | **Retention runs per run, per chunk, yielding.** Candidate tasks `archived_at <= now − days`, oldest first; per run `SELECT id, data FROM run_events WHERE run_id = ? AND stream = 'tool_result' AND LENGTH(CAST(data AS BLOB)) > 4096 AND substr(data,1,13) != '{"retention":' AND id > ? ORDER BY id LIMIT 200` (walks `idx_run_events_run`, no sort), chunks also capped at ~2 MB of input, one `db.transaction` per chunk, `await` yield whenever a slice passes 20 ms. Scheduler: 90 s after the API is up, then every 24 h, single-flight, re-run requested on a preference change (debounced 5 s), `.unref()`'d, stopped on shutdown. Bookkeeping in `preferences` under `retention:lastRunAt` / `retention:lastFreedBytes` / `retention:lastTrimmedRows`. | owner R3, RD3, RD6–RD7 |

The estimate shown is `(page_count − freelist_count) × page_size / GB × 7.5 s` (constant `DB_COMPACT_SEC_PER_GB`, re-calibrated in T14). Never automatic. | owner R4–R5, RD8; §8 A4 |

## 7. Blast radius & risks

- **Every claude spawn, resume, boot reattach and held-task re-arm** goes through T2/T6/T7. The seed's per-row logic is moved, not changed; the ordering guarantee is `ready` after the seed, as today. Risk: a settle/notification arriving mid-seed — analysed in §8 A2 (no-ops that the later rehydrate reconciles). Risk: `pumpWatcherForHoldCheck` during the first ~0.5 s of an attach is now a no-op — a turn cannot end that early on a resume; accepted and documented.
- **Boot** still awaits `reconcileOrphans` before the API starts; it gets faster (query) and yields (harmless there). The held-task re-arm now awaits `ready` — sequentially per task, bounded by the fast seed.
- **`sendInput` consumers** (webview composer, diff composer, backlog tray, ask-card free text, commit-and-push, resolve-conflicts, CLI `send`, the pipeline reminder path, cursor plan approval): the delivered/pending shape is unchanged for the fast path; `pending: true` may now arrive before a run is minted (its `runId` then names the addressed run) — every consumer only displays it or ignores it. A late failure is surfaced by the new `send-failed` event (webview toast) and by the backlog tray; the CLI's `send` can't observe a late failure (documented in its usage text).
- **`GlobalEvent` union grows** — the TUI/CLI kind-switches must tolerate `send-failed` (T12 checks).
- **`run_events` rows are rewritten** by retention — the only in-place mutation of event history in the codebase. Scope is fenced: `stream = 'tool_result'`, archived ≥ N days, size > 4 KB, never `line_uuid`/`id`/`ts`/`stream`, marker-first JSON. One-way (RD4). Derived task columns (plans, sent files, TODO progress, handoffs) are unaffected (RD5). A trimmed row that the "Rebuild from session JSONL" button re-derives comes back full only where Claude's transcript still exists.
- **VACUUM** blocks the core for its full duration (owner-accepted, modal + refusal gate). A crash mid-VACUUM is safe (SQLite's VACUUM is transactional). The refusal counts in-memory `active` + `startingTaskIds`; a run the DB still marks `running` from a dead process is not counted (boot reconciliation handles it before the API is up).
- **`/health` probe false positives** under the webview's ~6-connection cap: the banner copy stays neutral; it clears itself. No request is ever aborted or retried because of the banner.
- **Rollback**: every change is a code revert; no migration, no schema change. Trimmed rows stay trimmed after a rollback (an older build renders the first 4 KB of content without the note).
- **Feature switches**: `AGETOR_TRACK_SUBAGENTS=0` (existing), `AGETOR_LAG_MONITOR`, `AGETOR_ARCHIVED_HISTORY_RETENTION=0`, the `archivedHistoryRetentionDays` preference (`off`).

## 8. Open questions / assumptions

Assumptions the grill left to the planner, now resolved from code (A1–A3), plus the ones execution proceeds on:

- **A1 — Per-harness `tool_result` shapes (grill open item 1).** Every driver persists `{ toolUseId, content, isError, attachments? }` (§2.4). The separable text field is `content` when it's a string (codex, antigravity, most gemini, claude plain) or an array of `{type:"text"}` blocks (claude, fx ACP items). Cursor always persists an object, gemini/fx sometimes do: those take the whole-payload fallback (stringified + cut), which the renderers already handle because `stringifyResult`/`textOf`/`toolResultText` all accept a string. Claude image/document blocks (base64) are the one shape where cutting text would not shrink the row — they are replaced by a placeholder text block. Confidence: high (read every emit site).
- **A2 — Synchronicity audit (grill open item 2).** Four callers assume `attachSubagentWatcher` returns with `files` populated: the spawn IIFE (`ready` emitted right after), `reattachSession` (then `healWindowSize`), the two re-arm sites (result discarded). With the handle returned synchronously and `ready` awaited at all four, every observable ordering is preserved. Mid-seed arrivals: `syncSettled(id)` for a not-yet-rehydrated id is already a documented no-op, and the DB write it mirrors (`markSettledById`) happened before the call, so the later rehydrate reads the settled status; `hasMonitor(id)` false → `handleBackgroundTaskNotification` already falls back to the DB-only path; `discover()` cannot run (cycle gated) and the dir watcher is armed only by the first cycle; a second attach for the task detaches (aborts) the first. The one behavioural change is production `pump()` being a no-op while a job is pending (TT2 pins it). Confidence: high.
- **A3 — First retention pass duration and VACUUM estimate (grill items 3–4)** are measured by T14 on the copy; until then the plan carries the grill's ≈ 1.66 GB / ≈ 15 s extrapolations and `DB_COMPACT_SEC_PER_GB = 7.5`. The single-row parse of a very large `tool_result` cannot be yielded inside `JSON.parse`; T14 records `MAX(LENGTH(data))` among candidates so the residual block is known (if > 100 ms, the implementer caps a chunk at one such row and documents the residual in §10).
- **A4 — `activeRunCount()` as the Compact gate.** In-memory `active` + `startingTaskIds` is the same truth `cancelRun`/`sendInput` use; a held-for-background-agents run is still in `active` (released only by `maybeReleaseHeldTask`), so it blocks Compact too — intended (R5).
- **A5 — No new per-task claim in `sendInput`.** D6 names the existing `startingTaskIds` claim; it covers the mint window only. Two overlapping sends during a worktree restore both await the same teardown and `prepareWorkdir`'s reuse branch; that is today's behaviour, unchanged. A `pending` answer that precedes the mint reports the addressed `runId` (documented on `SendInputResult`); no client dereferences it beyond display.
- **A6 — The e2e cannot reproduce the multi-second stall** (a fake backend's DB is tiny); it pins the structural properties (real watcher on the resume path, other surfaces load, dedupe across attaches, `/health` responsive) while TT2 pins the timing bar on a 200k-row / 180 MB fixture with a structurally safe threshold (unfixed ≥ 500 ms vs asserted < 150 ms).
- **A7 — Breadcrumb ordering.** Deferring the slow-launch line into the IIFE means it may now follow a startup-question status instead of always being the run's first status line; the launch-failure case keeps today's early emission. Accepted for the `watcher` stage (D4).
- **A8 — `NODE_ENV === "test"` under `bun test`** gates the lag monitor off by default (Bun sets it); e2e backends inherit the Playwright process env (not `test`), so the monitor runs there and never adds a status line unless a real ≥ 1 s stall happens.
- **A9 — The `retention:*` bookkeeping keys ride the generic `preferences` store** (like `lastModel:<kind>`), so they appear in `GET /preferences` and `agetor config`; harmless and avoids a migration.
- **A10 — The test-only block route** (`AGETOR_TEST_BLOCK_ROUTE=1`) is the only way an e2e can make the core unresponsive on purpose; it is never registered in production.
- **A11 — The retention preference fails closed (review round 4, owner-delegated decision).** The original T4 parser returned the 30-day default for every unparsable value, so `agetor config archivedHistoryRetentionDays 0` (a user meaning "off") stored `"0"`, read as 30 and scheduled an irreversible trim within 5 s. Now: absent/blank → 30; an off-word (`off`/`0`/`false`/`no`/`none`/`disabled`, any case, trimmed) → off; an integer 1..3650 → that many days; **any other value reads as off**, never the default. `PUT /preferences/archivedHistoryRetentionDays` validates through `normalizeArchivedHistoryRetentionValue`: off-words are stored as `"off"`, day counts as the plain integer string, and anything else is a 400 naming the accepted values with nothing stored and no pass scheduled. The same review round bracketed every native Open panel (`openFileDialog` is a synchronous FFI call) with a context-free `native file dialog` lag label server-side and `withCoreBusySuspended` in the webview, made lag attribution prefer the most recently begun label (interleaved async labels make stack depth meaningless), started the lag monitor before the boot restore instead of after the API, and threaded the real re-stash outcome into `SendInputResult.savedToBacklog`.

**Chunked transcript reads (review follow-up, measured 2026-10-15 with `subagent-watcher-drift.test.ts`, load average 8–10).** The first pass above still read each transcript — and the main JSONL delta — in one unsliced block, so one file of 50–100 MB would block 125–250 ms on its own. `tailFile` and the main-signal scan now read in `TAIL_READ_CHUNK_BYTES` chunks with a deadline check between chunks (a single line longer than a chunk is read whole; the replay-floor `batchStart` is pinned for the whole drain).

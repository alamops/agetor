## 1. What we know

### Where the handoff comes from
- A step's prompt asks the agent to end its final message with one `<handoff>` block: `<handoff>`, a newline, the JSON, a newline, `</handoff>`, and nothing after it (`renderHandoffContract`, `src/shared/pipeline.ts:1008`). The schema is the `Handoff` interface (`src/shared/types.ts:593`): `schemaVersion`, `purpose`, `summary`, `reason`, `next` (string or null), `artifacts` (string[], "paths or URLs"), `openQuestions` (string[]), optional `status: "done" | "blocked"`.
- The runner joins all main-stream `assistant` rows of a run with `"\n"` (`assistantTextFrom`, `src/bun/pipeline-runner.ts:450`) and calls `classifyStepResponse` → `parseHandoff` (`src/shared/pipeline.ts:777`, `:827`).
- `parseHandoff` finds the last `<handoff…>…</handoff>` pair with the linear scanner `findLastHandoffBlock` (`src/shared/pipeline.ts:205`): an open tag pairs with the first close after it, the last pair wins, only the trailing 256 KB are scanned. The inner text loses an optional ```` ```json ```` fence, is `JSON.parse`d (brace-balanced fallback), and goes through `normalizeHandoff` (`:749`): 8,000 UTF-16 units per string field and per array entry, 50 entries per array, 64 KB for the whole object. Unknown keys are dropped.
- `src/shared/pipeline.ts` imports only types and `PIPELINE_LIMITS` from `./types.ts` (`:10-21`), so the webview can call `parseHandoff` directly. `RunPanel.tsx:112` already imports from it.

### How it renders today
- Every `assistant` event becomes `<AssistantBlock text>` (`RunPanel.tsx:5578`, `:6344`): one `ReactMarkdown` with `remark-gfm`, `ASSISTANT_MD_COMPONENTS` and `MD_URL_TRANSFORM`, and no `rehype-raw`. `AssistantBlock` receives only `text` — no task id, roots or pipeline context.
- Spike 1 (§2) shows react-markdown 10.1.0 turns the block into a bare escaped text node, not an element. With `.agetor-md`'s normal whitespace (`src/mainview/index.css:173`), the JSON collapses into one long wrapped line, `<handoff> {"schemaVersion":1,"purpose":…} </handoff>`, glued under the prose and outside the `> * + *` spacing rule. This is the raw text the owner sees.
- The step task's next prompt (a `user` bubble) already shows the previous handoff as a fenced ```` ```json ```` block between `--- BEGIN/END untrusted handoff <nonce> ---` markers (`composeStepPrompt`, `src/shared/pipeline.ts:1084-1118`). That is readable, but it is still raw JSON.
- The pipeline run view's history row prints `JSON.stringify(record.handoff, null, 2)` in a `<pre>` (`PipelineRunView.tsx:1311-1318`, test id `pipeline-run-history-handoff`). This is a second raw-JSON surface for the same object.
- CLI `agetor logs` prints assistant text verbatim (`src/cli/commands/logs.ts:238`). The TUI prints it truncated (`src/cli/tui/Dashboard.tsx:917`). `agetor pipeline status` prints no handoff content (`src/cli/commands/pipeline.ts:489-494`).
- Message search matches raw event text (`src/mainview/lib/event-search.ts:112`). Collapsed cards reveal themselves on a search jump through `useExpandOnJump` (`src/mainview/lib/use-expand-on-jump.ts`), as `CompactionSummaryBlock` and `ToolUseBlock` already do.

### Real handoffs (read-only query of the owner's `~/.agetor/agetor.sqlite`)
- 1,484 assistant events contain `<handoff`, and **every one belongs to a pipeline step task**. The 13 non-step events containing `<handoff` are inline-code mentions. No non-step event contains `</handoff>`.
- Harnesses: claude-code-kind harnesses (most), cursor 53, codex 15. Each event carries the whole block: there are no split open/close pairs. Cursor's 5 open-only events are prose mentions.
- In the 400-event sample, 398 have nothing after `</handoff>`, 395 open at a line start, and 395 use compact single-line JSON. Across all 1,482 parsed handoffs, 0 are fenced, 0 have extra keys and 0 have non-string array entries. 59 are `status: "blocked"` (4%) and 176 have `next: null` (12%).
- Sizes in the sample: `summary` p50 2,050 chars, p90 3,117, max 6,267, and 36% contain markdown (bold, code, lists). `reason` p50 477. `purpose` p50 384. `artifacts` p50 7 entries, max 23. `openQuestions` p50 4, max 17. Whole handoff p50 4.4 KB, max 12 KB. A fully expanded inline card would be very tall.
- Artifact shapes across all handoffs (13,151 entries, spike 4): relative paths 70% (`docs/plans/x.md`, `src/…`; relative to the shared worktree), absolute paths 19% (worktrees, `/private/tmp/…/scratchpad/…`, `~/.agetor/…`), URLs 6%, non-path text 3.5% (`jubarteai:<uuid> (note)`, `commit 1becb711 on <branch>`, "Local Docker images …"), `path (note)` or `path — note` 1.7%, `path:line` anchors 0.4%. A plain "open as path" would mis-handle the note forms.
- In 7 of 1,484 events, prose follows `</handoff>` in the same event. The block is not always last, so the card must render in place between the prose before and after it.
- 24 events contain several `<handoff>` occurrences, because a JSON value or the prose quotes the tag (for example, "a claude step's real <handoff> was ignored").

## 3. What we're assuming
- **Detection is per event.** Claude, codex and cursor write the whole block in one `assistant` event (proved above). antigravity emits one `assistant` event per `text_delta` (`src/bun/antigravity-tmux.ts:164`), so a handoff there would span many events and no card would render. There is no antigravity handoff in the data. If the owner wants antigravity covered, the plan needs client-side merging of adjacent assistant events, a much bigger change that touches the dedup and evid invariants (`RunPanel.tsx:5313`).
- **The card is webview-only plus a pure shared helper.** No server, API or DB change is needed, unless the owner wants an in-app file preview (§4 Q6) or the runner fix (§4 Q7).
- **`normalizeHandoff`'s caps bound the render cost** (≤ 64 KB per card). A long `summary` renders through the existing markdown components, so links open externally and images resolve through `MdImageScope`.
- **Handoff text gets the same trust as assistant text.** It is agent output already rendered as markdown today. The card adds clickable artifacts, and those go through the existing `/open-path` and `/open-external` routes. These are desktop-only, `existsSync`-checked, and restricted to http, https and mailto, the same trust tier as `SendUserFile` tiles. Nothing new reaches the filesystem.
- **Relative artifacts resolve against the step task's roots.** A step task shares the parent's `worktreePath`/`workdir`. If the worktree was torn down, `/open-path`'s single-root resolution 404s even when the file exists in `workdir`. Resolving client-side to absolute candidates `[worktreePath, workdir]` (the `MdImage` rule) would avoid that.

## 4. What we must ask the owner
1. **Which surfaces?** The core is the RunPanel transcript card. Should the same component also replace (a) the run view's raw-JSON history `<pre>` (`PipelineRunView.tsx:1311`; this changes the `toContainText("schemaVersion")` assertion in `e2e/pipelines-run.spec.ts:365`), (b) the inlined previous handoff in the next step's prompt bubble, and (c) `agetor logs` / the TUI as a plain-text `handoff›` digest? Based on your usual preference the recommendation is (a) yes, and (b) and (c) as explicit decisions.
2. **Gating.** Should cards render only in pipeline step tasks (100% of real handoffs; zero risk of beautifying an agent that merely talks about handoffs), or in any task's assistant message?
3. **Inline card density.** Proposal: a header with a status chip (done / blocked in warning tone), `next` as "→ Grilling" (or "Last step"), and an "Open" button for the modal. Below it: a 3–4-line markdown preview of `summary`, the artifacts as a chip row (first ~6, then "+N"), and the open-question count. Everything else goes in the modal. Alternatively, the full handoff could expand in place with no modal, or the modal could be the only view.
4. **Modal.** Should it cover only the panel (as `PlanDialog` does) or the whole window (portaled, as `MdImage`'s dialogs are)? Should it offer "Copy JSON" and a "Raw" toggle? Should it show the pipeline context (step name, where `next` resolves, "this handoff advanced the pipeline / was superseded" from the parent's history `handoffRunId`)?
5. **Quick-open behaviour.** Proposal: click opens with the OS default app. A context menu offers Reveal in Finder and Copy path. URLs open in the browser. Free-text entries (`jubarteai:<uuid>`, `commit …`) show as non-clickable text with Copy. A `path (note)` shows the note muted beside the chip. `path:123` opens the file without jumping to the line, because `/open-path` can't take a line. Missing files: check existence up front with one batched `/refs/resolve` and dim missing chips (the `SentFilesCard` pattern), or only find out on click (the `AttachmentChips` pattern)? And should relative paths fall back from the worktree to `workdir`?
6. **In-app preview?** "Open referenced files" could also mean viewing a `.md`/text artifact inside the modal. No route serves text file contents today: `/files/preview` serves images only. A new route would read agent-chosen bytes and must go through `core-file-read.ts` while disclaiming (D26), with size caps. Is this in scope, or is OS-open enough?
7. **Runner parser bug.** The inline-code mention bug (§2) causes spurious reminders today. Should we fix it in this feature by sharing one code-span-aware locator between the runner and the card, so the two can never disagree? Or should it be a separate fix? Either way the card must not show "valid handoff" while the run view says `handoff-invalid`. Related: should a handoff wrapped in a code fence count? The runner accepts one today, there are none in the data, and a quoted example in a fence would then be beautified.
8. **Several blocks or an invalid one.** Should only the last block of an event become a card (runner semantics), with earlier ones left raw or carded as "draft"? Should a tag whose JSON doesn't parse get an "Invalid handoff" card showing the parse error plus the raw text, or stay raw?
9. **Search.** Should message search keep matching the raw JSON (`schemaVersion` would hit a card that doesn't show it), or should `searchableEventText` index only the card's visible text?
10. **Antigravity** (see §3). Is it acceptable that a delta-streamed handoff stays raw?

## 7. Risks & blast radius
- **The card and the runner can disagree** unless they share one locator. Today they would on 1 of 1,484 real events (the runner bug). Rendering through `parseHandoff` exactly as the runner does keeps them aligned but inherits the bug.
- **Over-eager detection.** Agents discussing handoffs, including agents building this very feature, quote `<handoff>` in prose and code. Detection must skip inline and fenced code. Gating on step tasks removes the remaining risk.
- **Performance.** `RunEventList`'s `blocks` memo re-renders only on event changes. The splitter is O(n) at about 0.06 ms per event, and a card's markdown preview must stay as cheap as today's `AssistantBlock`. Cards must not fetch anything per render: one batched existence check per card, cached, if Q5 chooses up-front checks.
- **RunPanel invariants.** If the modal mounts at `RunPanelBody` level, its key must be namespaced (`handoff-…`) and its open-state must reset in the `[task.id]` reset effect. A card-local modal must portal or accept panel-scoped placement. Escape layering already works through the `Dialog` stack.
- **Existing e2e assertions** that read raw handoff text or `schemaVersion` must be updated (`e2e/pipelines-run.spec.ts:365` if Q1(a) is accepted). Specs that assert transcript text such as "Done." keep passing because prose before the block still renders.
- **Runner fix (Q7) is behaviour-changing.** A handoff wrapped in a fence or quoted in inline code changes classification. It needs unit tests in `src/shared/pipeline.test.ts` and a pass over `src/bun/pipeline-runner*.test.ts`.

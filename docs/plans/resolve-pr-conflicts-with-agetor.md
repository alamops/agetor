## 1. Objective & success criteria

When a GitHub PR in the PR detail subpage shows "Conflicts must be resolved before merging", a **Resolve with Agetor** button appears next to that message. Clicking it opens a **stacked modal** where the user picks harness / model / effort / mode (same semantics as New Task) over an **editable prefilled prompt**. Submitting creates **and starts** a task with `isolation: "worktree"` whose worktree is checked out **on the PR's head branch** (fetched fresh from origin). The prefilled prompt instructs the agent to fetch origin, merge the latest target branch into the head branch, resolve conflicts treating **both sides as important**, commit the merge, and **never push** — the user reviews and pushes via the existing Commit & Push flow, which updates the PR directly.

Success: button appears only for open, same-repo, `mergeableState === "dirty"` GitHub PRs; task materializes a worktree on the existing head branch; task delete/archive never deletes that branch; typecheck + full `bun test` green.

It does **not** yet say whether the head lives on a fork → must add a cross-repo signal in `normalizeMergeability` (`src/bun/github.ts:2305`) from the REST payload's `head.repo.full_name`.
- Picker mechanics to mirror: `NewTaskForm.tsx` — harness grid with availability dots (~671), mode select via `supportedModes` (~704), model select merging `AGENT_OPTIONS` + CLI-discovered `agentModels` (~744), effort via `supportedEfforts` (~757). - Harness data: the new dialog self-fetches `api.listHarnesses()` / `api.listAgentModels()` (consistent with GitHubDialog's direct-api style; avoids threading new props from App).
- Stacked dialogs are now supported: `ui/dialog.tsx` has a module-level `openDialogStack` (topmost-only Escape/Tab) — landed on main 2026-07-23. A true modal from inside GitHubDialog is the convention-sanctioned shape for this.
- Backend gap: `createTask` (`orchestrator.ts:1774`) always mints a fresh branch (template + `ensureUniqueBranch`) off a sha-pinned `baseRef`; `prepareWorkdir` (`worktree.ts:618`) either `git worktree add -b <new> wt <base>` or reuses its own branch. **No fetch, no existing-branch checkout, no merge helper.** `removeWorktree` (`worktree.ts:838`) unconditionally `git branch -D` — must be gated for tasks on real PR branches.
- `POST /tasks` (`server.ts:2953`) already forwards the whole body into `createTask`, so a new input field is wire-compatible; `api.createTask` (`api.ts:1005`) needs the typed field.
- Test conventions: `worktree.test.ts` `makeRepo()`/`fakeTask()`; `AGETOR_DATA_DIR` mkdtemp before importing db; dynamic imports. New tests need a second bare "origin" repo to simulate a remote-only head branch.

## 3. Approach & key decisions (owner-confirmed)

1. **Agent runs the merge** — agetor only prepares the worktree on the head branch; the prompt drives `git fetch` + `git merge origin/<base>` + resolution. No merge helper, no carve-out from "git failure aborts start".
2. **Fork PRs: hide the button** — shown only when head repo == base repo (`crossRepo === false`).
3. **Task works on the PR head branch itself** — local branch tracking `origin/<head>`; push-after-review updates the PR. Consequence: task teardown must never delete this branch.
4. **Re-run reuses the worktree as-is** — no reset/refetch logic; the prompt's fetch picks up new base commits.
5. New Task concept: `branchSource: "created" | "existing"` on `Task` (migration 028, default `"created"`), plus `existingBranch?: string` on `CreateTaskInput`. `baseRef` stays a frozen sha (pinned to `origin/<head>` at create time) so diff/review views keep working; the *merge target* freshness is the agent's job, not `baseRef`'s.
6. The prefilled prompt is generated by a pure, unit-testable function in `src/mainview/lib/resolve-conflicts-prompt.ts`.

## 4. Work breakdown — implementation tasks

### Task A — backend existing-branch tasks + crossRepo signal (Wave 1)
**Owns:** `src/shared/types.ts`, `src/bun/migrations/028_branch_source.sql`, `src/bun/migrations/index.ts`, `src/bun/db.ts`, `src/bun/orchestrator.ts`, `src/bun/worktree.ts`, `src/bun/server.ts`, `src/bun/github.ts`, `src/mainview/lib/api.ts` (type-level additions only: `existingBranch` on the createTask input type — no other api.ts changes).
- `types.ts`: `Task.branchSource: "created" | "existing"`; `GitHubPullMergeability.crossRepo: boolean` (and `headRepo: string | null` if cheap).
- Migration 026: `ALTER TABLE tasks ADD COLUMN branch_source TEXT NOT NULL DEFAULT 'created'`; wire into `migrations/index.ts`; `db.ts` read/write mapping.
- `orchestrator.createTask`: accept `existingBranch` (only meaningful with worktree isolation + git repo; reject otherwise with `{ error }`). When set: run a targeted `git fetch origin <existingBranch>` (best-effort `--all` fallback), require `origin/<existingBranch>` or local `<existingBranch>` to resolve (else `{ error }`), set `branch = existingBranch`, `branchSource = "existing"`, pin `baseRef` to the sha of `origin/<existingBranch>` (fallback local). Skip branch-template rendering and `ensureUniqueBranch`.
- `worktree.prepareWorkdir`: when `task.branchSource === "existing"` and materializing fresh: fetch `origin <branch>` best-effort; if local branch exists → `git worktree add wt <branch>` (existing arm); else `git worktree add --track -b <branch> wt origin/<branch>`. Reuse arm unchanged.
- `worktree.removeWorktree` (and any archive teardown path that deletes branches): skip `git branch -D` when `branchSource === "existing"`.
- `github.normalizeMergeability`: derive `crossRepo` from `head.repo.full_name !== base.repo.full_name` (null-safe: missing head repo ⇒ treat as cross-repo).
- `server.ts`: ensure `existingBranch` passes through `POST /tasks` (it forwards the body already; add to any explicit pick-list if one exists).
**Acceptance:** typecheck green; existing tests still pass; `createTask({ existingBranch })` behavior as above.

## 7. Blast radius & risks

- `removeWorktree`/archive teardown branch deletion — the gate must cover **every** path that deletes `task.branch` (delete, archive-delete, agent-switch teardown if any). A miss deletes a real PR branch.
- Worktrees page / diff view / PR-composer tolerate a non-`agetor/`-prefixed task branch (investigation found no hard assumption, but review should watch for `agetor/` prefix special-cases).
- `ensureUniqueBranch`'s `takenBranches` bookkeeping: an existing-branch task's branch must not collide with another task pinning the same branch — createTask should reject if another live task already owns that branch name (cheap check against tasks table).
- Codex sandbox: worktree `.git`-file escalation (`gitWritableRootsSync`) already handles linked worktrees; merge commits by the agent are covered by the existing full-access escalation.
- GitLab/Bitbucket: feature is GitHub-only by gating on `provider === "github"` (mergeability endpoint doesn't exist for others).
- Migration 028 runs against `~/.agetor-dev` during dogfooding — additive column, default backfills, safe.

## 8. Open questions / assumptions

- Assumption: the agent commits the merge locally (needed for a clean reviewable state); the "no push" rule is enforced by prompt text only — consistent with agetor's no-sandbox philosophy.
- Assumption: success UX after submit is a confirmation inside the dialog/toast; we do not auto-navigate to the board or auto-open the task.
- Assumption: `existingBranch` tasks are only creatable with `isolation: "worktree"`; the modal doesn't expose an isolation toggle.
- Deferred: fork-PR support; GitLab/Bitbucket mergeability; auto-refresh of PR mergeability after the user pushes the resolution.

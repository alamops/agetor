## One-way doors awaiting a human

None. No schema/migration, auth/tenancy boundary, money, or public API contract changes. The only payload touched is the already-typed optional `pipelineId` on `POST /tasks` (`src/mainview/lib/api.ts:1667`), which the server already accepts and validates.

## Settled by evidence (not asked)

- **Exactly two Git-integration dialogs create tasks.** `CreateTaskFromIssueDialog` (issue detail, "Work on this with Agetor") and `ResolveConflictsDialog` (GitHub PR detail, "Resolve with Agetor"). `grep` over `createAndStartTask`/`api.createTask` finds only `App.tsx` (New Task), those two dialogs, and the shared `TaskLaunchPickers.createAndStartTask`; `TaskLaunchPickers` has four consumers, and only those two are Git dialogs (`docs/architecture/issue-tasks.md:5`; `docs/architecture/clone-repository.md:61`).
- **`CloneProjectDialog` is the only adjacent candidate, and it needs server work.** It shares `useTaskLaunch`/`TaskLaunchPickers` for the ELI5 explainer (`CloneProjectDialog.tsx:103`, `:427`), but `POST /projects/clone` validates a fixed launch whitelist and drops any `pipelineId` (`src/bun/server.ts:1178-1237`, `:1787-1795`). Including it means pre-clone pipeline validation, plumbing `pipelineId` through the clone route, and settling `isolation:"none"` pipeline semantics in a just-cloned repo.
- **No backend, route, schema, migration or type change is needed for the two in-scope dialogs.** `api.createTask` already types `pipelineId` (`api.ts:1667`); `POST /tasks` already accepts it (`server.ts:5492-5504`); `createTask` rejects `pipelineId` + `agentProfileId`, validates the graph and every non-human step's profile, mirrors the start step's cosmetic fields, and stores the idle `pipelineRun` (`orchestrator.ts:8493-8515`, `:8545-8548`, `:8700-8732`); `startTask` branches a pipeline parent straight to `startPipelineRun` before harness pre-flight (`orchestrator.ts:2054-2057`).
- **`existingBranch` + `pipelineId` is a supported combination.** `createTask` resolves `existingBranch` before pipeline binding (`orchestrator.ts:8429-8470`); `prepareWorkdir` checks the existing branch out (`worktree.ts:1009-1073`); the runner materializes the parent worktree once and copies `branch`/`worktreePath` to every step (`pipeline-runner.ts:1024-1032`, `:1346-1401`). No route or create guard rejects the pair.
- **The runner forbids a human start step, and `createTask` rejects a non-human step with no/deleted profile.** `pipeline-runner.ts:1826-1831`; `orchestrator.ts:8498-8515`. These are two of the preflight conditions the picker must expose before submit.
- **Step tasks inherit the parent's references (including the issue snapshot) but not the issue URL.** `pipeline-runner.ts:1346-1348` copies `parent.references` plus handoff refs into every step task, and `:1380` sets `issueUrl: null`. The parent keeps `issueUrl`/`issueSnapshot` (`orchestrator.ts:8700-8732`, `:8765-8775`). This change needs no server work; only the parent card links to the issue.
- **`createAndStartTask` deletes the newly created row when start fails** (`TaskLaunchPickers.tsx:700-713`); deleting a pipeline parent cascades its step rows (`orchestrator.ts:9195-9220`). Preflight is the mitigation; the rollback itself stays as-is.
- **New Task's exact picker semantics are the parity target.** State `pipelineId` at `NewTaskForm.tsx:208`; selected pipeline/stale guard at `:524-539`; start step/profile/harness resolution at `:548-553`; `effectiveAgent` at `:568-570`; pipeline-specific overage at `:598-608`; payload at `:647`; `rememberPicks` skipped for pipelines at `:659-666`; post-submit reset at `:672-673`; JSX at `:840-898`.
- **The pipeline list is already available to the webview.** `usePipelines` is module-cached (`src/mainview/lib/pipelines.ts:68-100`), `App.tsx:341` mounts it after preferences load, and `api.listPipelines` exists (`api.ts:690`). No new request layer is needed.
- **`PipelinePicker` already satisfies the nested-dialog popover contract.** `data-popover-open` only while open (`PipelinePicker.tsx:143`), Escape closes before the Dialog (`:48-60`), and the `data-testid`s are stable (`pipeline-picker`, `-trigger`, `-popover`, `-row`, `-none`, `-clear`).
- **There is no React component-test harness.** `bunfig.toml` scopes `bun test` to `src/`; `package.json` has no jsdom/testing-library; UI changes are proven by Playwright e2e (`package.json:25`, `playwright.config.ts`).
- **This worktree has no `node_modules`.** `bun run typecheck` fails with `tsc: command not found`; the implementation step must run `bun install --frozen-lockfile` before typecheck/tests/e2e (investigation §6).

## Implementation invariants the plan must honor

These are not new owner decisions; they follow from D1-D11 and the code, and they are the traps the plan should encode as acceptance criteria.

- **Opt-in only.** `useTaskLaunch`/`TaskLaunchPickers` gain a `withPipelines` opt-in (default **false**). `AgentProfileFormDialog` (`hideProfilePicker`) and `CloneProjectDialog` must render byte-for-byte as today; the existing `e2e/agent-profiles*`, `e2e/clone-project.spec.ts`, and `e2e/clone-providers.spec.ts` suites are the guard.
- **One implementation, both dialogs.** Put the pipeline section in `TaskLaunchPickers` behind the opt-in rather than duplicating it in each dialog, so the issue and PR dialogs cannot drift (`docs/architecture/issue-tasks.md:5`).
- **Effective launch identity.** While a pipeline is selected, `effectiveAgent`/`effectiveKind`/`effectiveStatus` must describe the pipeline's **start-step profile**, not the hidden manual picker: `resolveStartStep(pipeline.graph)` → `agentProfileId` → `profiles` → `harnesses`. The prompt composer's `@`/skill discovery, the overage check, the availability/auth hint, and `canSubmit` all read those fields. Getting this wrong both blocks valid pipelines and allows invalid ones. If the start profile is unresolved, do **not** let the manual picker's `effectiveStatus` turn `canSubmit` true — the preflight reason must explicitly fail the pipeline selection, and the overage check is skipped or carries the same reason.
- **Worktree behavior unchanged.** The issue dialog's existing isolate/baseRef/branch options apply to the pipeline parent; the runner materializes that worktree once and every step runs in it. The PR conflict dialog remains locked to `existingBranch: context.headRef` with `isolation:"worktree"`. No new worktree controls or restrictions.
- **Creation flow unchanged.** Both dialogs still call `createAndStartTask` with `column:"ready"`, the same title/prompt/taskType/references/issue metadata/worktree fields; only `pipelineId` is added and `agentProfileId` omitted. The parent auto-starts; there is no separate "create then run" step.
- **Goal semantics.** The dialog's prompt becomes the pipeline run's goal; the runner composes each step's prompt from that goal plus the step's instructions and prior handoffs. For the PR dialog, the conflict-resolution prompt is the goal for every step (D8). No prompt wrapping change is needed.
- **Overage parity.** A pipeline's overage check uses the start-step harness kind and the **raw prompt** (no `composeLaunchPrompt` profile preamble), matching `NewTaskForm.tsx:598-608`. If the start profile is unresolved, show the preflight reason rather than a silent disabled button.
- **No "remember picks" for pipelines.** `rememberPicks()` stays a no-op when a pipeline is selected (there is no "last used pipeline" preference); `NewTaskForm.tsx:659-666` is the reference.
- **Payload.** Add `...(pipelineId ? { pipelineId } : {})`; omit `agentProfileId` when a pipeline is selected. The server overrides the cosmetic `agent`/`mode`/`model`/`effort`/`speed`/`maxMode` fields from the start step (`orchestrator.ts:8545-8548`, `:8700-8725`), so the body may keep the hidden manual values; prefer `effectiveAgent`/start-step values where it stays self-consistent.
- **Stale-selection guard.** Clear a selected pipeline once `pipelinesLoaded` is true and the list no longer contains it, mirroring `NewTaskForm.tsx:535-539`. Do not clear against a not-yet-loaded list.
- **Loaded flags, not lengths.** `useAgentProfiles` exposes a `loaded` flag (`agent-profiles.ts:63-101`) that `useTaskLaunch` does not currently surface; preflight needs it (or an equivalent `launch.loading` gate) so a pipeline's start profile is not falsely reported missing during the first fetch. `usePipelines` likewise exposes `loaded`/`error` (not just `pipelines`), which D9's empty/error state and the stale guard need.
- **Import cycle.** Import `@/components/pipelines/PipelinePicker` directly, not through the `@/components/pipelines` barrel: the barrel pulls `StepPanel` → `AgentProfileFormDialog` → `TaskLaunchPickers`, creating a cycle (investigation §7).
- **Test-id scoping.** The board's `NewTaskForm` always renders a `pipeline-picker` while the Git dialog is stacked over it, so every e2e locator must be scoped to the dialog (`issueTaskDialog.getByTestId("pipeline-picker")`), never `page.getByTestId(...)`.
- **Busy state.** Disable the pipeline picker (and its manage row) while `submitting`, matching the rest of the dialog; the existing `PipelinePicker` already accepts `disabled`.
- **Manage-row verification.** Because D6/D6a add a new navigation edge, cover it too: Manage from an untouched dialog goes to the Pipelines list; Manage from a dirty dialog shows the discard confirm and only navigates on confirm. If the e2e fixture cannot reach the full Pipelines page, at least assert the callback/confirm and record the gap rather than leaving the new edge untested.
- **Rollback stays.** `createAndStartTask` still deletes the parent if `startTask` fails; do not change that behavior in this ticket. Preflight reduces the failure surface, but a race (profile/harness deleted between preflight and submit) still surfaces the inline error.
- **Docs in the same change** (`CLAUDE.md:5`): `docs/architecture/pipelines.md` entry points/picker (the `:151` line), `docs/architecture/issue-tasks.md:5` (shared pickers now include Pipeline), `docs/architecture/agent-profiles.md:42-44` ("one selection" now has a third kind), and `docs/architecture/clone-repository.md:61` (pipeline deliberately remains off there).

## Non-functional, trust and rollout

- **Local single-user trust shape is unchanged.** One Bun process owns SQLite + the loopback API; the webview is the only client; no new role, tenancy boundary, or remote input is introduced. Pipeline validation remains server-authoritative (`createTask`/`startPipelineRun`), and the dialog preflight is advisory.
- **No new fetch or polling layer.** The picker reuses the module-cached `usePipelines` (`pipelines.ts:68-100`); opening a dialog costs no extra pipeline request, and the preflight is in-memory. No performance budget changes.
- **Issue text remains untrusted.** The dialog already embeds issue text behind `ISSUE_UNTRUSTED_CONTENT_WARNING`; selecting a pipeline does not change that, and pipeline handoffs carry their own fencing (`docs/architecture/pipelines.md`). The PR conflict prompt is likewise unchanged.
- **Worst-case failure and rollback.** The only new failure surface is a pipeline start failure after create (e.g. a profile/harness deleted between preflight and submit). `createAndStartTask` deletes the parent and cascades step rows, then shows the existing inline error. There is no data migration, no partial state to clean up, and no feature flag/rollout sequencing — the change is UI-only and the server already accepts `pipelineId`.
- **No new observability required.** Existing server errors and the dialog's inline `submitError` are the signal; no new logging/telemetry is planned.

## Assumptions still open

- **`usePipelines` is warm when the dialog opens.** App mounts it after preferences load (`App.tsx:341`), so the picker normally reads a resolved cache. If a Git dialog is somehow the first consumer, the section shows its loading state and the stale guard must not clear a selection until `pipelinesLoaded`; no new fetch layer is planned.
- **Preflight waits for profiles to be known.** `useTaskLaunch` currently returns `profiles` but not `loaded`; the plan must add the flag (or gate on `launch.loading`) so a valid pipeline isn't reported as "profile deleted" during the first profile fetch. If it cannot, the plan must fall back to the current generic loading state for the preflight reason.
- **Step tasks inherit references, not the issue link.** The parent card keeps "View issue"; step cards will not. If the owner expected every step card to link back to the issue, that is a separate `pipeline-runner.ts` change and would need its own decision.
- **Rollback is untouched.** A start failure still deletes the pipeline parent and its step rows; the inline error wording stays `createAndStartTask`'s. Preflight is best-effort, not a transaction.
- **Only the start-step harness is preflighted.** A later step whose own harness is disabled or logged out is not blocked at create time; it surfaces as a run block when that step is reached, exactly as a pipeline launched from New Task today. Whole-graph harness preflight would be a separate change. `createTask` does still reject a later non-human step whose profile is missing/deleted (`orchestrator.ts:8503-8515`).
- **Existing branch-collision behavior remains.** `createTask` rejects an `existingBranch` already checked out by another non-archived task (`orchestrator.ts:8449-8453`); a pipeline launched from the PR conflict modal inherits that error and surfaces it inline. This change does not alter it.
- **"Dirty" for the manage confirm** means any user change to prompt text, references, task type, worktree options, or pipeline selection since the dialog opened. The plan must expose/derive that signal (the issue dialog already has `promptDirty`/`typeDirty`; `useWorktreeOptions` may need a dirty flag or a comparison to its open-seed). If the plan cannot detect worktree changes cheaply, it must state the narrower definition (prompt/references/type/pipeline) in the confirm copy rather than silently ignoring worktree edits.
- **Per-open reset also needs a context-change reset if the dialog stays mounted while the issue/PR changes.** The issue dialog already resets prompt/type/references on a context change, so clear the pipeline there too; the PR dialog's reset keys on `open`, so add a context key if the app can switch PRs while the dialog stays open. Otherwise one issue's pipeline selection could carry into another within one open.
- **Manage lands on the Pipelines list page** (`App.openPipelinesPage`), not Settings → Pipelines; this matches New Task's `onOpenPipelines`. If the owner wants Settings instead, the callback target changes.
- **The pipeline summary's "starts with" line** uses `pipelineStartStepProfile?.name`, matching New Task; when the start profile is missing it is omitted and D3's inline reason carries the explanation.
- **First-load states are explicit.** While the pipeline list is still fetching, show a disabled "Loading pipelines…" state (not "No pipelines yet."); while profiles are still fetching, do not render a "profile deleted" preflight reason — show the dialog's loading state or a neutral "checking the pipeline…" reason.
- **Clearing a pipeline does not restore the Agent profile that was cleared when it was picked.** New Task behaves the same way: picking a pipeline clears the profile, and clearing the pipeline leaves the manual Agent block with no profile selected. If the owner expects restoration, that is a separate UX change.
- **Payload self-consistency.** The server overrides the cosmetic launch fields from the pipeline's start step (`orchestrator.ts:8545-8548`, `:8700-8725`), so sending the hidden manual values is harmless; the plan should still prefer `effectiveAgent`/start-step values where it keeps the body readable. No server behavior depends on it.
- **e2e environment.** The shared Vite server is pinned to `:5173` and `reuseExistingServer` can silently reuse another checkout's Vite; the implementation must ensure nothing else holds the port or set `AGETOR_E2E_VITE_PORT`. Each worker gets its own headless backend/token/data dir and GitHub stub (`e2e/fixtures.ts`), and the fake driver is enabled by the fixture.
- **No feature flag.** The change ships behind the existing pipelines feature; a user with zero pipelines simply sees the always-visible "No pipeline" section (D9).

## 1. Objective & success criteria

Let the user point an agent at something reported on the repo's issue tracker. Three entry points, one plumbing:

1. **Issue detail page → "Work on this with Agetor"** (Git Integration dialog, `IssueActions`) — a stacked dialog, the exact sibling of "Resolve with Agetor" on a conflicted PR: pick harness / mode / model / effort over an editable prefilled prompt, then **create & start** a task in a fresh worktree branch.
2. **New Task sidebar → paste an issue URL** — seeds title + prompt for the selected project, links the task to the issue; the user finishes the form as usual (backlog or run).
3. **CLI → `agetor add --issue <url>`** — same seeding, non-interactive or wizard.

Every task created this way carries `task.issueUrl` (migration 048), which powers a durable **"View issue"** affordance (run panel button + card context-menu entry → opens the Git dialog directly on that issue, mirroring `prUrl`/"View PR") and prefills **`Closes #N`** into the PR body when the user later opens "Create PR" from that task.

The prompt embeds the issue (title, metadata, body) and its **full comment thread** — the server pages comments (up to 5×100) — inline up to a byte cap, and the **complete thread snapshot** is written to `~/.agetor/issue-threads/<taskId>/issue-<n>-thread.md` and attached as a task *reference* so the agent can read it in full regardless of the inline cap or Gemini's 4 KB argv limit. When `gh` (GitHub) / `glab` (GitLab) is on `PATH`, the prompt also carries a one-line **re-fetch command** so the agent can pull the live thread later.

**Done means:** all three entry points create a task whose prompt contains the issue body + thread + directives; `issueUrl` persisted and surfaced; snapshot file written on create and removed on delete; wrong-repo URLs rejected; Gemini over-cap prompts blocked in the UI with a clear message; `bun run typecheck` + `bun test` green; new e2e spec green.

## 3. Approach & key decisions

1. **One server route feeds all three entry points:** `GET /github/issue-thread?path=&number=` → `gitHost.issueThread` → `{ ok, repo, item, comments, truncated, refetchCommand }`. Client-side (webview + CLI) builds the prompt and the snapshot markdown from it with shared pure functions; `POST /tasks` receives `issueUrl` + `issueSnapshot`. The server never re-fetches at create time. (Owner-confirmed: full thread, capped 5×100.)
2. **Snapshot as a task reference** (owner-confirmed): `createTask` writes `dataDir/issue-threads/<taskId>/issue-<n>-thread.md` and appends `{ path, isDirectory: false }` to the row's references; `deleteTask` removes the directory; archive keeps it (unarchive/resume must still find it). Inline prompt is capped at `ISSUE_PROMPT_INLINE_MAX_BYTES = 32 768` and points at the snapshot when cut.
3. **Re-fetch hint** (owner-confirmed): `refetchCommand` computed server-side — GitHub `gh issue view <htmlUrl> --comments` when `gh` is on PATH (URL form works on GHES hosts too); GitLab `glab issue view <iid> --comments --repo <owner/name>` when `glab` is on PATH; Bitbucket `null`; absent binary → `null` and the line is omitted.
4. **Prompt directives** (owner-confirmed): investigate & reproduce first → implement the fix/change + tests → commit locally referencing the issue (`Fixes #N` for GitHub, `Closes #N` for GitLab, `issue #N` for Bitbucket) → never push. No "comment on the issue" directive.
5. **Gating** (owner-confirmed): the button shows for every issue (open or closed) on every provider with an issue tracker; no `provider === "github"` hardcode.
6. **Provenance field:** `Task.issueUrl` (migration 048, nullable) — create-time only, validated (`parseIssueUrl`) and **same-repo checked** against `providerRepoForDir(workdir)` (case-insensitive `owner/name`, provider must match), never patchable. This is what makes "View issue" and `Closes #N` safe by construction.
7. **Generalize the detail prefill instead of adding a parallel one:** `GitHubPullDetailPrefill { projectPath, number, prUrl }` becomes `GitHubItemDetailPrefill { projectPath, kind, number, url }` (prop `itemDetailPrefill`); the effect pair branches on `kind`. Keeps one mechanism, one set of guards.
8. **Extract the shared launch machinery** rather than copy 300 lines: `TaskLaunchPickers.tsx` exports `useTaskLaunch()` (harness/model/prefs fetch + picker state + `rememberPicks`), `<TaskLaunchPickers>` (harness grid + mode/model/effort selects + availability/auth hints) and `createAndStartTask()` (create → start → delete-rollback). `ResolveConflictsDialog` is refactored onto it with identical behavior; `CreateTaskFromIssueDialog` is the second consumer.
9. **Gemini cap surfaced before submit:** shared `promptByteOverage(kind, prompt)` (`src/shared/prompt-limits.ts`, the constant moves there and `agents.ts` re-exports it); the issue dialog and the New Task form show a warning and block submit when the selected harness is capped and the prompt exceeds it.
10. **Title template:** `Issue #<n>: <title>` (neutral — not every issue is a bug). Branch is minted by the normal template; no `existingBranch`.
11. **Paste-URL semantics in the form:** requires a selected project; the fetched item's `htmlUrl` must equal the pasted URL (normalized) or the load fails with "points at a different repository than the selected project". Title is set only when empty; prompt is replaced when empty, otherwise the built prompt is appended after a blank line. A "Issue #N ✕" chip shows the link and clears it (and the snapshot).

## 1. Objective & success criteria

A client that reconnects to `GET /tasks/:id/events` receives **only the `run_events` it missed**, resumed from a cursor (the `run_events.id` it last saw). When the gap is larger than the replay window (800 events or 4 MB), the server says so (`snapshotRequired`) and sends the fresh window on the same connection; the client drops its local copy and reloads from it. The desktop webview (RunPanel), `agetor logs` and the TUI all use it.

Done means:

1. **Server.** `GET /tasks/:id/events` accepts a cursor from `Last-Event-ID` (preferred) or `?afterId=`; answers a resume (`replay_meta.resumedAfter`) or a snapshot (`replay_meta.snapshotRequired: true`) per D2/D3/D15; writes an SSE `id:` line on every saved row, replayed or live (D20); CORS allows `last-event-id`.
2. **Live frames carry their stored row.** Every save-then-send site sends the stored `id` and `ts` (D11); a dedup hit sends nothing (D12); send order equals id order, documented and tested (D19).
3. **The four unsaved status/stderr lines are saved** (D4): `started — …`, `background agents still running (N) — holding in running`, `exit:N` / `cancelled (exit:N)`, and the spawn-rejection `cancelled` / `String(err)`.
4. **Clients.** RunPanel resumes without re-rendering or duplicating anything, resets on a snapshot with a muted notice, and refetches pending interactions + kicks its polls on every reconnect (D18). `agetor logs` never reprints after a reconnect and prints a dim notice on a snapshot. The TUI resumes, and resets with a dim notice on a snapshot.
5. **Tests.** Unit + integration + one Playwright e2e spec (D10) pass; `bun run typecheck` is green; the full `bun test` suite is green except the three failures already red on `main` (tmux-socket ×2, reconcile-cancel).
6. **Mixed versions stay correct**: an old CLI against the new core behaves as today; a new client against an older core gets today's full replay, filtered by id (D16).

## 3. Approach & key decisions

### 3.1 Wire contract (pinned — every task codes against this)

**Request.** `GET /tasks/:id/events[?anchor=0][&afterId=<n>]`, optional header `Last-Event-ID: <n>`.

**Cursor resolution** (`resolveResumeCursor(header, query)`, `src/bun/event-resume.ts`): the first of `[header, query]` that matches `/^[0-9]{1,16}$/` and is a safe integer is the cursor; anything else (absent, empty, negative, decimal, non-numeric, too long) is ignored as if absent. No cursor → today's behaviour exactly. Never a 400 (D15).

**Decision** (`decideForwardResume`, pure, `src/bun/event-resume.ts`), inputs `{ afterId, highWater, gapRowsAsc: {id, len}[], maxEvents: 800, maxBytes: 4 MB }` where `highWater` is `sqlite_sequence.seq` for `run_events` (0 when the row is absent) and `gapRowsAsc` is the task's rows with `id > afterId`, ascending, fetched with `LIMIT maxEvents + 1`, subagent rows included (D14):

| Condition (in order) | Answer |
| --- | --- |
| `afterId > highWater` | snapshot, reason `cursor-ahead` |
| `gapRowsAsc.length > maxEvents` | snapshot, reason `too-many` |
| `Σ len > maxBytes` | snapshot, reason `too-large` |
| otherwise | resume (possibly 0 rows) |

**Response frames, in order.**

1. `event: replay_meta` (no `id:` line), exactly one of:
   - no cursor: `{ earliestId, hasMore }` — unchanged;
   - resume: `{ earliestId: null, hasMore: false, resumedAfter: <cursor> }`;
   - snapshot: `{ earliestId, hasMore, snapshotRequired: true }`, where the window and both values are exactly what a no-cursor connect with the same `?anchor` would send (D3).
2. Rows ascending, each `id: <id>\ndata: <RunEvent JSON, including "id">\n\n`.
3. Live: a saved row is `id: <id>\ndata: …`; `interaction`, `interaction_resolved`, `subagent` and `{"type":"ping"}` are `data:` only. Never an empty `id:` (D20).

**`TaskEventsReplayMeta`** gains `resumedAfter?: number` and `snapshotRequired?: true`.

**Clients** keep two separate numbers per subscription: the transport's *last SSE id* (sent back as `Last-Event-ID` on reconnect, D6) and the consumer's *highest server id accepted* (drop any frame with `id <=` it, D16). On each `replay_meta`, `classifyReplayMeta` → `fresh` (today's handling), `resumed` (ignore `earliestId`/`hasMore`) or `snapshot` (reset, replace `earliestId`/`hasMore`, show the notice).

### 3.3 Alternatives considered and rejected

- **Query-only cursor** (blueprint wording) — rejected by D5; the owner wants standard SSE semantics so a fixed-URL reconnect resumes.
- **A separate `snapshot_required` named frame** or **close-and-reconnect** — rejected by D3/D7 (extra round trip; a second named frame old clients must learn).
- **Leaving `appendEvent` alone and adding `appendEventRow`** — smaller test churn, but two append methods with one id-less would let a future site send without an id; D11 chose the single method. The churn is 5 test files, mechanical, owned by T2.
- **Counting the gap as `latestId - afterId`** — wrong, ids interleave across tasks (D14).
- **Persisting `interaction`/`subagent` lifecycle** — rejected by D4; refetch/poll recovery instead.
- **503 during the e2e hold** — rejected for P8's server-side wait (deterministic timing, no error logs).

## 7. Blast radius & risks

- **Callers of changed signatures.** `appendEvent` (45 non-test call sites; return used by 6 source sites, all owned by T3/T4, and 5 test files owned by T2). `SseFrame` gains an optional field (both readers owned by T7/T9). `TaskEventsReplayMeta` gains optional fields (RunPanel, logs, TUI). `streamSse` gains an optional option (the `/events`, `/app/events`, clone-progress callers are untouched).
- **Behaviour visible to users.** `started — …`, `exit:N`, `cancelled (exit:N)`, the hold line and spawn-rejection lines now appear in history on reopen, in `agetor logs` replays and in message search (D4, accepted). `GET /runs/:id/events` (unused, D8) now carries `id` in its live JSON as a side effect of D11; no SSE `id:` lines there.
- **Ordering invariant (D19).** The cursor is only safe while a saved row's send is synchronous right after its insert. A future batched or deferred send would let a client skip rows. Mitigated by the single `saveAndEmit` helper, the comment on `emit()`, and TT3's monotonic-order test.
- **Mixed versions.** Old installed CLI → never sends a cursor, its parser ignores `id:` → unchanged. New client → older core: no `resumedAfter`/`snapshotRequired`, full window; the high-water filter (D16) and the deduper keep it duplicate-free. Webview and core ship together in the app.
- **Preflight cache.** The webview caches preflights for 600 s; a cached answer without `last-event-id` triggers a fresh preflight on the first reconnect that sends the header (Fetch rule: an uncached header name forces a new preflight). Covered by TT4's OPTIONS check and V1.
- **WKWebView.** `Last-Event-ID` is not a forbidden request header, but e2e runs Chromium; V1 checks the packaged path.
- **Main-thread cost.** Probe bounded at 801 `{id, len}` rows (≤ 16 ms warm on the largest real task); row fetch only on resume. The plan guard keeps both on indexes. A cold cache may be slower, comparable to today's replay.
- **Snapshot edge.** A single gap row over 4 MB (one huge `tool_result`) forces a snapshot whose window still includes that row (`minEvents` 20). Rare; accepted.
- **Settle-path saves.** A save on a cascade-deleted run would throw a foreign-key error inside `attachDoneHandler`; `saveStatusLineQuietly` swallows it so settlement, queues and global events still run. TT3 covers the saves on live runs; the run-gone branch mirrors `makeChunkHandler`'s existing guard (`orchestrator.ts:2637-2643`) rather than getting its own race test.
- **Test-only route.** Registered only under its flag (like the block route); the registry and hold map are absent otherwise. `route-policy.test.ts` pins it as desktop-only and conditional.
- **Rollback.** Additive on the wire; reverting the commits restores today's behaviour. No data migration; the newly saved status rows stay in existing databases harmlessly.
- **No feature flag** (A3): every addition is optional on the wire and covered by mixed-version handling above.

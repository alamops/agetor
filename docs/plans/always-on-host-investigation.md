## 1. What we know

### The headless core today

- **K1. Idle shutdown is decided once, at module load.** `IDLE_TIMEOUT_MS = Number(process.env.AGETOR_DAEMON_IDLE_MS ?? 300000)` (`src/bun/headless.ts:46-48`), checked every `IDLE_CHECK_MS` = 30 s (`:42`). The loop is only armed when the value is above 0 at boot (`:340-352`), so nothing can turn idle shutdown on or off at runtime. The core exits when `hasRunningWork()` is false (no `running` run, no running subagent row younger than 6 h, `:60`, `:84-97`) and `attachedClientCount()` is 0 (SSE clients, `src/bun/server.ts:305-313`) for the whole timeout. A non-numeric value parses to `NaN`, which also disables it.
- **K2. Two shutdown paths, and only one is complete.** `shutdown()` (`headless.ts:101-131`) reaps fx children, stops fx auto-resume, retention and lag timers, removes `agetor-core.json`, then exits. `POST /daemon/shutdown` on a headless core calls `removeCoreCreds` + `process.exit(0)` directly (`server.ts:8002-8020`), skipping `shutdown()`; fx children are still reaped by fx-acp's own `exit` hook and the other timers are `.unref()`'d. SIGINT/SIGTERM handlers are installed only after the port binds (`headless.ts:334-335`); launchd stops a job with SIGTERM.
- **K3. A second core exits when the port is taken.** If `startApiServer` throws and `agetor-core.json` names a live core, the daemon logs "port already owned by a live core — exiting quietly" and exits **0**; otherwise exits 1 (`headless.ts:255-275`). It does not wait for the port.
- **K4. Boot order matters and is shared with the app:** `rehydratePath` → lag monitor → `initDisclaimSwitch("headless")` (always disclaims, ignores a stored "off") → `ensureDisclaimedServer` (starts the tmux server) → pipeline runner → `reconcileOrphans` (reattaches live tmux sessions) → `reconcilePipelineRuns` → fx re-arm → discovery → bind (`headless.ts:134-310`). `db.ts` opens SQLite and runs migrations on import, so anything that imports `headless.ts` has already opened the database.
- **K5. The headless core has no runtime Electrobun dependency.** Only `index.ts`, `updater.ts`, `window-focus.ts` and `window-lifecycle.ts` import `electrobun`; `window.ts` is type-only. The compiled `agetor` CLI already carries the whole server stack and boots it with the hidden `__daemon` subcommand (`src/cli/index.ts:119-124`, `scripts/build-cli.ts`).
- **K6. Headless posts no OS notifications.** `index.ts` installs the notification hooks and the task notifier; `headless.ts` doesn't, and has no `native` (artifact item 4.2). With the app closed, nothing tells the user a task needs them.

### The app ⇄ daemon handoff today

- **K7. App launch takes over a CLI daemon.** On a failed bind, if `agetor-core.json` says `kind: "cli-daemon"` and `probeLiveCore` passes, the app POSTs `/daemon/shutdown` with the file's CLI token, waits up to 10 s for the port (`waitForPortFree`), then binds; anything else prints an `lsof` hint and `process.exit(1)` (`src/bun/index.ts:393-429`). There is no retry when the port is held but the file is missing or not yet written (a daemon that has bound but not yet called `writeCoreCreds`, `headless.ts:259` vs `:313`).
- **K8. App quit never starts anything.** `before-quit` (`index.ts:500-533`) removes `agetor-core.json` and allows the quit when no run is `running`; otherwise it broadcasts `quit_request` and vetoes, and the webview's confirm dialog re-quits through `POST /app/force-quit`. tmux sessions survive and the next launch reattaches them (CLAUDE.md "Confirm-on-quit").
- **K9. Electrobun's quit sequence:** `Utils.quit()` emits `before-quit`, then `stopEventLoop`, `waitForShutdownComplete(5000)`, `forceExit(0)`; `process.exit` is overridden to go through `quit()` (`node_modules/electrobun/dist/api/bun/core/Utils.ts:122-160`, Electrobun 1.18.1). Closing the window is not a quit (`runtime.exitOnLastWindowClosed: false`, `electrobun.config.ts`).
- **K10. Updates also go through `before-quit`.** On macOS `Updater.applyUpdate` deletes the running bundle (`rmSync`), renames the new one into place, starts a detached `sh -c 'while kill -0 <pid>; do sleep 0.5; done; sleep 1; open <bundle>'`, then calls `quit()` (`Updater.ts` ≈884-1090). A handback hooked on `before-quit` would also fire on every update, about 1.5 s before the new app launches and takes the port again.
- **K11. The CLI side.** `ensureCore` → `discoverCore` → else `spawnDaemon`: a detached, `unref`'d `Bun.spawn` of `bun headless.ts` (source checkout) or `<binary> __daemon`, waiting 15 s for it (`src/cli/daemon/supervisor.ts:22-89`). `agetor daemon start|stop|status` (`src/cli/commands/daemon.ts`); `stop` = `POST /daemon/shutdown`.
- **K12. `agetor-core.json`'s `kind` is validated strictly.** `readCoreCreds` accepts only `"app"` or `"cli-daemon"` and returns `null` otherwise (`src/bun/core-creds.ts:99`); unknown extra fields are ignored. The CLI ships separately (`scripts/install.sh`), so installed CLIs are often older than the app.
- **K13. `/daemon/shutdown` is `app+cli`** (`src/bun/route-policy.ts:440`), so anything holding the CLI token (an agent included) can stop the core today; `route-policy.test.ts:389-398` extracts that call from `supervisor.ts` and `index.ts`.

### Packaging

- **K14. Bundle layout** (installed `/Applications/Agetor.app`, v1.0.3): `Contents/MacOS/{launcher, bun, libNativeWrapper.dylib, libasar.dylib, bspatch, zig-zstd}`, `Contents/Resources/main.js` (Electrobun's launcher script: loads the native wrapper and runs `app/bun/index.js` in a `Worker`), `Contents/Resources/app/bun/index.js` (the only app bundle), `Contents/Resources/app/bin/{tmux, AgetorNotifier.app, disclaim, dylibs}`. There is no headless entry point in the app bundle, and the CLI binary is not bundled.
- **K15. Minimum macOS is effectively 14.** `otool` `LC_BUILD_VERSION minos`: `bun` 13.0, `libNativeWrapper.dylib` 14.0. `SMAppService` needs 13.0, so it is always available.
- **K16. Electrobun can place files where `SMAppService` needs them.** `build.copy` destinations are joined to `Contents/Resources/app` with `cpSync` (`node_modules/electrobun/src/cli/index.ts:3287-3308`), so `../../MacOS/<x>` and `../../Library/LaunchAgents/<x>.plist` land in `Contents/MacOS` and `Contents/Library/LaunchAgents`. A `postBuild` hook (config `scripts.postBuild`) runs before code signing and before the self-extracting tarball is made (`:3435` vs `:3714`, `:3990-4060`). Electrobun signs every Mach-O under `Contents/MacOS` with Developer ID, `--options runtime`, `--identifier <filename>` and the app entitlements, and never touches `Contents/Resources/app/bin` (that is why `scripts/build-disclaim.ts` and `build-notifier.ts` sign their own helpers). Dev builds skip signing (`buildEnvironment !== "dev"`).
- **K17. Electrobun 1.18.1 has no login-item API** (no `SMAppService`, `LaunchAgents` or login-item code in `node_modules/electrobun`). The repo's native-helper precedent is a small Swift/C helper built by `scripts/build-*.ts`, signed there, checked by `scripts/verify-vendor-signing.ts`.
- **K18. Every channel shares one bundle identifier** (`config.app.identifier = sh.alamops.agetor`; only the app file name changes per channel). Dev runs use `AGETOR_DATA_DIR=$HOME/.agetor-dev` and port 4318 from `package.json` scripts (`src/bun/dev-defaults.ts`); a launchd plist's `EnvironmentVariables` are static and don't expand `$HOME`.

### Platform facts (web)

- **W1.** Apple: put LaunchAgent plists in `Contents/Library/LaunchAgents`, replace `Program` with `BundleProgram` (bundle-relative); bundle LaunchAgents associate with the app in System Settings → Login Items automatically; `register()` registers "subject to user approval"; `status` ∈ `notRegistered`, `enabled`, `requiresApproval`, `notFound`; `openSystemSettingsLoginItems()` sends the user to the panel ([Updating helper executables](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos), [SMAppService](https://developer.apple.com/documentation/servicemanagement/smappservice)).
- **W2.** `launchd.plist(5)` on this Mac (macOS 26.6.2): `BundleProgram` is only for SMAppService plists; `ProgramArguments` are not bundle-relative (absolute, or resolved via `_PATH_STDPATH`); `KeepAlive` `true` or `{SuccessfulExit: bool}`; jobs aren't respawned more than once per `ThrottleInterval` (default 10 s); **an unspecified `ProcessType` gets "light resource limits … throttling its CPU usage and I/O bandwidth", `Standard` is the same as unspecified, `Interactive` has none**; by default launchd kills the job's process group when the job dies (`AbandonProcessGroup`).
- **W3.** Developer forums: a `BundleProgram` outside `Contents/MacOS` (e.g. `Contents/Helpers`) failed with a code-signing error (-67028) and worked from `Contents/MacOS`; DTS recommends `BundleProgram` like `Contents/MacOS/<binary>`; `unregister()` then `register()` back-to-back can fail with "Operation not permitted" unless delayed (~500 ms); a changed executable or plist may need re-registering; `register()` can succeed while launchd reports error 78; an agent installed with SMAppService should be managed with SMAppService, not `launchctl` ([779379](https://developer.apple.com/forums/thread/779379), [768592](https://developer.apple.com/forums/thread/768592), [745412](https://developer.apple.com/forums/thread/745412), [726826](https://developer.apple.com/forums/thread/726826)).
- **W4.** Prior art: Electron's `app.setLoginItemSettings({ type: "agentService", serviceName })` uses the same `Contents/Library/LaunchAgents` layout and warns that an app that isn't packaged, signed and notarized "may silently fail" ([Electron app API](https://www.electronjs.org/docs/latest/api/app)).
- **W5.** BTM (Background Task Management) records tie an agent to its parent app by a code requirement (bundle id + team), shown by `sfltool dumpbtm`; dispositions track enabled/allowed/notified ([theevilbit](https://theevilbit.github.io/posts/smappservice)).

## 3. What we're assuming

- **A1. A Developer-ID-signed Agetor can register `SMAppService.agent` from a helper in `Contents/MacOS`, and launchd starts it.** If wrong (W3's error 78, or a dev/ad-hoc build that silently fails, W4), the fallback is the app's own `bun` process calling `SMAppService` over `bun:ffi`/Objective-C, or `SMAppService.mainApp` (start the GUI app at login).
- **A2. `KeepAlive` behaves for SMAppService agents as for classic agents** (W2 semantics, 10 s throttle). The "park and wait" design in §4 Q3 depends on it; if wrong, the app has to start the daemon itself on quit.
- **A3. Agent sessions survive the daemon's job ending.** Proven for `launchctl remove` (S3) because the tmux server calls `setsid`. Not proven for `SMAppService.unregister()` or a job that launchd stops at logout. If launchd kills by coalition rather than process group there, turning the mode off (or every app takeover, if it ends the job) would kill every running agent; mitigations would be `AbandonProcessGroup: true` and a separately launched tmux server.
- **A4. Children inherit the job's resource class.** The tmux server and every agent are descendants of whichever core started the tmux server first, and the server outlives that core (S3). If the daemon runs with launchd's default `ProcessType` (W2: throttled CPU and I/O), every agent session on that tmux server may run throttled, even after the app takes over, until the tmux server restarts. The plan should set `ProcessType: Interactive` and verify it.
- **A5. An app update keeps the registration valid.** The updater replaces the bundle at the same path with the same identifier and team (K10, W5). Forums say a changed executable may need re-registering (W3). If wrong, the app must re-register after an update (unregister, delay, register).
- **A6. Running from the DMG or a translocated path breaks the registration once the app moves.** Unverified; it argues for refusing to register outside `/Applications` or `~/Applications`.
- **A7. The launchd daemon gets the same environment the Finder-launched app gets today** (minimal `PATH`, `HOME` set), and `rehydratePath()` covers `PATH` as it does for the app.

## 4. What we must ask the owner

1. **What turns the always-on mode on before remote access exists?** The artifact ties all three items to "remote access is on", but no remote-access setting exists and turning one on is native-only (K19). Options: (a) a separate user setting, e.g. "Keep Agetor running in the background" (registers the login item, disables idle exit, enables handback), which remote access will later imply; (b) build the mechanism dormant behind a future remote-access flag; (c) build a native-only remote-access on/off switch now. Recommendation: (a). It is useful today for the CLI and long runs, and needs no Companion decisions.
2. **Who may turn it on and off?** Any same-user process can run Agetor's signed helper and register the login item anyway (it gets a macOS "background item added" notification), and preferences are agent-writable (K20). Recommendation: turn on from the app only (Settings → General, no CLI-token route); turn off and read status from anywhere (`agetor daemon …` and Settings), matching the "removing authority may be HTTP/CLI" rule.
3. **Handback design.** (i) `KeepAlive: true` plus a parked daemon: launchd restarts the daemon ≤10 s after the app takes over; it waits without opening the database or tmux while another live core owns the port, and boots when that process exits. launchd then provides the handback on quit and crash restart for free. (ii) `KeepAlive: {SuccessfulExit: false}` plus the app starting the job on quit (`launchctl kickstart`, discouraged for SMAppService jobs by W3) or spawning it. (iii) The app spawns a plain detached daemon on quit, with no launchd supervision until the next login. Recommendation: (i), pending the launchd spike (Q10). Its cost is one idle `bun` process while the app runs.
4. **`agetor daemon stop` while the login item is on.** Under (i) the daemon comes back within about 10 s. Options: document it; make `stop` say "turn off Keep running in background to stop it"; or a distinct exit code so launchd leaves a stopped daemon alone.
5. **The quit confirm.** With always-on, quitting the app no longer leaves runs unsupervised. Keep the "N tasks running" confirm, change its copy ("they keep running in the background"), or skip it when handback is armed?
6. **Skip the handback on updater-driven quits?** (K10: the new app relaunches about 1.5 s later and would take the port straight back.)
7. **Which builds get a login item?** All channels share one bundle id (K18), so stable and canary can't each register their own. Dev builds are unsigned (W4) and a static plist would point a dev daemon at prod `~/.agetor` (K18). Recommendation: stable only, possibly canary later; disable the toggle in dev builds.
8. **OS notifications while the app is closed** (artifact item 4.2, K6). Fold them into this change, or leave them for the notification-router work? An always-on core that never notifies is half useful.
9. **Keep-awake (item 5.4).** Confirm it stays out of scope.
10. **May we run a real `SMAppService` spike on your Mac** (or a VM)? It registers a test background item from a scratch app (you see the macOS notification), then checks `KeepAlive` respawn and parking, `ProcessType` inheritance, tmux survival across `unregister()`, behavior after an updater-style bundle swap, and `status` after you disable it in System Settings, then unregisters. That settles A1–A5 before the plan commits. The alternative is to plan for them and verify in manual QA on a signed build.
11. **Approval UX.** When `status` is `requiresApproval` (you switched it off in System Settings), show a notice with a button that opens Login Items? And when it is `enabled` but the daemon isn't reachable, what does Settings say?
12. **App location.** Refuse to register when Agetor runs from a DMG (`/Volumes/…`) or an App Translocation path (A6)?

## 7. Risks and blast radius

- **Throttled agents (A4).** If the daemon starts the tmux server under launchd's default resource class, every agent session on that server can run with throttled CPU and I/O, and the server outlives the daemon. Set `ProcessType: Interactive`; verify.
- **Respawn loops.** With `KeepAlive`, any path that makes the daemon exit while another core owns the port (K3) turns into a restart every 10 s. Parking must happen before the daemon touches the database, tmux or the port, and must handle SIGTERM.
- **Version skew after an update.** A parked daemon keeps running the old `bun` binary after the updater deletes and replaces the bundle (K10); its JS files are gone or new. It should exit when its bundle changes (launchd restarts it from the new bundle) rather than boot old code later.
- **Two cores at login.** Daemon (RunAtLoad) and app (old-style login item, or a quick manual open) can race: the app fails with "port held" if the daemon has bound but not yet written `agetor-core.json` (K7). The app's takeover needs a short retry.
- **Installed CLIs.** A new `kind` value makes every older CLI see "no core" and try to spawn its own daemon (K12).
- **Agents can stop the core** through `/daemon/shutdown` (K13, pre-existing). Under handback design (i) launchd restarts it, which is an availability gain. Agents can also register the login item by running the signed helper (Q2); macOS notifies the user.
- **TCC.** The launchd daemon is a separate responsible process (Agetor's `bun` from the bundle). The headless core always disclaims its children and task-directory I/O (K4), so a protected project folder still prompts for the disclaimed child, not for Agetor. Not re-verified for a launchd-run core.
- **Logout and shutdown.** launchd sends SIGTERM (`ExitTimeOut` default 20 s); the daemon's `shutdown()` must run. The parked phase needs its own handler.
- **Crash loop log growth.** A daemon that fails at boot every 10 s appends to `daemon.log`, which is truncated past 5 MB once per process (`src/bun/daemon-log.ts`).
- **Channel collisions and dev builds** (Q7, K18).
- **Rollback.** Turning the mode off must unregister and leave tmux sessions alive (A3). A later build that drops the feature has to unregister on launch, or the old agent keeps starting a `BundleProgram` that no longer exists.

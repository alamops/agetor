## 1. Objective & success criteria

A **pipeline** is a named graph of **steps**, each bound to an agent profile (Settings → Agents), connected by edges. Running a pipeline creates one **pipeline task** on the board; agetor runs the steps one at a time as hidden **step tasks** that share the pipeline task's worktree, and each step ends its turn with a JSON **handoff** (`<handoff>…</handoff>`) that tells agetor which step comes next and carries the context forward.

Done means:

1. A full-page, n8n-style canvas editor (React Flow) creates/edits pipelines: draggable step nodes, drag-to-connect edges, a per-step side panel (name, instructions, agent profile with inline "New agent…", allowed subagent profiles + cap), Auto-arrange, Fit view, keyboard delete, smooth board↔page transitions.
2. New Task offers a **Pipeline** picker (mutually exclusive with the Agent picker). The created board card shows a Pipeline badge with step progress; clicking it opens the full-page **run view** instead of the run panel.
3. The run view animates the run: the active step pulses, traversed edges animate, a token travels the edge on each handoff; clicking a step node opens that step task's normal details (RunPanel) on top; "Back to board" returns.
4. Server-side runner: step 1 starts on Run; on a step's successful settle the handoff is parsed; the next step's task is created + started with the handoff (and the original goal) in its prompt; the last step moves the pipeline task to Review; a failing/dying/asking step moves it to Blocked with the reason; Retry, Stop, and manual advance (pick the next step) are available; branching (agent picks `next`) and cycles (25-step cap, per pipeline) work.
5. Per-step subagent guidance is injected into the step prompt (allowed profiles' settings + cap) — prose only, agetor does not enforce it.
6. Settings → Pipelines section lists pipelines and links into the editor. CLI parity: `agetor pipeline ls|show|rm|export|import`, `agetor add --pipeline <id|name>`, `agetor ls --steps`.
7. Profiles are frozen into the pipeline task at run start; deleting a profile or pipeline never breaks a running pipeline; the editor flags a step whose profile is gone and the runner refuses to start such a pipeline.
8. Deleting/archiving a pipeline task cascades to its step tasks; step tasks cannot be deleted/archived individually.
9. Unit + endpoint + runner + CLI tests, two Playwright specs (editor, run), CLAUDE.md item 19, README section.

| D4 | **Graph rules**: multiple outgoing edges allowed; a step's `transition` is `choose` (the agent's `next` — step name, case-insensitive, or edge label — picks ONE; with a single edge `next` is ignored) or `all` (**fan-out**: every outgoing step starts in parallel with the same handoff); 0 edges = terminal for that path; a step's `join` is `any` (default: every arrival starts a new execution — how cycles work) or `all` (**join**: starts once every distinct incoming source has arrived in this generation, receiving all their handoffs); cycles allowed; `maxSteps` per pipeline (default 25, 1..200) caps executions per run → Blocked `step-cap` — **(as landed, review pass)** the cap is no longer a hard wall: Retry on a `step-cap` block increments `run.capExtensions` and doubles the effective cap (`effectiveStepCap = maxSteps * (1 + capExtensions)`) each time, so a run can keep going for as long as the user keeps retrying past it, instead of the cap being the run's permanent end. Names unique per pipeline (case-insensitive) since `next` is by name. Start step = `startStepId` (editor marks it; defaults to the first step with no incoming edge). **Parallel steps share the parent's single worktree** (tmux sessions are per task id, so nothing collides at the process level, but concurrent agents can edit the same files) — the editor shows a warning on fan-out steps and the step prompt names its parallel siblings. The run finishes when no execution is active and no join is partially filled; a partially filled join whose remaining sources can no longer arrive (all paths ended) → Blocked `join-incomplete`, resolvable by manual advance (start the join step with what arrived). | Owner pick ("sweep in parallel fan-out/join steps too"). Rejected: per-branch worktrees + merge at join (a merge/conflict feature of its own). |

| D8 | **Freeze at run start**: on the first Run the runner snapshots the pipeline graph + every referenced profile (`AgentProfileSnapshot`) into `tasks.pipeline_run.snapshot`; later edits/deletes of the pipeline or profiles never affect a started run. Step tasks are inserted with `agentProfileId` + the frozen snapshot; `effectiveAgentProfile` returns `"snapshot"` for step tasks (one added guard) so the live-until-first-run refresh can't re-read an edited profile mid-pipeline. The editor shows a "profile deleted" warning; the runner refuses to start with `profile-missing`. | Owner pick; mirrors the agent-profile decision. `agentProfiles.delete`/`pipelines.delete` stay never-blocked; both carry `taskCount`. |
| D9 | **Lifecycle** (owner-confirmed a–f): Run on the parent starts step 1 (or retries the current step when Blocked/cancelled); each step is one agent turn (follow-ups in the step's panel extend it; handoff re-parsed on each settle); all paths finished → parent `review` (each step task → `done` when its handoff is consumed); any execution `failed`/`blocked` → parent `blocked` (reason kinds `step-failed`, `step-blocked`, `handoff-missing`, `handoff-invalid`, `step-cap`, `profile-missing`, `join-incomplete`) while sibling executions keep running; Stop on the parent cancels every active execution and returns the parent to `ready` (state `cancelled`, active set kept so Run retries them); delete/archive cascade; step tasks can't be deleted/archived individually (409). A step task the user manually re-runs from its own panel is a retry (parent mirrors the child's column events). **(as landed, review pass)**: a `blocked`/`cancelled` run is *always* retried in place (`performPipelineRetry`), including when the only thing left to retry is a run-level pending block with nothing in `active` — this was a review-found dead end in the original implementation. A **`done`** run is a fourth, harder case the original design didn't separate out: plain Run/`POST /tasks/:id/start` on a finished pipeline now refuses (`"pipeline already finished — restart it explicitly"`) rather than silently discarding history, and only the new explicit `POST /tasks/:id/pipeline/restart` (`{restart: true}`) runs it again from scratch. A step-level Stop (the ordinary Stop button on one step task's own panel) also turned out to need its own rule beyond "Stop on the parent": it only escalates to cancelling the *whole* run when no other execution is still genuinely live (`isTaskRunLive`) — a Stop on one fan-out branch must not cancel a still-running sibling. | Consistent with today's semantics; the done/restart split and the step-level-Stop nuance were both review findings (first-pass majors), not part of the original 7-point lifecycle list. |
| D10 | **Prompt composition** (`composeStepPrompt`, pure): pipeline header (name, step k of the run, cap), the original goal (the task prompt), the previous handoff inlined (capped at 16 KB, the rest in a file), the step's own instructions, delegation guidance (allowed profiles' name/harness/model/instructions/skills + cap or "no limit"), the list of possible next steps, and the handoff contract. Then the normal `composeLaunchPrompt(profileSnapshot, …)` wraps it. Every handoff is also written to `dataDir/pipeline-runs/<parentId>/handoff-<seq>.json` and attached as a `TaskReference` on the next step (issue-threads pattern); for gemini steps the inline copy is dropped when the composed prompt would exceed the 4 KB argv cap. **(as landed, review pass)**: the "capped at 16 KB" line was true in name only through wave 2/3 — `PIPELINE_LIMITS.handoffInlineMaxBytes` existed but nothing read it, so every previous handoff was always inlined in full regardless of size. The review pass wired it up for real: `composeStepPrompt` now tracks a running byte total across all inlined handoffs and, once the *next* one would push that total over 16 KB, drops it whole to a "(handoff too large to inline — saved to `<path>`)" file reference instead — never a mid-JSON truncation. The gemini 4 KB-argv fallback is unchanged in spirit but is genuinely all-or-nothing: it re-composes the *entire* prompt once with `inlineHandoff:false`, dropping every previous handoff to a file reference in one shot rather than trimming just enough. Every inlined (or file-pointer) handoff is also now preceded by an `HANDOFF_UNTRUSTED_CONTENT_WARNING` (mirrors the issue-thread untrusted-content guard) — not in the original design, added because a handoff is agent-produced text that may itself quote untrusted issue/web/file content. | Keeps the "main purpose + reason" context flowing; the file makes it durable and bounded. The untrusted-content warning and the real 16 KB enforcement were both review findings. |
| D11 | **Board/CLI hiding**: `GET /tasks` returns step rows too (so `selected` sync + the run view work from one list); the board filters `pipelineParentId == null`; the parent's `pendingInteractionCount` aggregates its steps' counts (so the card's "waiting on you" glow is honest); CLI `ls`/TUI hide steps unless `--steps`. | One list keeps `reconcileById` identity semantics; filtering is a one-liner per consumer. |
| D12 | **Live updates**: new `GlobalEvent` kind `"pipeline"` (`{taskId, status, currentStepId, stepCount, ts}`) emitted on every state change; the run view subscribes via `api.subscribeGlobalEvents` and refetches the parent + steps on it; the 2 s `/tasks` poll is the fallback. `column` reason enum gains `"pipeline"`. | Animation needs sub-poll latency. |
| D13 | **Editor connect fallback**: besides drag-to-connect, the step panel has a "Connect to…" select (adds an edge). | Keyboard/a11y and a deterministic e2e path (Playwright handle-drags are flaky). |
| D14 | **Pipeline authoring in CLI = JSON files** (`export`/`import`, `add` from a file); `agetor add --pipeline` creates the parent task. | Canvas is the authoring surface; the CLI moves pipelines around. |

### Contracts

`src/shared/types.ts` (additive):

```ts
export interface PipelineStep {
  id: string;                 // uuid, stable across edits
  name: string;               // unique per pipeline, case-insensitive; `next` targets it
  instructions: string;       // step-specific prompt text
  agentProfileId: string | null;
  position: { x: number; y: number };
  subagents: { profileIds: string[]; cap: number | null };  // cap null = no limit
  transition: "choose" | "all";   // after this step: the agent's `next` picks ONE outgoing edge, or ALL outgoing steps start in parallel (fan-out)
  join: "any" | "all";            // start when ANY incoming step finishes (default; each arrival = a new execution), or only once ALL incoming steps have finished this generation (join)
}
export interface PipelineEdge { id: string; from: string; to: string; label: string }
export interface PipelineGraph { steps: PipelineStep[]; edges: PipelineEdge[]; startStepId: string | null }
export interface Pipeline {
  id: string; name: string; description: string; graph: PipelineGraph; maxSteps: number;
  createdAt: number; updatedAt: number; taskCount?: number;   // taskCount server-derived (parents bound by pipeline_id)
}
export interface PipelineInput { name: string; description?: string; graph: PipelineGraph; maxSteps?: number }
export interface Handoff {
  schemaVersion: 1; purpose: string; summary: string; reason: string;
  next: string | null; artifacts: string[]; openQuestions: string[]; status?: "done" | "blocked";
}
export type PipelineRunStatus = "idle" | "running" | "blocked" | "done" | "cancelled";
export type PipelineBlockKind = "step-failed" | "step-blocked" | "handoff-missing" | "handoff-invalid" | "step-cap" | "profile-missing" | "join-incomplete";
export interface PipelineStepRecord {
  seq: number; stepId: string; taskId: string; startedAt: number; endedAt: number | null;
  outcome: "succeeded" | "failed" | "cancelled" | "advanced-manually" | null;
  handoff: Handoff | null; nextStepIds: string[];   // (as landed) was `nextStepId: string | null` — widened to an array so a `transition:"all"` fan-out's history entry can record every step it actually launched, not just one
}
export interface PipelineRunState {
  pipelineId: string; pipelineName: string;
  snapshot: { graph: PipelineGraph; maxSteps: number; profiles: Record<string, AgentProfileSnapshot>; capturedAt: number } | null; // null until first Run
  status: PipelineRunStatus;
  active: { stepId: string; taskId: string; seq: number }[];                 // every step execution currently running/blocked (parallel fan-out ⇒ several)
  joins: Record<string, { arrivals: { fromStepId: string; seq: number; handoff: Handoff | null }[] }>; // partial fan-in state per join="all" step
  blocked: {
    taskId: string | null; stepId: string | null; kind: PipelineBlockKind; message: string;
    // (as landed) `pending` is new — populated only on a run-level block (taskId/stepId both
    // null: step-cap/profile-missing/join-incomplete) so Retry can re-attempt the exact launch
    // instead of re-deriving it, instead of that block being a dead end with nothing to retry.
    pending?: { stepId: string; arrivals: { fromStepId: string; seq: number; handoff: Handoff | null }[] };
  }[]; // one entry per blocked execution (or a run-level entry with null ids)
  history: PipelineStepRecord[]; stepCount: number; startedAt: number | null; endedAt: number | null;
  // (as landed) new — times a step-cap block has been extended via Retry; each extension
  // doubles the running allowance (effectiveStepCap = maxSteps * (1 + capExtensions)).
  capExtensions?: number;
}
// Task (additive): pipelineId?: string | null; pipelineRun?: PipelineRunState | null; pipelineParentId?: string | null; pipelineStepId?: string | null;
// GlobalEvent (additive): { kind: "pipeline"; taskId: string; status: PipelineRunStatus; activeStepIds: string[]; stepCount: number; ts: number }
// column-event reason gains "pipeline".
export const PIPELINE_LIMITS = { name: 80, description: 2000, steps: 50, edges: 200, stepName: 60, instructions: 20_000, maxStepsDefault: 25, maxStepsMax: 200, handoffInlineMaxBytes: 16_384 } as const;
// (as landed) PIPELINE_LIMITS grew six more fields the original design didn't call out:
// handoffField: 8_000 (per handoff string field), handoffArray: 50 (per handoff array field),
// edgeLabel: 120, id: 128 (step/edge id length), subagentProfiles: 20, subagentCap: 1000,
// and positionAbs: 1_000_000 (canvas coordinates clamp into ±this range rather than reject).
```

## 8. Open questions / assumptions

- A1: The parent task's `agent`/`model` fields are cosmetic (set to the start step's harness) — the parent never spawns.
- A2: Step tasks inherit the parent's `taskType`; the parent's branch naming uses the normal `agetor/<id>-<slug>` scheme (worktree row in New Task stays available for pipeline tasks).
- A3: Follow-up chat to a *finished* pipeline's last step is allowed (normal task); it does not re-open the pipeline.
- A4: `agetor ls` default hides steps; `agetor show <step>` works by id.
- A5: Handoff `next` matching is by step name or edge label, case-insensitive, trimmed; when only one outgoing edge exists `next` is ignored.
- A6: Cycles: the same step may run many times; each execution is a new step task (history keeps them all); cap default 25.

### Follow-up: one-shot handoff reminder (65f8a75)

A post-landing follow-up (owner request), not part of the original plan or any review round above: a step whose final response lacked a valid `<handoff>` block used to block the pipeline immediately (`handoff-missing`/`handoff-invalid`). As of `65f8a75` it instead gets ONE automatic correction attempt first.

**Design.** `classifyStepResponse` (`src/shared/pipeline.ts`) is a new pure function and the single decision point `handleRunStatus` (`src/bun/pipeline-runner.ts`) now calls on every settle, replacing the old direct `parseHandoff` call. It returns a `StepResponseKind` (`src/shared/types.ts`) — `handoff` | `handoff-blocked` | `handoff-missing` | `handoff-invalid` | `user-ask` | `error` | `cancelled` — checked in that precedence, and is stamped onto `PipelineStepRecord.responseKind` regardless of outcome, not just on the reminder path. Only `handoff-missing`/`handoff-invalid` trigger the reminder: `handleRunStatus` composes it via the new `composeHandoffReminder`, which shares its handoff-schema rendering (`renderHandoffContract`, factored out of the block `composeStepPrompt` already built) with the original step prompt so the two can never state the schema differently, sends it as a plain follow-up turn through `sendInput` (folds into a live claude session, or spawns a fresh turn for the one-shot harnesses), and records the attempt on the SAME `PipelineStepRecord` via the new `reminder: PipelineStepReminder` field (`{at, reason, runId, detail}`). The execution stays in `run.active` — no block, no advance — so the reminder turn's own settle re-enters `handleRunStatus` and re-classifies. A record's `reminder` is written once and never cleared by a Retry (a Retry re-runs the same history entry in place), so a second bad response after a Retry still reads as "already reminded" and blocks immediately, with `"still no valid handoff after one reminder — "` prefixed onto the usual message. A reminder that can't even be sent (`sendInput` returns `delivered:false`) falls straight through to the pre-existing `upsertBlocked` path instead of silently dropping the response.

**Collateral fixes bundled into the same commit:**
- **Run-scoped `user-ask` signal.** `classifyStepResponse` needed a "is the agent waiting on the user" signal, and the obvious `listPendingForTask(taskId)` would have counted stale interactions left over from an earlier execution of the same step (a prior retry, or a test fixture that registered one against a synthetic run id and never cleared it) — which would misclassify every later valid handoff on that step as `user-ask` forever. The new `pendingInteractionsForRun(taskId, runId)` filters `listPendingForTask`'s result down to entries whose own `runId` matches the run that just settled, so only an interaction the run that just finished actually raised can suppress its classification.
- **`db.ts` sanitizer whitelist.** `sanitizeStepRecord` gained `sanitizeResponseKind`/`sanitizeStepReminder` to round-trip the two new `PipelineStepRecord` fields through the persisted `pipeline_run` JSON column. Without this, a run reloaded from storage (any subsequent read after the settle that wrote it) would silently drop `reminder`, and the one-shot gate (`!historyEntry?.reminder`) would read `false` again on the next poll — sending a fresh reminder every time instead of exactly once. Both sanitizers fail closed to `null` on anything malformed rather than dropping the whole history entry, since worst case is one extra reminder attempt, never a control-flow bug.
- **Fake-driver two-turn suffixes.** `FAKE_CLAUDE_HANDOFF_PROMPT_MARKER` gained `missing-then-<token>`/`invalid-then-<token>` suffixes (`missing-then-done`/`invalid-then-done` are the common case) so a test can drive exactly this scenario: `missing`/`invalid` behavior on the step's first fake-driver turn, then `<token>`'s behavior (typically `done`, or a named outgoing step) on every turn after. This needed two supporting pieces: a per-task turn counter (`fakeHandoffTurnCounts`, capped at `FAKE_HANDOFF_TURN_MAP_CAP` = 1000 entries with FIFO eviction so a long-running test process can't leak memory across many short-lived fake tasks), and marker inheritance (`resolveFakeHandoffPromptSource`) — the runner's automatic reminder turn is an ordinary follow-up line with no `FAKE_CLAUDE_HANDOFF_PROMPT_MARKER` of its own, so when the CURRENT turn's prompt carries no marker, the fake driver now falls back to the task's own stored (turn-1) `prompt` via a direct `tasks.get` import from `db.ts` (safe — `db.ts` has no import of `agents.ts` in its chain, so this doesn't introduce a cycle) to keep resolving the same scenario across the reminder round-trip.
- **UI/CLI surfaces.** The run view's history rows (`PipelineRunView.tsx`) render a `pipeline-run-response-kind` chip (via the new `responseKindLabel` in `src/mainview/lib/pipelines.ts`, tone-mapped success/warning/danger/muted) and, when a reminder fired, a `pipeline-run-reminder` chip with its timestamp; a still-active step node (`StepNode.tsx`) shows a small spinning-arrow glyph (`pipeline-step-reminded`, driven by the new `stepReminded` helper) while its in-progress execution has been reminded and hasn't settled since. `agetor pipeline status <ref>` (`src/cli/commands/pipeline.ts`) appends a dim `[<responseKind>]` tag and, when reminded, a yellow `(reminded)` tag to each history line.

### Follow-up: handoff-reminder review fixes (`eecabea`, `9434699`)

A review pass against the `65f8a75` follow-up above, closing gaps in the reminder's classification order, delivery accounting, and display. `eecabea` (e2e coverage for the base feature) landed first; `9434699` is the fix commit.

**`classifyStepResponse` reorders to parse-first.** The base commit checked `pendingInteractions > 0` before ever calling `parseHandoff`, so a stale or already-answered interaction card could discard a perfectly good handoff the agent produced later in the same turn. `9434699` reorders it: `parseHandoff` runs first, a valid handoff — `handoff-blocked` included — always wins regardless of pending interactions, and `user-ask` is now reachable only when parsing genuinely fails AND `pendingInteractionsForRun` reports something pending. A `user-ask` classification also changed behavior, not just ordering: it used to record no block at all (relying on the ordinary interactions/column machinery to surface it); it now additionally records a retryable `PipelineBlock{kind:"step-blocked", message:"step \"<name>\" is waiting for you"}` so `deriveRunStatus` reads `blocked` instead of a silently-stuck `running` while the card is unanswered. `handleColumnChange`'s existing running-column block-clear (which already strips any block naming a task the moment that task's step genuinely runs again) covers clearing it once the user answers; that same handler was extended to also null out `historyEntry.responseKind` on that transition, so a stale kind from the *previous* attempt can't be misread as the new attempt's outcome.

**`handoff-next-unknown` — a third reminder-eligible reason.** A handoff that parses fine but whose `next` doesn't resolve to a real outgoing step (`resolveNextSteps`'s `"ambiguous"`/`"unknown"` outcomes) used to block immediately with no reminder. It now retroactively overwrites `historyEntry.responseKind` from `"handoff"` to `"handoff-invalid"` (`classifyStepResponse` can't itself see the graph, so it can't know this at classification time) and routes through the same one-shot reminder path as `handoff-missing`/`handoff-invalid`, via the new shared `attemptHandoffReminderOrBlock` helper both branches now call. `composeHandoffReminder`'s `reason` union grew this third value; its message names the candidate outgoing steps. When a second reminder-eligible response still doesn't resolve, `handoff-next-unknown` maps onto the `handoff-invalid` block kind (`reminderBlockKind`) — a bad `next` is a malformed handoff, not a distinct block kind of its own.

**Reminders are recorded only when actually delivered.** `PipelineStepReminder` gained `delivered: boolean`. The base commit stamped `historyEntry.reminder` unconditionally (with `runId: null` standing in for "not delivered"); `9434699` instead writes the reminder record ONLY on `sendInput`'s `delivered:true` path — a failed/withheld send records nothing on the history entry at all, so the *next* settle can still attempt the one reminder, rather than the execution being permanently treated as "already reminded" off a send that never actually reached the agent. `delivered` is never persisted `false` today (a record only gets created once delivery succeeds) but the field exists so a future partial-delivery path could record an honest `false` without a schema change; `db.ts`'s `sanitizeStepReminder` defaults a missing `delivered` to `true` (every reminder persisted before this field existed was in fact delivered) and treats a present-but-wrong-typed value as malformed (collapses the whole reminder to `null`).

**New collateral fixes in `attemptHandoffReminderOrBlock` (round 4 review, `Major 1`/`Major 2`/`Medium 3`/`Medium 4`/`Low`):**
- **Major 1 — stale top-of-turn state.** Re-reads the parent task and the step task fresh from `tasks.get` rather than trusting `handleRunStatus`'s top-of-turn copies, since `archiveTask`/a delete cascade can race in through the same per-parent lock and set `archivedAt`/tombstone the parent between when `handleRunStatus` started and when the reminder would fire. A gone/tombstoned/archived parent, or an archived step task, skips `sendInput` entirely and records an ordinary block instead (message suffixed `(automatic reminder skipped — <reason>)`).
- **Major 2 — don't revive a run mid-Stop.** `isDeliberateWholeRunStop(run, taskId)` — a new shared helper, factored out of the cancelled/orphaned settle branch's own equivalent inline check — also gates the reminder send: a step that finished with a bad handoff while the whole pipeline is being torn down (`cancelPipelineRun`, or every other live sibling already `isTaskRunCancelling`) must not have its reminder revive the run back into `running`.

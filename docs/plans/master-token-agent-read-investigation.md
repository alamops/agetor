# Investigation — agents can read the core's master API token

| Field | Value |
| --- | --- |
| Date | 2026-10-27 |
| Change | Validate the claim "your own agents can read the master token, so pairing a phone must happen only in a native desktop dialog with a code typed from the phone, and no HTTP route may pair a device or raise its permissions", and scope the fix: what the agent-readable creds file should carry, which routes count as "raise permissions" today, and how to make the rule enforceable before the Companion app exists. |
| Agents | none — this pipeline step forbade subagents; codebase, git history and web research ran inline; 3 spikes (2 live-safe reads, 1 throwaway headless core) |

## 0. Verdict

**Valid.** Every factual clause holds on `main` at v1.0.3 (5b1d38c), and it was proven on the live machine from inside this very agent session. Two refinements:

1. **"Agents run unsandboxed"** is true for every harness's *default* mode, which is what Agetor ships (claude `--dangerously-skip-permissions`, codex escalated to `danger-full-access` in worktrees, cursor `--force --sandbox disabled`, gemini `--yolo`, fx Full access, antigravity `--dangerously-skip-permissions`). Restricted modes put the harness's own gate in the way, but Agetor does not control or rely on it.
2. **The pairing rule guards a feature that doesn't exist yet.** There are no pairing, device or remote-access routes among the 192 registered routes, so nothing violates the rule literally today. The principle behind it — *anything reachable over HTTP is reachable by a prompt-injected agent* — is violated today, though: several routes lend Agetor's own macOS identity (TCC grants, Automation permission) to whoever holds the token, and one route lets the token holder switch off the TCC separation for future agents.

So "the fix" cannot be "build native pairing" (that is Companion v1). It is: stop putting full authority in the agent-readable file, decide which routes are desktop-only, and make "no HTTP route may pair a device or raise its permissions" an invariant a test enforces. The research brief this statement came from says the same in its "Ship regardless of the app" note (§12): *stop writing the master token where agents can read it, or give the CLI its own scoped credential; move SSE and terminal WebSocket authentication out of `?token=` URLs.*

## 1. What we know

**The credential and where it lives**

- **K1 — the creds file.** `writeCoreCreds` writes `{port, token, pid, kind, version, startedAt}` atomically at mode 0600 to `$AGETOR_DATA_DIR/agetor-core.json` (`src/bun/core-creds.ts:25-72`). Writers: the app (`src/bun/index.ts:383-394`, `kind: "app"`) and the headless daemon (`src/bun/headless.ts:279-291`, `kind: "cli-daemon"`). Readers: the CLI's `discoverCore` (`src/cli/api-client.ts:130-134`), the app's daemon handoff (`src/bun/index.ts:351-360`), the daemon's port-busy probe (`src/bun/headless.ts:249-250`), `stopDaemon` (`src/cli/daemon/supervisor.ts:95-108`).
- **K2 — one token, one scope.** `API_TOKEN` is one per-launch 32-byte hex value, or `AGETOR_API_TOKEN` when set (`src/bun/api-config.ts:83`). `authed()` → `isAuthorized` → `tokenMatches` (`src/bun/server.ts:422-455`) accepts it as a `Bearer` header **or** `?token=` on any route. Every route is `authed()` except `/health` (`server.ts:1256`) and the test-only `/test/block-event-loop` (`server.ts:3737`, a 404 unless enabled). The terminal WebSocket upgrade checks the same token (`server.ts:7861`). There is no notion of scope.
- **K3 — the webview holds the same token.** It arrives through the preload `window.__AGETOR` (`index.ts:557-563`) and the URL hash (`index.ts:588`), read at `src/mainview/lib/api.ts:354`. The webview then puts it in `?token=` for four EventSources, the terminal WebSocket and two `<img>` routes (`api.ts:1672, 1881, 1891, 2095, 2121, 2140, 2167`).
- **K4 — the CLI holds the same token.** About 60 `req()` routes in `src/cli/api-client.ts` plus three SSE paths (`/events`, `/tasks/:id/events`, `/app/events`). `src/cli/sse.ts:36` puts the token in `?token=` even though it reads the stream with `fetch`, which can send an `Authorization` header.
- **K5 — this is a regression of a stated intent.** #54 (`a344b56`, 2026-06-03) stopped injecting `AGETOR_API_TOKEN` into claude's tmux env; `src/bun/claude-tmux.ts:8121-8125` says "AGETOR_API_TOKEN gates every orchestration route — no reason to expose it to the agent's environment." #65 (`da8c2cd`, 2026-07-01, the standalone CLI + headless daemon) added the creds file and re-exposed the same token through disk.

**What an agent can reach**

- **K6 — proven live (S1).** From this session — claude running under Agetor's tmux (parent chain `zsh → claude → tmux`, tmux parented to launchd) — `~/.agetor/agetor-core.json` is readable and parses to a 64-hex token with `kind: "app"`. The token was never printed.
- **K7 — the file is the only leak today (S1b).** The live token appears in no process argv or environment (`ps -axww`, `ps -E`), not in `daemon.log`, `~/.agetor/{settings.local.json,bin,harnesses}`, `~/Library/WebKit/sh.alamops.agetor` or `~/Library/Application Support/sh.alamops.agetor`.
- **K8 — env channel when an override is set.** tmux clients are spawned with `{...process.env}` (`src/bun/tmux-resolution.ts:153-155`, used by `ensureDisclaimedServer` at `:183-199`), so the tmux server and every agent session it hosts inherit the core's environment; terminal tabs (`src/bun/terminals.ts:267`) and fx children (`src/bun/fx-acp.ts:3368`) do the same. When `AGETOR_API_TOKEN` is set — `scripts/dev-headless.sh:223`, `e2e/fixtures.ts:325`, or a user's debug override — agents get the token in their environment too. Production default: not set.
- **K9 — a world-readable dev token.** `scripts/dev-headless.sh:205-215` writes the token to `$DATA_DIR/headless-dev/token` with a plain `echo >`; the live `~/.agetor-dev/headless-dev/token` is `-rw-r--r--`.
- **K10 — what the token adds beyond plain same-user access (confused deputy).** Agents are TCC-disclaimed: the tmux server starts through `disclaim` (`tmux-resolution.ts:166`) and fx is wrapped (`fx-acp.ts:3389`). The core itself is not disclaimed — it runs as Agetor.app. With the token, an agent can borrow the app's identity:
  - **Terminal tabs.** `POST /tasks/:id/terminals` plus the `/terminals/:id/ws` WebSocket spawn `$SHELL -l` with `Bun.spawn` and **no** `disclaimArgv` (`terminals.ts:265-269`). Commands typed there run under Agetor's TCC responsibility.
  - **Terminal.app via Automation.** `POST /harnesses` (absolute `bin`, `env`) followed by `POST /harnesses/:id/open-terminal` (`server.ts:4843`) runs `osascript` → `tell application "Terminal" to do script "<PATH=dir:$PATH> <basename>"` (`src/bun/agents.ts` `buildHarnessTerminalCommand` / `toTerminalAppleScript`). That executes a binary of the token holder's choosing in Terminal.app, using the Automation grant the user gave Agetor and running under Terminal's own TCC identity. Not executed here, because it opens a window on the user's screen; read from code.
  - **Switching the separation off.** `PUT /preferences/:key` stores any string for any key except the retention key (`server.ts` `/preferences/:key`). `disclaimSpawnedAgents = "false"` (`src/bun/disclaim.ts:23, 93`) makes the next tmux server and every fx spawn inherit Agetor's TCC identity. Proven in S2.
  - **Reads under the app's grants.** `GET /files/preview?path=` serves any absolute image path from the core process (`server.ts` `/files/preview`; gated by `isImagePath` only).
  - **Acting as the app.** `POST /notifications` (an OS notification in Agetor's name), `/open-external`, the native pickers (`/projects/pick`, `/refs/pick`, `/bundle/pick-file`), `/window/*`, `/updates/*`, `/app/force-quit`, and `/daemon/shutdown` (denial of service; proven in S2).
- **K11 — what the token adds that same-user access already had.** Create and start Auto-mode tasks in any directory (proven in S3), send input, answer ask cards and permission prompts, approve plans in any task, `PATCH` a task's mode, harness CRUD, DB tools. An unsandboxed agent can do the equivalent without the token: the tmux socket (`tmux -L agetor send-keys …`), `agetor.sqlite`, other tasks' worktrees. **No credential split can take these away from an unsandboxed agent** (see §3, A1).
- **K12 — no pairing code exists.** A grep for pairing, device and remote-access vocabulary over `src/`, `e2e/` and `native/` finds nothing relevant, and both companion spike branches (`spike/spike-agetor-companion-app`, `spike/spike-app-for-remote-control`) carry zero commits beyond `main`. The statement comes from the Agetor Companion research brief (claude.ai artifact `25cyTFUnoiRksPpD9CiiPy`): §01 "New threat", §03 readiness table ("Authentication — Missing … Agents can read it … stop exposing the master token to agents"), §06 security model, §12 "Ship regardless of the app".
- **K13 — direction of the typed code.** In the brief's pairing sequence (§06) the phone displays a 6-digit code and the user types it **into the Mac's native window**, after a QR-pinned Noise NKpsk0 handshake. "A code typed from the phone" means that direction: the agent can't see the phone and can't type into a native window.
- **K14 — no native text-input dialog in Electrobun 1.18.1.** `Utils` exports `showMessageBox` (buttons only), `openFileDialog`, `showNotification` and others (`node_modules/electrobun/dist/api/bun/core/Utils.ts:117, 162, 235`), but no text field. A typed-code dialog needs either a Swift helper (precedents: `native/notifier`, `native/disclaim`) or a dedicated window driven over Electrobun RPC, not HTTP.
- **K15 — why "native" and not a webview modal.** The webview renders agent-authored content: markdown, images (`MdImage`), links, tagged messages. Its in-memory master token is one rendering bug away from agent influence, and pairing must survive a compromised webview.
- **K16 — docs.** README's security model (`README.md:344-349`) promises protection from websites only and says agents run with your privileges, so it does not overclaim. README `:316`, `api-config.ts:18-23, 68` and the tracked `.claude/CLAUDE.md` (an `ask_user` MCP tool) still describe hooks and an MCP server that #54 removed (`claude-tmux.ts:8105-8110`). README `:287, :338` and CLAUDE.md's "Stack and architecture" paragraph describe the creds file and the single token.
- **K17 — headless has no webview.** The file token is the only way into a headless core: the CLI, container users (`README.md:316-338`, `AGETOR_API_HOST=0.0.0.0`), and the app's handoff. e2e and `dev-headless.sh` drive a Vite webview against headless by passing `AGETOR_API_TOKEN` and putting it in the URL hash (`e2e/fixtures.ts:325, 501`).
- **K18 — other agent-readable secrets (out of scope).** `~/.agetor/github-tokens.json` (0600, git-host PATs; `README.md:288`). An agent could also run `gh auth token`.

**Outside practice (web)**

- Coding agents that inherit the user's privileges make prompt injection a code-execution primitive. The useful question is whether a local credential grants *more* than the user's own access; if it does, it is a real boundary ([NHIMG](https://nhimg.org/faq/why-do-prompt-injection-flaws-become-more-dangerous-when-a-cli-can-access-local/), [GitLab agentic threats](https://docs.gitlab.com/user/duo_agent_platform/security_threats/), [GitHub on VS Code agent mode](https://github.blog/security/vulnerability-research/safeguarding-vs-code-against-prompt-injections)). K10 is exactly that "more".
- Confused deputies: agents weaken their own or a sibling agent's restrictions through a more-privileged component. The durable mitigation is that a restricted principal can't write the thing that grants permissions ([Origin HQ](https://www.originhq.com/research/escaping-the-sandbox-confused-deputies)). `PUT /preferences/disclaimSpawnedAgents` is the same pattern.
- Localhost services reachable from a browser need authentication ([CVE-2025-52882](https://securitylabs.datadoghq.com/articles/claude-mcp-cve-2025-52882/), Claude Code IDE WebSocket). Agetor already covers that; the same-user case is the gap.
- Short typed codes give limited assurance on their own; pair them with a key pinned out of band ([IETF SAS pairing drafts](https://datatracker.ietf.org/doc/draft-ietf-dnssd-pairing/04/)). The brief already does this (QR-pinned key, then the typed code).
- Keychain ACLs prompt for any app outside the trusted list ([Apple: access control lists](https://developer.apple.com/documentation/security/access-control-lists)). That doesn't help here: the agent can execute the very CLI binary the user would trust.

## 3. What we're assuming

- **A1 — the CLI must keep working without user presence** (scripts, the TUI, people deliberately running `agetor` from an agent). Then **no credential the CLI can obtain can be kept from an unsandboxed agent**: the agent can read what the CLI reads, or simply run the CLI. Keychain ACLs, peer-pid or ancestry checks, and a Unix socket with a code-signing check are all defeated the same way: exec the CLI, or reparent through `launchd`/`nohup`. The only levers left are **scope** (what the agent-readable credential can do) and **user presence** (native UI) for what it can't. If the owner accepts an interactive `agetor login` approval, the minted credential still sits on disk, so scoping is still needed.
- **A2 — agents stay unsandboxed by default** (README security model). If Agetor sandboxed agents later, hiding the file would gain real value, and the scoping done now would still apply.
- **A3 — restricted harness modes are not a barrier Agetor relies on.** In those modes, reading the file and calling 127.0.0.1 needs tools the harness gates (for example, codex `read-only`/`workspace-write` have no network by default). Nothing in this change depends on that.
- **A4 — Agetor.app holds TCC grants worth protecting**: at least Automation → Terminal for anyone who has used "Open terminal" or "Open tmux", possibly Documents/Desktop/Full Disk Access. This varies per user and `TCC.db` can't be read without Full Disk Access. If the app held no grants, K10's terminal and preview items would lose most of their weight, but `disclaimSpawnedAgents`, Terminal.app automation and future pairing would remain.
- **A5 — version skew is safe if the field name stays `token`.** An older, separately installed CLI (`scripts/install.sh` → `/usr/local/bin` or `~/.local/bin`) reading a new file gets the scoped token and keeps working for CLI routes. A new CLI against an older core gets the master token. If a new field name were used instead, old CLIs would break.
- **A6 — the webview's master token is not agent-readable.** It lives in process memory (Bun and WKWebView), and K7 found it nowhere on disk, in argv or in env. That would stop holding if WebKit cached a `?token=` URL to disk, or if the webview were compromised (K15), which is the reason for the `?token=` and native-dialog items.

## 4. What we must ask the owner

1. **What "fix it" covers in this branch.** Options: (a) credential split, route policy table and invariant test; (b) plus moving today's escalating routes to desktop-only; (c) plus removing `?token=` (CLI first, then webview); (d) plus groundwork for native pairing. Recommendation: a + b + c (CLI header now; the webview too if you want it complete) + docs + the env-strip and dev-token hygiene below; leave native pairing to Companion v1, since building it now has nothing to pair with. *Why it matters:* it decides the plan's size.
2. **Credential shape.** Recommendation: two tokens. The **master** stays in memory (webview via preload and hash, e2e/dev via `AGETOR_API_TOKEN`) and is never written. The **CLI token** is a new per-launch random value written to `agetor-core.json` under the existing `token` field (A5). Headless keeps a master too (random, or the env override), so e2e and `dev-headless` still work. *Alternative:* keep one token but strip escalating routes from HTTP entirely. That breaks the webview features that use them.
3. **Which existing routes become desktop-only (master token only).** Proposed set (none is used by the CLI): terminals (`/tasks/:id/terminals`, `/terminals/:id`, the WS upgrade), `/harnesses/:id/open-terminal`, `/tasks/:id/open-tmux`, `/files/preview`, `/tasks/:id/diff/blob`, `/open-path`, `/reveal-path`, `/open-external`, `/refs/pick`, `/refs/drag`, `/projects/pick`, `/bundle/pick-file`, `/bundle/export/save`, `/window/*`, `/app/force-quit`, `/updates/*`, `/screenshots`, `/attachments`, `DELETE /notifications/:taskId`, `POST /tmux-source`. Plus **security preferences**: refuse `disclaimSpawnedAgents = "false"` from the CLI token. Is that a value-level rule (turning it *on* stays allowed), and would you accept `agetor config disclaimSpawnedAgents false` returning an error? *Evidence:* S2, K10.
4. **Harness CRUD stays CLI-scoped?** `agetor harness add/edit --bin/--env` needs it, and an unsandboxed agent could edit SQLite anyway (K11). Making `open-terminal` desktop-only already breaks the Terminal.app chain. Recommendation: keep harness CRUD in CLI scope.
5. **Terminal tabs aren't disclaimed (`terminals.ts:265`).** Is that intended, so the user's own terminal keeps Agetor's grants? Once terminals are desktop-only, agents can't reach them through the API either way. Disclaiming them is a separate behavior change. Keep it out of this branch?
6. **Response when the CLI token hits a desktop-only route.** Recommendation: `403 {error: "only available in the Agetor app", code: "desktop-only"}`, with the CLI printing it plainly. Headless already answers 501 for native routes; should a desktop-only route on headless return 403 or keep 501?
7. **Webview `?token=` (SSE, WS, `<img>`).** Fix now (one-time tickets minted by an authed POST, or a fetch-based SSE reader, WS tickets, `blob:` image URLs) or defer? The CLI part is a one-line header change. Recommendation: CLI now; webview now too if completeness is the bar (you usually pick completeness), otherwise record it as Companion Phase 0.
8. **Strip `AGETOR_API_TOKEN` (and the new CLI token, if exported) from every env Agetor hands down** — tmux clients, terminal tabs, fx children. Recommendation: yes (K8). It costs a filter in `tmuxClientEnv` and two spawn sites.
9. **`dev-headless.sh` token file at 0644** — write it 0600? Recommendation: yes (K9).
10. **Record the future pairing rules now?** Write the Companion requirements into `docs/plans/` so they aren't lost: pairing, enabling remote access and raising device permissions are native-only (a Swift helper or an RPC window, never HTTP and never the webview); the code is shown on the phone and typed on the Mac (K13); revoke and disable may be HTTP/CLI; device-registry rows must be authenticated by a key the agent can't read (a MAC with a key in an app-only Keychain item), because an agent can write `agetor.sqlite` directly and could otherwise insert a device row without ever touching HTTP. That last point is new; the brief's "core key kept in the Keychain" guards impersonation, not registry injection.
11. **README security model wording.** It should say plainly that agents can read the CLI credential and what it can't reach. Approve the wording at plan time?

## 6. Runnability

- **Setup:** `export PATH="$HOME/.bun/bin:$HOME/.local/bin:/opt/homebrew/bin:$PATH"`, then `bun install` (a fresh worktree has no `node_modules`; done in this step).
- **Typecheck and unit/integration tests:** `bun run typecheck`; `bun test`; a single file with `bun test src/bun/core-creds.test.ts`. The CLI daemon tests bind fixed ports (4494-4498 and others) and stall under heavy load; run them serialized.
- **Throwaway core (the spike recipe, never against `~/.agetor`):** `AGETOR_DATA_DIR=<tmp> AGETOR_API_PORT=<port> AGETOR_DAEMON_IDLE_MS=60000 AGETOR_CLAUDE_DRIVER=fake AGETOR_{CLAUDE,TMUX,CODEX,CURSOR,GEMINI,FX,ANTIGRAVITY}_BIN=/bin/echo AGETOR_DISCLAIM_BIN=/nonexistent bun src/bun/headless.ts`, then call the API with the token from `<tmp>/agetor-core.json`.
- **E2E:** Playwright via `bun node_modules/@playwright/test/cli.js test`. `e2e/fixtures.ts` spawns headless with `AGETOR_API_TOKEN` and boots the webview with `#api=…&token=…`. One Playwright run at a time.

## 7. Risks & blast radius

- **Breaking the CLI quietly.** A route the CLI needs but the CLI token lacks would surface only at runtime, because most CLI paths are mocked (S4). The policy table must be derived from, or checked against, the `AgetorClient` route list.
- **The app⇄daemon handoff** reads the daemon's file and calls `/daemon/shutdown` with it (`index.ts:351-360`), so that route must stay CLI-scoped.
- **Headless users:** a container user who used the file token for a route that becomes desktop-only gets a 403. Today only native routes (501) and terminals are affected; terminals over headless with a file token would stop working.
- **e2e and `dev-headless.sh`** need the master token to reach the webview, through `AGETOR_API_TOKEN`; keep that override meaning "master".
- **Version skew** between the separately installed CLI and the app (A5).
- **False sense of security.** The split doesn't stop an unsandboxed agent from same-user harm (K11: the tmux socket, SQLite, CLI-scoped routes). Docs must say what it does protect: Agetor's own OS identity, the TCC separation, and the future remote surface.
- **The webview is the master's weak spot** (K15) — the reason pairing must never be an HTTP route, even a master-only one.
- **`?token=` URLs** keep the master token in WebKit's network layer; none was found on disk today (K7).

# Task context menu

> Moved from `CLAUDE.md`, where this was orchestration-flow item 9. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

**Task context menu** (right-click quick actions on a board card, replacing WebKit's native menu): a document-level `contextmenu` listener in `App.tsx` calls `preventDefault()` app-wide unless `keepsNativeContextMenu(event.target)` (`src/mainview/lib/context-menu.ts`) matches `NATIVE_CONTEXT_MENU_SELECTOR` — text-entry `input`s, `textarea`, `[contenteditable]`, and `.xterm` — or `hasTextSelection(window.getSelection())` reports a non-empty read-only text selection, so spell-check/"Look Up"/paste-and-match-style, the terminal's own right-click menu, and mouse-only Copy/Look Up on selected assistant output keep working (a task card still gets our menu even with stale selected text elsewhere: `TaskCard`'s handler calls `preventDefault()` before the document listener consults the selection).
`TaskCard` only reports `onContextMenu(task, { x, y })` (threaded through `Column`'s memo comparator like every other card callback); dnd-kit is unaffected because its `PointerSensor` bails on `event.button !== 0`. The same callback serves the card's **`⋯` button** (`data-testid="task-card-more"`, `aria-label="More actions"`, `aria-haspopup="menu"`, `aria-expanded` from `Column`'s `menuTaskId` prop): it opens this menu anchored at the button, and the menu returns focus to it on close. The card shows only its primary actions (`cardActions`); Diff, Archive, Unarchive, the extra Stop and Delete live only here, so the menu must stay a superset of everything the card used to show (`task-card-actions.test.ts` pins it).
The entry list itself is `buildTaskContextMenu(task, { isOpen })` (`src/mainview/lib/task-context-menu.ts`), a pure, unit-tested builder that is the single source of truth for which entries show: only the Run gate follows `TaskCard`'s own button precedence — `!archived && !awaiting && !active && !openable && !imported`, the card's final `else` branch — so "Run" is hidden whenever the card would show a different button. The card and the menu no longer mirror each other by comment: both read `taskActionFlags(task)` (`src/mainview/lib/task-card-actions.ts`: `archived`, `active`, `awaiting`, `openable`, `gatePending`, `stoppable`, `isPipelineParent`, `isStepTask`, `imported`, `canMarkDone`), and `TaskCardActions` renders `cardActions(task)`.
Every other entry is exposed independently of the card's single-button choice: the menu is additive, not a mirror, so it can list Open details and Stop together, or show Stop even when the card's own button reads Answer/Review.
It also hides the read/unread pair while that task's own run panel is open, and gates "Mark as unread" on `Task.hasAssistantMessages` so a task that has never produced an assistant message can't be dishonestly re-flagged.
`App.tsx` maps each returned `action` to the same callbacks the hover buttons already use (`start`/`cancel`/`markDone`/`archive`/`unarchive`/`del`, confirm dialogs included) plus `openPath`, the shared View-PR handler, the durable View-issue handler, mark-read/mark-unread, and clipboard copies of `branch`/`worktreePath`.
On a multi-repository task (issue #291) there is no single branch, worktree path or PR: the menu instead offers `Copy <repo> branch`, `Copy <repo> worktree path` and `View <repo> PR: <head>` for every pull request each repository opened (a converted legacy PR with no recorded head reads `View <repo> pull request`), resolved from the entry's `repo` name. A single-repository task lists one `View PR: <head>` per entry of `Task.prs` (read through `taskPrsOf`, so an older core's `prUrl`-only JSON still shows its PR). Each entry carries its `prUrl` and an item id `view-pr-<n>`, and the handler opens that URL, not "the" PR. Past `MAX_FLAT_PR_ENTRIES` (3) pull requests, counted across repositories, the entries collapse into one `View pull requests` (`view-prs`) item that opens a **submenu** (a `type: "submenu"` item in `<ContextMenu>`: hover, Enter or ArrowRight opens a portaled child panel placed by `placeSubmenu`; a keyboard open moves focus into the child only once `placeSubmenu` has positioned it, because the panel is `visibility: hidden` until then and refuses focus; ArrowLeft or the first Escape closes only the child, also when a hover opened it and focus is still on the parent item; a new anchor or item set while the menu stays open, such as a right-click on another card, drops the child and focuses the new menu's first item, compared by value so an ordinary re-render keeps it). The single View-PR entry only appears when the task has PRs of its own (a multi row never has task-level ones), and View issue passes `issueProjectPath` so the GitHub dialog reads the repository that owns the issue — never the non-git workspace root.
The rendering primitive, `<ContextMenu>` (`src/mainview/components/ui/context-menu.tsx`), is controlled — App owns `open`/`x`/`y`/`items` — and portals to `document.body` with `position: fixed`, because a non-portaled `fixed` descendant breaks under the RunPanel `<aside>`'s `translate-x` transform (a CSS transform on an ancestor rebases `fixed` to that ancestor instead of the viewport); it's styled `bg-card`/`border-border` since there is no `popover` token (see the undefined-token trap in [CLAUDE.md § UI conventions](../../CLAUDE.md#ui-conventions)), and it carries a `data-popover-open=""` marker that is load-bearing, not decorative: RunPanel's document-level Escape/Cmd+F handlers bail out whenever that marker is present, which is what lets the first Escape close the menu instead of the panel.
Positioning is `placeContextMenu` (`src/mainview/lib/context-menu.ts`) — opens bottom-right of the cursor, flips to the opposite side per axis on overflow, then clamps into an 8px margin — and keyboard roving focus is `moveMenuIndex` (wraps, skips separators/disabled items); the outside-`mousedown` close deliberately ignores the right button (`e.button === 2`) and defers to a capture-phase outside-`contextmenu` listener instead, which is why a right-click on a second card moves the menu (close-then-open batched in one event) rather than dismissing it, backstopped by a document-level Escape listener for when focus isn't inside the panel.
Server side, "Mark as unread" is `DELETE /tasks/:id/seen` → `tasks.markUnread`, which sets `last_seen_event_id = last_assistant_event_id - 1` (not `0`, so exactly the latest message reads as unread) in one guarded UPDATE — a no-op when the task is already unread or `last_assistant_event_id IS NULL`, and it can never move an already-lower watermark back up; like `markSeen` it deliberately skips the `updated_at` bump, for the same `reconcileById` identity-preservation reason.
`Task.hasAssistantMessages` is derived in `toTask` (`last_assistant_event_id != null`), optional for the same fixture-compatibility reason as `unread`, and surfaced client-side via `api.markTaskUnread`; like `POST …/seen`, the `DELETE` route is deliberately not archived-gated, and the UI merges back only the returned `unread` field, never the whole `Task` snapshot.

**Human steps.** A pipeline parent with a pending human gate (`pipelineRun.humanSteps` non-empty) gets a **Review pipeline** entry (`review-pipeline`, group `primary`, right after **Open pipeline**) and loses **Mark done** (which is otherwise shown for any `review`-column task). The card's own Review button (`task-card-pipeline-review`) does the same from the board, and Stop — offered while a gate is pending as well as while the run is `running` — asks for confirmation first. At a gate the card shows Review and Open and **no Stop**: Stop lives in `⋯`. Stopping a pipeline parent always confirms, from the card's Stop and from this menu alike, because both route through App's `stopFromBoard` (the menu's Stop used to skip the confirmation); `TaskCard` has no stop logic of its own. Both Review paths land on the run view with the gate's panel open. The menu's danger entries (Delete…) use `text-danger`, not `text-destructive`, which is below AA contrast on the popover in either theme.

# Keeping the core responsive: bounded spawn, history windows, cooperative jobs, lag monitor, busy banner

> Moved from `CLAUDE.md`, where this was orchestration-flow item 16 plus the main-thread / event-loop-lag / busy-banner / real-watcher-seam bullets of “Things that will trip you up”. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

**Bounded spawn await on send/start** (`docs/plans/task-details-blank-while-session-restores.md`): `POST /runs/:id/input` (claude idle branch → `spawnResumedSession`) and `POST /tasks/:id/start` (`startTaskInner`'s final `spawnAgentOrFail`) wait at most `SPAWN_RESPONSE_BUDGET_MS` (1.5 s, `shared/types.ts`) for the agent spawn.
Past that the response returns immediately with `pending: true` on top of today's shape (`{ delivered: true, runId, pending: true }` / `{ runId, pending: true }`) — the run row, the `running` column flip and the user event already exist — and the spawn continues as a detached continuation that still holds the per-task `startingTaskIds` claim until it settles (so a second message is declined with the existing "another message is already starting a new turn" / "task is already starting" result until the continuation registers the run, after which follow-ups fold via `active` exactly as before).
On settle the continuation re-reads the task: if it was deleted, archived, or `task.runId` no longer names this run, the freshly spawned agent is killed (`agent.kill()`, plus `dropSession` for claude-code) and the run is recorded `cancelled` — never registered.
A Stop pressed during that pending window is honored too: `cancelRun` finds no `active` handle, records the run in `pendingCancelRunIds`, and the spawn path consumes it right before it would register (`consumePendingCancel` — used by the codex/cursor/gemini/antigravity/opencode/copilot/fx one-shot spawns and the claude idle mint; the two bounded continuations do the same inline): the agent is killed, the run recorded `cancelled`, the task returned to `ready` with a status line, and the follow-up queue dropped exactly as on a failed spawn.
A Stop that lands even earlier, while a spawn holds the task's `startingTaskIds` claim but hasn't minted its run (codex's per-model CLI floor probe runs there), is recorded against the claim (`pendingCancelTaskIds`, via `cancelLiveRunOfTask`) and handed to the run the claim mints (`adoptPendingTaskCancel`, called by every claimed mint right after `task.runId` points at the run and before its `running` column event); `releaseStartingClaim` drops it when the claim ends without a run, and `isTaskRunCancelling` counts a current run carrying a pending cancel.
A spawn that settles inside the budget is byte-identical to before (no `pending` key).

**`POST /runs/:id/input` is bounded end to end** (`docs/plans/non-blocking-session-restore.md`, decision D) — the outer race is opt-in, `sendInput(runId, line, { bounded: true })`, passed ONLY by that route: internal callers (the pipeline handoff reminder, cursor plan approve, the ask-card fallback message) await the real outcome, because they act on `delivered` and the budget equals `PASTE_MODAL_GRACE_MS`, so every withheld claude paste would otherwise read `{ delivered: true, pending: true }` (claude's own idle-mint `pending` from `spawnResumedSession` is unchanged): only the `run not found` / `task not found` lookups answer synchronously;
everything after them — the codex CLI floor, the `archivedAt` clear (still after the floor, so a refused send never un-archives), `pendingTeardown`, the pipeline-step guard, the worktree restore, `@`-expansion, the argv re-check and the per-kind dispatch — runs as `sendInputInner`, raced against the same budget.
Past it the answer is `{ delivered: true, runId, pending: true }`, where `runId` is the run this message minted when the dispatch got that far (`pendingRunIdFor`: `task.runId` changed to a run created during this send), else the run it was addressed to; a late `delivered: false` re-stashes the RAW (pre-`@`-expansion) text into the task's backlog (`restashPasteWithheldText`, which now reports whether it stashed) and emits a live-only `send-failed` `GlobalEvent` (`{ taskId, reason, savedToBacklog }`, pipeline-parent stamped) that the webview toasts ("Message not sent", not gated on the open panel) and the TUI shows as one line; the CLI's `send` can't observe a late failure (its usage text says so).
Why: in the owner's packaged app a claude `--resume` launch took 5–31 s and the held request starved the webview's connection budget (see the connection budget in [run-panel.md](run-panel.md)).
`spawnClaudeViaTmux` additionally times its three pre-launch stages (`killTaskSession`, `ensureInstalledForCwd`, `tmux new-session`) and, past `SLOW_LAUNCH_WARN_MS` (5 s), emits one `status` line `session launch took Ns (kill … · settings … · tmux new-session …)` — before the `ready` line, and also when `tmux new-session` itself fails — plus a `console.warn` — the breadcrumb that names the slow stage.
History payloads are byte-budgeted as well as count-capped: the SSE replay (`EVENTS_REPLAY_LIMIT` = 800 events AND `EVENTS_REPLAY_MAX_BYTES` = 4 MB), `/tasks/:id/events/page` (`EVENTS_PAGE_MAX_BYTES` = 2 MB) and `/runs/:id/rebuild-events` **only when `?limit=` is passed** (the auto-rebuild on panel open; same 4 MB) — the no-limit path, used by the panel's manual "Rebuild from session JSONL" button and the CLI, deliberately returns the complete history, because it is the one way to see JSONL-only events the persisted rows lack and "Load earlier" pages the persisted rows, not the JSONL — each capped window keeping at least `MIN_REPLAY_EVENTS` = 20 events and never truncating a single event — `runs.eventsForTask({ limit, maxBytes, minEvents })` walks the newest-first id list accumulating `LENGTH(data)`; older history stays reachable through "Load earlier".

**The first load is additionally anchored to the last user message** (`docs/plans/first-load-reaches-last-user-message.md`): the SSE replay and the `?limit=` auto-rebuild both extend their window's floor back to the newest main-stream `user` event (`runs.lastUserEventId`, main stream = `subagent_id IS NULL`, any content
— a slash-command or `<local-command-stdout>` echo counts — except the hidden harness-stack continuation agetor sends after an account switch, which both the replay anchor and the rebuild route's anchor scan skip) whenever the span from it to the newest event fits BOTH `EVENTS_REPLAY_ANCHOR_MAX_EVENTS` (3000, deliberately = `EVENTS_WINDOW_MAX`, the webview's own flush-trim cap) and `EVENTS_REPLAY_ANCHOR_MAX_BYTES` (16 MB) — all-or-nothing via the pure `resolveAnchoredMinId` (`db.ts`), shared by `eventsForTask({ anchor })` and the rebuild route's in-memory slice, so over either ceiling the plain 800 / 4 MB window stands (2000 / 4 MB on the rebuild branch, whose `?limit=` is server-clamped at 2000 while the panel asks for `EVENTS_WINDOW_MAX`) and "Load earlier" pages as before;
`/tasks/:id/events/page` never anchors, `/tasks/:id/events?anchor=0` opts a client out (the TUI dashboard's `useCoalescedStream` passes it, since it keeps only 500 lines), `hasMore` still derives from the returned window (so it can stay true for breadcrumbs older than that user message), and the CLI's `agetor logs` inherits the anchored window through the same SSE route.

**A reconnect resumes forward** (`docs/plans/event-stream-forward-resume.md`): every saved row's frame on `/tasks/:id/events` carries an SSE `id:` line (= `run_events.id`, replayed and live alike — saved rows only; `interaction`, `interaction_resolved`, `subagent` lifecycle, ping and `replay_meta` never get one, and never an empty `id:`), and the route takes a cursor from `Last-Event-ID` or `?afterId=` — the first VALID of the two (`resolveResumeCursor` in `src/bun/event-resume.ts`: `/^[0-9]{1,16}$/` and a safe integer; anything else is ignored as if absent, never a 400, since `openEventStream` retries a 400 forever).
With a cursor, `runs.eventsForTaskAfter` reads `sqlite_sequence` and probes the ids of at most 801 rows of the task (index-only; their byte lengths are read only when the count fits — subagent rows included; counted in rows, never as an id difference — ids interleave across tasks) and the pure `decideForwardResume` answers all-or-nothing: the gap is sent only when it is ≤ 800 rows AND ≤ 4 MB (`replay_meta` `{earliestId: null, hasMore: false, resumedAfter: <cursor>}`, then just the gap); otherwise — or when the cursor is ahead of `sqlite_sequence` (another or a wiped database) — `snapshotRequired: true` with exactly the window and `earliestId`/`hasMore` a no-cursor connect with the same `?anchor` gets, on the same connection.
CORS allow-headers carry `last-event-id`.
The cursor is only sound because a saved row's live send is synchronous right after its insert (send order = id order): every save-then-send site goes through `saveAndEmit` (`orchestrator.ts`) or sends the `{id, ts}` that `runs.appendEvent` now returns, sends nothing on a `(run_id, line_uuid)` dedup hit, and the claude monitor sink stores the notification line's own time as the row `ts` so live and replayed copies agree — never batch or defer such a send.
Four lines that used to be broadcast-only are saved rows now (`saveStatusLineQuietly`, which never throws on a settle path): the opening `started — …` breadcrumb, `background agents still running (N) — holding in running`, `exit:N` / `cancelled (exit:N)`, and the spawn-rejection `cancelled` / stderr `String(err)`; older runs aren't backfilled.
Clients keep the transport's last SSE id (sent back as `Last-Event-ID`) apart from the consumer's highest accepted id (`createIdHighWater`, `src/shared/task-stream-resume.ts`, drops any frame with an id at or below it, which also keeps an older core's full replay duplicate-free) and classify each `replay_meta` with `classifyReplayMeta`: the RunPanel resets on a snapshot (see "Things that will trip you up"), `agetor logs` never prints a row older than one it already printed and puts one dim `LOGS_STREAM_GAP_NOTICE` on stderr, and the TUI's `useCoalescedStream` clears its lines and shows a dim `TASK_STREAM_GAP_NOTICE` row.
Desktop cursors last only across reconnects of one live subscription (opening/switching a task or relaunching is a fresh connect).
Test seams: `AGETOR_TEST_DROP_STREAMS_ROUTE=1` registers a test-only `POST /test/drop-task-streams { taskId, holdMs? }` (desktop-only + conditional in `ROUTE_POLICY`; closes the task's open streams and holds new requests for that task's stream server-side for `holdMs`, 0–30000, so a reconnect resumes over a deterministic gap — `e2e/event-stream-resume.spec.ts`), and `FAKE_CLAUDE_DONE_REJECT_PROMPT_MARKER` (`__agetor_fake_claude_done_reject__`) makes the fake claude driver's `done` reject after its prompt echo, exercising the spawn-rejection settle path.
Test seam: `FAKE_CLAUDE_LONG_REPLY_PROMPT_MARKER` (`__agetor_fake_claude_long_reply__`, optional `:<count>` suffix, default 900 > `EVENTS_REPLAY_LIMIT`, clamped 1..5000) makes the fake claude driver emit that many `assistant` chunks.
Test seam: `AGETOR_FAKE_CLAUDE_SPAWN_DELAY_MS` delays the fake claude driver's SPAWN (unlike `AGETOR_FAKE_CLAUDE_RESOLVE_DELAY_MS`, which delays the turn's resolution).
`AGETOR_FAKE_CODEX_RESOLVE_DELAY_MS` (default 20 ms) is the codex-side counterpart: it holds a fake codex turn in flight so a test can queue follow-ups behind it and mutate the task before `drainCodexQueue` runs (`orchestrator-codex-queue-floor.test.ts`).
`AGETOR_FAKE_CLAUDE_TURN_MS` (default 20 ms) is the claude counterpart for the fake driver's generic turn: it holds the turn open so a test can fold a follow-up into it deterministically instead of racing the 20 ms timer (`orchestrator-paste-withheld.test.ts`).

- **The Bun main thread is shared by every task, pipeline and panel** — a synchronous loop over a large table or many files in a spawn/restore path freezes all of them (`docs/plans/non-blocking-session-restore.md`).
  Long work must be a cooperative job (see the subagent watcher's `createSeedJob`/`createCycleJob` and `retention.ts`): step in ~20 ms slices, `await` a `setImmediate` yield between them.
  Consequence for the watcher: in production `handle.pump()` (and so `pumpWatcherForHoldCheck`) is a no-op until the first cycle has finished (~0.6 s + replay after an attach); in `manual` test mode the seed runs synchronously at attach and the first `pump()` drains the first cycle, so the manual-mode tests drive it exactly as before.
- **Event-loop-lag monitor** (`src/bun/event-loop-lag.ts`, started by `index.ts`/`headless.ts` with a 100 ms sampler BEFORE the boot restore — ahead of `ensureDisclaimedServer()`/`reconcileOrphans()`, so the boot-time `reattach session`/`boot reattach` labels are sampled; `.unref()`'d): one `console.warn("[agetor] core was unresponsive for N.N s during <label>")` per stall ≥ 1 s, attributed to the `beginLagLabel(label, { taskId, runId })` that overlapped it
  — among near-equal overlaps the most recently BEGUN label wins (not the deepest: labels span `await`s and interleave across tasks, so stack depth isn't nesting) (labels today: the subagent-watcher attach, `reattach session`, `boot reattach`, `archived-history retention`, `compact database`, and the context-free `native file dialog` that `server.ts`'s `openFileDialogLabelled` brackets every Electrobun `openFileDialog` with
  — a synchronous FFI call that blocks the main thread while the panel is up); when the label carries a run, the orchestrator's sink also appends `core was unresponsive for N.N s during <label>` as a status line on that run.
  Off under `bun test` (`NODE_ENV=test`) unless `AGETOR_LAG_MONITOR=1`; `AGETOR_LAG_MONITOR=0` disables it anywhere.
- **Busy banner** (`src/mainview/lib/core-busy.ts` + `components/CoreBusyBanner.tsx`): `j()` registers every request; once one has been pending > 3 s the watchdog probes the unauthenticated `/health` (1.5 s abort) every 2 s, and two consecutive probes with no answer (`FAILED_PROBES_TO_SHOW` — one miss alone can be the probe queueing behind the very requests it watches in WKWebView's ~6-connection pool) show the app-level "Agetor is busy — waiting for the core…" strip (`core-busy-banner`) until a probe answers or everything settles.
  Purely observational — nothing is aborted or retried because of it; requests whose block is expected run through `withCoreBusySuspended` (`api.ts`), which suspends it for their lifetime: `api.compactDb()` and every request that opens a native Open panel (`pickProject`, `pickRefs`, `pickBundleFile`, and `saveBundle` with the `folder` target only).
  `AGETOR_TEST_BLOCK_ROUTE=1` registers a test-only `POST /test/block-event-loop { ms }` (`Bun.sleepSync`, ≤ 20 s) so the e2e can freeze the core on purpose; it is never registered otherwise.
- **Real-watcher fake seam**: `FAKE_CLAUDE_REAL_WATCHER_PROMPT_MARKER` (`__agetor_fake_claude_real_watcher__[:<files>x<kb>]`, `agents.ts`) makes the fake claude driver write N claude-shaped subagent transcripts under `<cwd>/agetor-fake-claude/…`, insert their `subagents` rows and attach the REAL watcher (awaiting `settled`); later turns of the task only re-attach (a genuine rehydrate that must persist zero new events).
  `e2e/non-blocking-restore.spec.ts` uses it; the timing bar itself is pinned by `src/bun/subagent-watcher-drift.test.ts` (real watcher over ~200k seeded events + large transcripts, max loop gap < 150 ms).

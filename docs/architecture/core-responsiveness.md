# Keeping the core responsive: the worker core, bounded spawn, history windows, cooperative jobs, lag monitor, busy banner, delta and push

> Moved from `CLAUDE.md`, where this was orchestration-flow item 16 plus the main-thread / event-loop-lag / busy-banner / real-watcher-seam bullets of “Things that will trip you up”. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

## The worker core: no SQLite and no big parse on the main thread

`docs/plans/non-blocking-core.md` moved every database query and every transcript parse off the Bun main thread, which serves HTTP, SSE, tmux and the orchestrator. The bar is a `/health` p95 and a main-thread block both under 100 ms during heavy work.

### Architecture

```
caller → db-async.ts → db-rpc.ts → postMessage → core-worker.ts (role "db") → workers/db-handler.ts → db-core/* → bun:sqlite
```

- **One connection, in one worker.** The `db` role of `src/bun/core-worker.ts` opens the only SQLite connection of a production core, applies the pragmas (see [persistence.md](persistence.md)), runs the migrations and serves requests. The main thread opens no connection.
- **Production imports `db-async.ts`.** It has the module names of `db.ts` (`tasks`, `runs`, …), with every method returning a Promise. It is typed from the db-core factories and forwards a call by name through a Proxy, so it cannot drift from them. `db.ts` is the synchronous module for tests and the in-process mode only. `src/bun/db-import-guard.test.ts` fails on a production import of it.
- **The facade overlays main-thread state.** The worker cannot see the in-memory interaction and terminal registries, so it reports `pendingInteractionCount` and `openTerminalCount` as 0. Boot wires the registries in with `setTaskDecorations`, and every `Task` (or `Task[]`, or `(Task | null)[]`) the facade returns is overlaid with the real counts, whether it came from a module call or from an `op(...)` result, so a worker-mode result matches the in-process one.
- **Two modes**, chosen once per client by `AGETOR_DB_MODE` (`worker` or `inprocess`; any other value is ignored). The default is `inprocess` under `NODE_ENV=test` and `worker` everywhere else. In-process mode runs the same dispatcher on the calling thread against the `db.ts` singleton. It clones arguments, results and errors the way a worker hop does, so a test sees what production sees. `AGETOR_DB_MODE=inprocess` is also the kill switch for a production core: if the worker misbehaves, it runs the one connection on the main thread (no worker is started), with a boot warning that heavy queries can stall the app. The kill switch is honored in production on purpose (plan section 5), and it keeps two guards against that stall: outside `NODE_ENV=test` the `db.ts` connection waits at most 100 ms for a lock (`SHORT_BUSY_TIMEOUT_MS`, set after its migrations; the worker's connection waits 5 s), and `closeDb` checkpoints the WAL (`PRAGMA wal_checkpoint(TRUNCATE)`) as the worker's close does.
- **FIFO.** The worker serves one message at a time, in the order posted, so a read after a write sees the write. Every reply carries `task_rev_meta.rev`. `db-rpc.ts` notes a rise, calls the `onRevChanged` listeners and announces it on `task-change-bus.ts` (the push in [Delta and push](#delta-and-push-the-boards-task-list)).
- **The worker file is found by `worker-entry.ts`**: `AGETOR_CORE_WORKER_ENTRY` (test and e2e only, see [security.md](security.md); read on every start, never pinned), then `core-worker.js` next to the running bundle, then the packaged `Resources/app/{bun,daemon}/core-worker.js`, then the source `core-worker.ts`. `scripts/build-daemon-bundle.ts` builds `vendor/daemon/core-worker.js` and `electrobun.config.ts` copies it into `app/bun/` and `app/daemon/`. **The entry is resolved once per process** and the path is reused for every later start (a restart after a crash, the lazily created transcript worker), so a file swapped on disk later cannot change which code a later worker runs.
- **The worker's console reaches `core.log`.** The worker forwards `console.*` as `{ log: { level, text } }` messages. The text is redacted (the pattern half of `core-log`'s redactor, `log-redact.ts`) and then cut at 8,192 characters, so a secret that straddles the cut never leaks its prefix. The main thread re-emits it with a `[agetor:db-worker]` or `[agetor:transcript-worker]` prefix, and `core-log` adds the registered literal secrets, which only the main thread knows.

### Worker build id

The worker bundle is a separate file from the main bundle, so the two can come from different builds: a packaged app updated in place while a core is running (the core's lazily started transcript worker, or its DB worker after a crash, would load the NEW `core-worker.js` beside the OLD main code, and a newer DB worker would run its migrations under the older core), or a dev rebuild that refreshed one bundle and not the other. Both bundles therefore carry the same **build id** (`src/bun/build-id.ts`).

- **Where it comes from.** `scripts/build-daemon-bundle.ts` hashes `src/bun`, `src/shared` and `package.json` and writes `vendor/build-id/build-id.ts` before it builds the bundles. The main bundle (built by Electrobun afterwards) and `headless.js`/`core-worker.js` all inline it. A run from source (tests, `bun src/bun/headless.ts`) has no generated file and reports the stable marker `dev` on both sides.
- **The handshake.** `createCoreWorker` puts the main thread's id in the worker's init message. A worker whose own id differs **refuses before it opens the database**, so no migration can run: it posts `{ ready: false, buildMismatch: true, error }` (db role) or `{ buildMismatch: true, error }` (transcript role) and answers nothing else. A db worker also reports its id in `{ ready: true, buildId }`, and the client refuses a missing or different one. The client terminates that worker, logs `database worker down: core worker build mismatch: worker X, main thread Y; restart Agetor` to `core.log`, and from then on rejects every call with a `DbUnavailableError` (503 `db-unavailable` on a route) instead of starting another worker from the same bundle. The transcript client rejects with `TranscriptClientError` code `EBUILDMISMATCH` the same way.
- **Dev.** `electrobun.config.ts` sets `scripts.preBuild` to the bundle script, which Electrobun runs at the start of every build, including each `bun run dev` watch rebuild (a change under `src/bun/`), so the worker copy and the id are refreshed together with `index.js`. `vendor/**` stays in `watchIgnore`: the script's own output must not trigger another rebuild. If the hook ever fails to run, the mismatch check is what makes the stale worker visible as a clear message instead of an unknown-op 500, and restarting `bun run dev` fixes it.
- **Tests.** `src/bun/worker-build-id.test.ts` (a mismatched worker is refused before the database file exists, a restart does not start another one, the transcript worker too, the entry is pinned, the log text is redacted before the cut).

### Named ops

A transaction never spans a thread hop. A unit of work that needs more than one statement to commit or roll back together is a named op in `src/bun/db-core/ops/<area>-ops.ts` (`defineOp({ tx, run })`, named `<area>.<verb>`, spread into the registry in `ops/index.ts`). The caller runs `op("<area>.<verb>", [...args])`, and the whole op runs inside the worker. `tx: true` wraps it in `BEGIN IMMEDIATE`, so a throw rolls back every write of the op. An op never imports `db.ts` or a main-thread registry, and its arguments and result must be structured-clone safe. Ops named `__test.*` are refused outside `NODE_ENV=test`.

A raw `db.query(...)` or `db.transaction(...)` outside `db-core` is a bug: it becomes a db-core method or an op.

### Read-modify-write

A read is a thread hop, so "read, decide, write" is three steps another caller can interleave with. Every such site uses one of three patterns:

1. **One op.** Read, decide and write inside a single op, in one transaction. The guarded column moves (`orchestrator.setColumn`) and the plan writes (`server.approvePlan`) are examples: the guard is checked against the rows inside the transaction, not against an earlier read.
2. **A per-task lock plus compare-and-set.** The state is read under a per-task async lock, the next value is computed, and `harnessState.cas` writes it only while the stored state still serializes to what was read. A false answer means someone else changed it: the caller re-reads and decides again (up to five attempts). This is how `harness_state` is written ([harness-stacks.md](harness-stacks.md)).
3. **A lock whose holder is the sole writer.** `withPipelineLock(parentId, …)` serializes every mutation of one pipeline parent, and `persist` is the only writer of `pipeline_run`, so no compare-and-set is needed ([pipelines.md](pipelines.md)).

In-memory claims (`startingTaskIds`, the switch claim) are taken synchronously, before the first `await`, so a start decision made from an earlier read can't race a second one ([task-lifecycle.md](task-lifecycle.md)).

### The per-run emit queue

`appendAndEmit` (`src/bun/run-emit-queue.ts`) is how a saved `run_events` row reaches the live stream. With an asynchronous insert, two flows appending to one run could finish out of order and send their SSE frames out of id order, which the forward resume below cannot tolerate. So the call takes its place in the run's queue synchronously, the inserts run one at a time per run, and each row is sent right after its own insert resolves, in call order. Different runs never wait on each other. A failed insert rejects only its own call and the queue moves on. A throwing emitter is logged and loses nothing. A run's entry is dropped as soon as it settles.

Every live send of a saved row goes through it (`saveAndEmit` in `orchestrator.ts` rides it): send order = id order.

### Crash and restart

- A worker that errors or exits rejects every in-flight call with `DbRestartingError` and is restarted, at most 5 times in a sliding 60 s window. Past that, calls reject with `DbUnavailableError` until the window passes. The event goes to `core.log`.
- Calls made while the worker is starting, or between a crash and its restart, wait their turn instead of failing.
- **The outcome of an in-flight write is unknown.** The worker may have committed before it died, with only the reply lost. No layer retries a non-idempotent call (`tasks.insert`, `runs.appendEvent`, …). A caller retries only when its call is idempotent or it re-reads to find out.
- **Routes answer 503**, not 500: `DbRestartingError` is `503 {code: "db-restarting"}` (`Retry-After: 1` on GET and HEAD only), and `DbUnavailableError` is `503 {code: "db-unavailable"}` (see the 503 bullet below). `/health`, `/info` and headless `/daemon/shutdown` touch no database and keep answering.
- A result that is not structured-clone safe fails its own call with `DbResultNotCloneable`, not the worker.

### Boot and quit

- **Boot.** `index.ts` and `headless.ts` install `core.log` first, register the tokens for redaction, call `setTaskDecorations`, and start the worker with `awaitDbReady()` (`src/bun/boot-db.ts`) while the rest of boot proceeds. The worker opens the database and runs the migrations before the boot gate opens, so `reconcileOrphans()` and every route wait for it, while `/health` and `/info` answer at once. Only opening is timed (30 s): the worker posts `{ migrating: true }` once the connection is open, and a long migration is not killed. A failure is logged and retried with a doubling backoff from 500 ms to 15 s. The core neither skips it nor exits.
- **Quit.** The desktop's before-quit handler vetoes the first quit and runs `runQuitSequence`: the quit effects first (they may still write), then `drainCoreForQuit` (flush `core.log`, then close the worker, which waits for in-flight calls and checkpoints the WAL). The whole sequence is bounded at 8 s (`QUIT_SEQUENCE_MAX_MS`; the drain alone at 5 s, the worker close at 3 s). Then it re-issues the quit. A headless core waits for its launch freeze (bounded), runs the same drain and calls `process.exit`.

### The transcript worker

The second role of `core-worker.ts` reads and parses subagent transcripts, so the file read, the UTF-8 decode and `JSON.parse` never run on the main thread (`transcript-client.ts` on the main side, `workers/transcript-handler.ts` in the worker, `transcript-parse.ts` shared by both and by the in-process mode).

- It serves one request at a time. A crash, an unserializable reply or a request over 30 s ends the worker, rejects the in-flight call and starts a fresh worker for the queue (the same cap of 5 per 60 s).
- **`allowedRoot` is required.** Every call names the subagents (or workflows) directory the watcher already validated. The handler refuses, with no read, unless the path is absolute, NUL-free, free of `..` and directly under that root, and every directory below the root is a real directory, not a symlink. The file itself is opened no-follow. See [security.md](security.md).
- **Replies are small.** The watcher reads 64 KB chunks (`TAIL_READ_CHUNK_BYTES`), because a larger reply costs the main thread too much to deserialize.
- A single line over 64 MB (`MAX_LINE_BYTES`) comes back as `tooLarge`, with the offset moved past it. `meta.json` is read up to 1 MB.

### The watcher passes

Every pass of the Claude subagent watcher (seed, first cycle, steady tick, the coalesced dir-watcher pass, `pump`) is a cooperative job: slices of about 20 ms with a `setImmediate` yield between them, at most one pass per watcher. A dir-watcher burst folds into one pass 50 ms later (`DIR_PASS_COALESCE_MS`). Each chunk's events go in with one `runs.appendEvents` call (one transaction) through `appendAndEmit`, so the `(run_id, line_uuid)` dedup and the id order hold. A failed batch retries per event. The `attach subagent watcher` lag label brackets work slices only, never a yield or idle time. A transcript outside the watcher's directories is not tailed. Pinned by `subagent-watcher-tick.test.ts` (39 files of 5 MB appended to concurrently, max gap under 100 ms) and `subagent-watcher-drift.test.ts`.

### core.log

`src/bun/core-log.ts` tees `console.log/info/warn/error/debug` into `<dataDir>/logs/core.log`. The packaged app sends the core's stdio to `/dev/null`, so this file is the only trace of a stall.

- **Where and how.** The file is mode 0600 in a 0700 directory. At 5 MB it rotates, keeping three files (`core.log`, `.1`, `.2`). A console call only formats, redacts and queues the line. A buffered async writer flushes every 200 ms or 64 KB. The queue is capped at 2 MB (the oldest lines drop, with a counted marker), and one line is cut at 16 KB. The only synchronous write is the best-effort flush on `process.on("exit")`.
- **Redaction** is described in [security.md](security.md#corelog-contents-and-redaction).
- **On by default**, except under `bun test`: `AGETOR_CORE_LOG=1` turns it on there, and `AGETOR_CORE_LOG=0` turns it off anywhere.
- **Every stall of 1 s or more** is logged by `event-loop-lag.ts`, labelled or not, as `[agetor] core was unresponsive for N.Ns during <label|idle> {json}`. The JSON tail is `{lagMs, label, taskId?, runId?, overlaps: [{label, overlapMs, taskId?, runId?}]}`, with up to 10 overlapping labels, the longest first.

### Event-loop-lag label scope

A stall is attributed to the label whose interval overlapped it most (see the monitor bullet below). A label brackets only synchronous or slice-sized work, never an `await` on the database. Today's labels are `reattach session`, `boot reattach`, `attach subagent watcher` (work slices only), `archived-history retention` (disposed before every yield), `compact database` (in-process mode only: in worker mode the VACUUM runs on the database worker, and the main thread is not blocked), and `native file dialog` / `native message box` (synchronous FFI calls that block while a native panel is up).

### Structured-clone cost

Every worker reply is structured-cloned, and the receiving thread pays for it: posting a 30 MB result cost the receiver 2 to 31 ms in the spike. So keep worker replies small. Don't return a whole table or a whole history from a method. Page it, project it (the board's delta), or cap it in SQL (the byte-budgeted history windows below). The transcript reply is capped at 64 KB per chunk for the same reason.

### The benchmark

`bun run measure:core` (`scripts/measure-core-responsiveness.ts`) boots a headless core on a throwaway data dir under `~/.agetor-dev/bench-<timestamp>/`, drives a heavy load and reports how responsive it stayed:

- `GET /health` probed every 50 ms (p50, p95, p99, max, and the count over 1 s and 3 s);
- the board poll, a transcript replay of a task with many large subagent transcripts, and a fake subagent run;
- the stalls the core's own monitor wrote to `core.log`.

Run it before and after a change and diff the two reports (`--label before|after`, `--json <out>`). `--calibrate` blocks the core's loop once and checks that the probe sees it.

**The `--source` rule.** `--source <agetor.sqlite>` copies a real-sized database with `sqlite3 -readonly … .backup` (never `cp`, which breaks WAL consistency) and sanitizes the copy (running runs become `orphaned`, non-builtin harnesses are disabled). Never point it at the live `~/.agetor` database: make a `.backup` copy into `~/.agetor-dev` and pass that. The script runs the core with a sandboxed `HOME`, `PATH` and fake drivers, refuses a target dir inside, equal to or containing `~/.agetor`, and never writes outside the bench dir it created.

## Spawn, history windows and stream resume

**Bounded spawn await on send/start** (`docs/plans/task-details-blank-while-session-restores.md`): `POST /runs/:id/input` (claude idle branch → `spawnResumedSession`) and `POST /tasks/:id/start` (`startTaskInner`'s final `spawnAgentOrFail`) wait at most `SPAWN_RESPONSE_BUDGET_MS` (1.5 s, `shared/types.ts`) for the agent spawn.
Past that the response returns immediately with `pending: true` on top of today's shape (`{ delivered: true, runId, pending: true }` / `{ runId, pending: true }`) — the run row, the `running` column flip and the user event already exist — and the spawn continues as a detached continuation that still holds the per-task `startingTaskIds` claim until it settles (so a second message is declined with the existing "another message is already starting a new turn" / "task is already starting" result until the continuation registers the run, after which follow-ups fold via `active` exactly as before).
On settle the continuation re-reads the task: if it was deleted, archived, or `task.runId` no longer names this run, the freshly spawned agent is killed (`agent.kill()`, plus `dropSession` for claude-code) and the run is recorded `cancelled` — never registered.
A Stop pressed during that pending window is honored too: `cancelRun` finds no `active` handle, records the run in `pendingCancelRunIds`, and the spawn path consumes it right before it would register (`consumePendingCancel` — used by the codex/cursor/gemini/antigravity/opencode/copilot/fx one-shot spawns and the claude idle mint; the two bounded continuations do the same inline): the agent is killed, the run recorded `cancelled`, the task returned to `ready` with a status line, and the follow-up queue dropped exactly as on a failed spawn.
A Stop that lands even earlier, while a spawn holds the task's `startingTaskIds` claim but hasn't minted its run (codex's per-model CLI floor probe runs there), is recorded against the claim (`pendingCancelTaskIds`, via `cancelLiveRunOfTask`) and handed to the run the claim mints (`adoptPendingTaskCancel`, called by every claimed mint right after `task.runId` points at the run and before its `running` column event); `releaseStartingClaim` drops it when the claim ends without a run, and `isTaskRunCancelling` counts a current run carrying a pending cancel.
A spawn that settles inside the budget is byte-identical to before (no `pending` key).

**`POST /runs/:id/input` is bounded end to end** (`docs/plans/non-blocking-session-restore.md`, decision D) — the outer race is opt-in, `sendInput(runId, line, { bounded: true })`, passed ONLY by that route: internal callers (the pipeline handoff reminder, cursor plan approve, the ask-card fallback message) await the real outcome, because they act on `delivered` and the budget equals `PASTE_MODAL_GRACE_MS`, so every withheld claude paste would otherwise read `{ delivered: true, pending: true }` (claude's own idle-mint `pending` from `spawnResumedSession` is unchanged): only the `run not found` / `task not found` lookups answer synchronously;
everything after them — the codex CLI floor, the `archivedAt` clear (still after the floor, so a refused send never un-archives), `pendingTeardown`, the pipeline-step guard, the worktree restore, `@`-expansion, the argv re-check and the per-kind dispatch — runs as `sendInputInner`, raced against the same budget.
Past it the answer is `{ delivered: true, runId, pending: true }`, where `runId` is the run this message minted when the dispatch got that far (`pendingRunIdFor`: `task.runId` changed to a run created during this send), else the run it was addressed to; a late `delivered: false` re-stashes the RAW (pre-`@`-expansion) text into the task's backlog (`restashPasteWithheldText`, which now reports whether it stashed) and emits a live-only `send-failed` `GlobalEvent` (`{ taskId, reason, savedToBacklog }`, pipeline-parent stamped) that the webview toasts ("Message not sent", not gated on the open panel) and the TUI shows as one line; the CLI's `send` can't observe a late failure (its usage text says so).
Why: in the owner's packaged app a claude `--resume` launch took 5–31 s and the held request starved the webview's connection budget (see the connection budget in [run-panel.md](run-panel.md)).
`spawnClaudeViaTmux` additionally times its three pre-launch stages (`killTaskSession`, `ensureInstalledForCwd`, `tmux new-session`) and, past `SLOW_LAUNCH_WARN_MS` (5 s), emits one `status` line `session launch took Ns (kill … · settings … · tmux new-session …)` — before the `ready` line, and also when `tmux new-session` itself fails — plus a `console.warn` — the breadcrumb that names the slow stage.
History payloads are byte-budgeted as well as count-capped: the SSE replay (`EVENTS_REPLAY_LIMIT` = 800 events AND `EVENTS_REPLAY_MAX_BYTES` = 4 MB), `/tasks/:id/events/page` (`EVENTS_PAGE_MAX_BYTES` = 2 MB) and `/runs/:id/rebuild-events` **only when `?limit=` is passed** (the auto-rebuild on panel open; same 4 MB) — the no-limit path, used by the panel's manual "Rebuild from session JSONL" button and the CLI, deliberately returns the complete history, because it is the one way to see JSONL-only events the persisted rows lack and "Load earlier" pages the persisted rows, not the JSONL — each capped window keeping at least `MIN_REPLAY_EVENTS` = 20 events and never truncating a single event — `runs.eventsForTask({ limit, maxBytes, minEvents })` walks the newest-first id list accumulating `LENGTH(data)`; older history stays reachable through "Load earlier".

**The first load is additionally anchored to the last user message** (`docs/plans/first-load-reaches-last-user-message.md`): the SSE replay and the `?limit=` auto-rebuild both extend their window's floor back to the newest main-stream `user` event (`runs.lastUserEventId`, main stream = `subagent_id IS NULL`, any content
— a slash-command or `<local-command-stdout>` echo counts — except the hidden harness-stack continuation agetor sends after an account switch, which both the replay anchor and the rebuild route's anchor scan skip) whenever the span from it to the newest event fits BOTH `EVENTS_REPLAY_ANCHOR_MAX_EVENTS` (3000, deliberately = `EVENTS_WINDOW_MAX`, the webview's own flush-trim cap) and `EVENTS_REPLAY_ANCHOR_MAX_BYTES` (16 MB) — all-or-nothing via the pure `resolveAnchoredMinId` (`db.ts`), shared by `eventsForTask({ anchor })` and the rebuild route's in-memory slice, so over either ceiling the plain 800 / 4 MB window stands (2000 / 4 MB on the rebuild branch, whose `?limit=` is server-clamped at 2000 while the panel asks for `EVENTS_WINDOW_MAX`) and "Load earlier" pages as before;
`/tasks/:id/events/page` never anchors, `/tasks/:id/events?anchor=0` opts a client out (the TUI dashboard's `useCoalescedStream` passes it, since it keeps only 500 lines), `hasMore` still derives from the returned window (so it can stay true for breadcrumbs older than that user message), and the CLI's `agetor logs` inherits the anchored window through the same SSE route.

**A reconnect resumes forward** (`docs/plans/event-stream-forward-resume.md`): every saved row's frame on `/tasks/:id/events` carries an SSE `id:` line (= `run_events.id`, replayed and live alike — saved rows only; `interaction`, `interaction_resolved`, `subagent` lifecycle, ping and `replay_meta` never get one, and never an empty `id:`), and the route takes a cursor from `Last-Event-ID` or `?afterId=` — the first VALID of the two (`resolveResumeCursor` in `src/bun/event-resume.ts`: `/^[0-9]{1,16}$/` and a safe integer; anything else is ignored as if absent, never a 400, since `openEventStream` retries a 400 forever).
With a cursor, `runs.eventsForTaskAfter` reads `sqlite_sequence` and probes the ids of at most 801 rows of the task (index-only; their byte lengths are read only when the count fits — subagent rows included; counted in rows, never as an id difference — ids interleave across tasks) and the pure `decideForwardResume` answers all-or-nothing: the gap is sent only when it is ≤ 800 rows AND ≤ 4 MB (`replay_meta` `{earliestId: null, hasMore: false, resumedAfter: <cursor>}`, then just the gap); otherwise — or when the cursor is ahead of `sqlite_sequence` (another or a wiped database) — `snapshotRequired: true` with exactly the window and `earliestId`/`hasMore` a no-cursor connect with the same `?anchor` gets, on the same connection.
CORS allow-headers carry `last-event-id`.
The replay is a database read, so live frames keep arriving while it is in flight: the route subscribes first and holds them in a buffer. A saved row committed before the read is in the replay, and its live send may land in the buffer or after the drain. So a live frame whose id is at or below the last id the replay covered is dropped as a duplicate ONLY when the replay sent that very row with that very data (`replayedHashes`: id to data hash, one number per replayed row, so memory stays bounded by the replay window). OpenCode rewrites a `tool_use` row in place and re-broadcasts it under the same id with new data; that frame differs from what the replay sent, or sits at or below a resume cursor and was never replayed, so it goes through and the client replaces the row by id. Live-only frames (no id) always go through. A replay read that fails (the database worker restarting) ends the stream, and the client reconnects with its cursor. Pinned by `server-events-replay-dedup.test.ts`.

The cursor is only sound because a run's saved rows are sent in the order of their ids (send order = id order): every save-then-send site goes through `saveAndEmit` (`orchestrator.ts`), which rides the run's queue in `run-emit-queue.ts` (`appendAndEmit`: the call takes its place synchronously, inserts run one at a time per run, and each row is sent right after its own insert, with the `{id, ts}` it was stored with), or through `appendAndEmit` itself (the subagent watchers, the session imports, interactions), sends nothing on a `(run_id, line_uuid)` dedup hit, and the claude monitor sink stores the notification line's own time as the row `ts` so live and replayed copies agree — never send a saved row any other way.
With the database on its own thread (`docs/plans/non-blocking-core.md`), the run's queue is also what orders the orchestrator's other per-run writes:
- A driver's chunk callback stays synchronous: the chunk's row takes its queue slot at once (so the stored ids follow the order the chunks arrived), the in-memory sentinels (`sessionDied`, `unknownCommand`, `limitHit`) are set at once, and the database follow-up of the chunk (the unread watermark, todo/plan/sent-files tracking, the `blocked` column flips, the stall marks) runs on a per-run chain in arrival order.
- A session id a driver reports (`queueRunPatch`), a conditional status line whose condition needs a read (the fx dropped-steer line, `saveAndEmit`'s `onlyIf`) and a continuation run's row, column move and opening line (`startContinuationRun`, which answers claude-tmux synchronously) take their slot in the run's queue at the moment they happen.
- The done handler takes the run out of `active` as soon as `done` resolves, then waits for that chain and the run's queue (`runChunksSettled`) before it reads the run's state or writes its final status, so the final status never lands before the run's last event.
- Global lifecycle events (`emitGlobal`) are stamped with their pipeline parent by one read (`orchestrator.pipelineStamp`), so they go out through one ordered chain: subscribers see them in emission order; an event with nothing to look up (no per-task kind, an emitter-stamped title, or an `interaction` event of an ordinary task) goes out synchronously when nothing is waiting ahead of it. Async callers `await emitGlobal(...)`; tests flush with `__globalEventsSettledForTest`.
Four lines that used to be broadcast-only are saved rows now (`saveStatusLineQuietly`, which never throws on a settle path): the opening `started — …` breadcrumb, `background agents still running (N) — holding in running`, `exit:N` / `cancelled (exit:N)`, and the spawn-rejection `cancelled` / stderr `String(err)`; older runs aren't backfilled.
Clients keep the transport's last SSE id (sent back as `Last-Event-ID`) apart from the consumer's highest accepted id (`createIdHighWater`, `src/shared/task-stream-resume.ts`, drops any frame with an id at or below it, which also keeps an older core's full replay duplicate-free) and classify each `replay_meta` with `classifyReplayMeta`: the RunPanel resets on a snapshot (see "Things that will trip you up"), `agetor logs` never prints a row older than one it already printed and puts one dim `LOGS_STREAM_GAP_NOTICE` on stderr, and the TUI's `useCoalescedStream` clears its lines and shows a dim `TASK_STREAM_GAP_NOTICE` row.
Desktop cursors last only across reconnects of one live subscription (opening/switching a task or relaunching is a fresh connect).
Test seams: `AGETOR_TEST_DROP_STREAMS_ROUTE=1` registers a test-only `POST /test/drop-task-streams { taskId, holdMs? }` (desktop-only + conditional in `ROUTE_POLICY`; closes the task's open streams and holds new requests for that task's stream server-side for `holdMs`, 0–30000, so a reconnect resumes over a deterministic gap — `e2e/event-stream-resume.spec.ts`), and `FAKE_CLAUDE_DONE_REJECT_PROMPT_MARKER` (`__agetor_fake_claude_done_reject__`) makes the fake claude driver's `done` reject after its prompt echo, exercising the spawn-rejection settle path.
Test seam: `FAKE_CLAUDE_LONG_REPLY_PROMPT_MARKER` (`__agetor_fake_claude_long_reply__`, optional `:<count>` suffix, default 900 > `EVENTS_REPLAY_LIMIT`, clamped 1..5000) makes the fake claude driver emit that many `assistant` chunks.
Test seam: `AGETOR_FAKE_CLAUDE_SPAWN_DELAY_MS` delays the fake claude driver's SPAWN (unlike `AGETOR_FAKE_CLAUDE_RESOLVE_DELAY_MS`, which delays the turn's resolution).
`AGETOR_FAKE_CODEX_RESOLVE_DELAY_MS` (default 20 ms) is the codex-side counterpart: it holds a fake codex turn in flight so a test can queue follow-ups behind it and mutate the task before `drainCodexQueue` runs (`orchestrator-codex-queue-floor.test.ts`).
`AGETOR_FAKE_CLAUDE_TURN_MS` (default 20 ms) is the claude counterpart for the fake driver's generic turn: it holds the turn open so a test can fold a follow-up into it deterministically instead of racing the 20 ms timer (`orchestrator-paste-withheld.test.ts`).

- **The board poll leaves archived tasks on the server.** `GET /tasks` takes `archived=include|exclude|only` (absent means `include`, the original answer, so an older CLI or webview is unchanged; any other value is a 400) and `keep=<id>,<id>` (at most `TASK_LIST_KEEP_MAX`, 50), ids listed whatever their archive state. `tasks.list({ archived, keepIds })` filters in SQL, before the runs join and the row parse. `taskListPath` (`src/shared/types.ts`) builds the path for both clients. On a DB with ~2,900 archived tasks the full list was ~38 MB of rows per 2 s tick, and WKWebView parsing it pushed the webview to ~2.4 GB, enough for macOS to pause Agetor under swap pressure. The board does not re-send this list every tick any more: it asks for a delta over the same filter (see [Delta and push](#delta-and-push-the-boards-task-list)). Who asks for what:
  - The webview (`App.tsx`, `taskListOptsRef`, read by `refresh()`) fetches `exclude` (as a delta, with a cursor per filter) on the default *Active only* view and asks for the full list only while a view needs archived tasks: the *All* / *Archived only* views, the Worktrees dialog (an archived worktree links to its task) and onboarding until it is dismissed (its "task" and "run" steps count archived tasks; `loaded` waits on `tasksWithArchivedLoaded`, so the checklist never flashes those steps undone from the boot poll). Becoming needed fetches at once instead of waiting for the next refresh, drops the cursor (a delta describes one filter), and a response requested under the other mode is returned but not applied. The open task, the open pipeline run, the open diff and the context-menu task ride in `keep`, so archiving the open task (or opening an archived one, then switching back to *Active only*) never reads as the task vanishing, which would close its panel.
  - The TUI (`useTasks`) asks for the `exclude` delta; `agetor ls` asks for `exclude`, `only` (`--archived`) or `include` (`--all`) and keeps its client-side filter for an older core. `resolveTask`, Settings' "in use by" lookup and the notification fallback still fetch everything, once.
  - Tests: `src/bun/task-list-archived.test.ts` (SQL filter, parser, route, path builder), `src/cli/ls.test.ts`, `e2e/board-archived-poll.spec.ts`.
- **The Bun main thread is shared by every task, pipeline and panel** — a synchronous loop over a large table or many files in a spawn/restore path freezes all of them (`docs/plans/non-blocking-session-restore.md`). SQLite and transcript parsing are on worker threads now ([The worker core](#the-worker-core-no-sqlite-and-no-big-parse-on-the-main-thread)), but the rest of the work on the main thread, such as walking many results, building a large response or scanning files, still has to be cooperative.
  Long work must be a cooperative job (see the subagent watcher's `createSeedJob`/`createCycleJob` and `retention.ts`): step in ~20 ms slices, `await` a `setImmediate` yield between them. The watcher's passes are described under [The watcher passes](#the-watcher-passes).
  Consequence for the watcher: in production `handle.pump()` (and so `pumpWatcherForHoldCheck`) is a no-op until the first cycle has finished (~0.6 s + replay after an attach); in `manual` test mode the seed runs synchronously at attach and the first `pump()` drains the first cycle, so the manual-mode tests drive it exactly as before.
- **A database worker crash is a 503, not a 500.** A route whose database call rejects with `DbRestartingError` (the worker crashed or exited and is restarting; `db-rpc.ts`) answers 503 `{error: "database restarting", code: "db-restarting"}`, with `Retry-After: 1` on GET and HEAD only (a write's outcome is unknown, so any other method gets no invitation to retry); `DbUnavailableError` (closed, failed to open, or restarted more than 5 times a minute) answers 503 `{error: "database unavailable", code: "db-unavailable"}`. The mapping lives once, in `applyRoutePolicy`'s handler wrapper (`runHandler`, `route-policy.ts`), so every route gets it; a handler that catches every error to answer its own 4xx/5xx rethrows these first (`isDbWorkerError`). Nothing retries: the failed call's outcome is unknown. `/health`, `/info` and headless `/daemon/shutdown` touch no database and keep answering. Pinned by `src/bun/route-db-errors.test.ts` (the wrapper, and the real server over a worker that crashes on every request).
- **Event-loop-lag monitor** (`src/bun/event-loop-lag.ts`, started by `index.ts`/`headless.ts` with a 100 ms sampler BEFORE the boot restore — ahead of `ensureDisclaimedServer()`/`reconcileOrphans()`, so the boot-time `reattach session`/`boot reattach` labels are sampled; `.unref()`'d): one `console.warn("[agetor] core was unresponsive for N.N s during <label|idle> {json}")` per stall ≥ 1 s, labelled or not (teed into `core.log`; see [core.log](#corelog)), attributed to the `beginLagLabel(label, { taskId, runId })` that overlapped it
  — among near-equal overlaps the most recently BEGUN label wins (not the deepest: labels span `await`s and interleave across tasks, so stack depth isn't nesting) (labels today, and their scope, are under [Event-loop-lag label scope](#event-loop-lag-label-scope): the subagent-watcher attach, `reattach session`, `boot reattach`, `archived-history retention`, `compact database` (only in in-process mode, `AGETOR_DB_MODE=inprocess` or tests: in worker mode the VACUUM runs on the database worker), and the context-free `native file dialog` that `server.ts`'s `openFileDialogLabelled` brackets every Electrobun `openFileDialog` with
  — a synchronous FFI call that blocks the main thread while the panel is up); when the label carries a run, the orchestrator's sink also appends `core was unresponsive for N.N s during <label>` as a status line on that run.
  Off under `bun test` (`NODE_ENV=test`) unless `AGETOR_LAG_MONITOR=1`; `AGETOR_LAG_MONITOR=0` disables it anywhere.
  **Where the lines go.** The packaged desktop app's launcher points the core's stdout/stderr at /dev/null, so `index.ts` installs `core-log-boot.ts` right after `channel-defaults.ts` (and `headless.ts` calls `installCoreLog()` at boot): every `console.log/info/warn/error/debug` line is still printed and is also queued for `<dataDir>/logs/core.log` ([core.log](#corelog)). To find stalls: `grep unresponsive ~/.agetor/logs/core.log`.
- **Busy banner** (`src/mainview/lib/core-busy.ts` + `components/CoreBusyBanner.tsx`): `j()` registers every request; once one has been pending > 3 s the watchdog probes the unauthenticated `/health` (1.5 s abort) every 2 s, and two consecutive probes with no answer (`FAILED_PROBES_TO_SHOW` — one miss alone can be the probe queueing behind the very requests it watches in WKWebView's ~6-connection pool) show the app-level "Agetor is busy — waiting for the core…" strip (`core-busy-banner`) until a probe answers or everything settles.

## Delta and push (the board's task list)

An idle board refresh costs one indexed lookup, and a change reaches it in about a quarter of a second (`docs/plans/non-blocking-core.md` §3, T12/T14b). Plain `GET /tasks` is unchanged; `?delta=1` opts in.

- **Revision log (migration 093).** `task_revs` holds one row per task (`rev`, `deleted`), `task_rev_meta` the database `epoch` and the monotonic `rev`. SQLite triggers bump them on every insert, update (any column, server-managed ones included) and delete of `tasks`, and on insert or `status` change of `runs` and `subagents`. No writer can forget; `updated_at` is never touched.
- **`tasks.changedSince` (db-core op, `db-core/ops/delta-ops.ts`).** Reads `task_rev_meta.rev` and the changed rows in ONE deferred read transaction, so the rows and the rev it reports are one snapshot: a write landing afterwards has a higher rev and is in the next delta (`rev > since`), never skipped. The range scan `SELECT … FROM task_revs WHERE rev > ? AND rev <= ?` SEARCHes `idx_task_revs_rev` (pinned by `task-list-delta.test.ts`). A changed row that no longer passes the `archived`/`keep` filter, or is a tombstone, is reported in `removedIds`. No cursor, another epoch, or a cursor ahead of the database: a full snapshot (`tasks.list` itself) with `removedIds: []`.
- **`GET /tasks?delta=1[&since=<cursor>]`** answers `{format: "delta", cursor, snapshot, tasks, removedIds, decorations}` (`TaskDelta`, `shared/types.ts`; route in `task-delta-route.ts`, same route and `ROUTE_POLICY` entry, no `pathParams`). Rows go through the same `toTaskListRow` as the legacy list (trimmed `pipelineRun`, `runningSubagents`, `stalledSince`), and `pendingInteractionCount`/`openTerminalCount` are the live registry counts (a pipeline parent folds its steps' pending counts from the whole step -> parent map, not only the rows in the answer). A malformed, foreign, future or too-old `since` is a snapshot, never an error. The cursor is opaque: `<dbEpoch>-<bootId>:<rev>:<decRev>`. It describes ONE `archived`/`keep` filter, so a client forgets it when its view changes. A bare-array answer means an older core ignored `delta=1`: treat it as a full list (`isTaskDelta`).
- **Decorations.** Open terminals, pending interaction cards and the stall mark live in main-thread memory, so `task_revs` cannot see them. `terminals.ts` (open, close, exit), `stall-registry.ts` (mark, clear) and `interactions.ts` (`noteCardRegistered`, `fanoutResolved`: every register and every answer/cancel/teardown passes one of them) call `noteDecorationChanged(taskId, pipelineParentId?)` (`task-decoration-rev.ts`). That bumps an in-memory decoration rev, remembers which task moved at which rev (bounded to 2,000 tasks; a cursor older than the pruned window snapshots) and announces on `task-change-bus`. The decoration rev is the third part of the cursor, and the per-process `bootId` is part of its epoch: the counter dies with the process, so a cursor from before a restart snapshots. The decoration rev is read BEFORE the database read, so a change landing in between is delivered again by the next delta (redundant, never lost). A delta's `decorations` is sparse: the tasks whose in-memory decoration moved since the cursor (`pendingInteractions`, `openTerminals`, `stalledSince`; an explicit `0`/`null` clears), and on a snapshot every task with a non-default decoration. `runningSubagents` rides the changed ROWS (subagent status is a database trigger), not the sparse map.
- **Merge helper.** `src/shared/task-delta.ts` `applyTaskDelta(prev, delta, {cache?})` is the one implementation the webview and the TUI use: unchanged rows keep their object (the array too, when nothing changed), `removedIds` drop, new rows land in `createdAt` order, decorations overlay, a snapshot replaces. Contract at the top of that file.
- **Push.** `task-change-push.ts` subscribes to `task-change-bus` (a worker reply whose rev moved, or a decoration change) from `index.ts` and `headless.ts` once the boot gate opens, and publishes `{kind: "tasks-changed", cursor, ts}` on the EXISTING global stream (`GET /events`, no new connection). Throttled: the first change after a quiet 250 ms goes out at once, changes inside the window collapse into one trailing event, so at most one per 250 ms. An emit does no database read: the epoch is cached at boot, the rev is the worker reply piggyback. A failed emit (epoch read during a database restart) is dropped and the next change emits again. The event carries no task data; a client fetches `?delta=1&since=<its cursor>` on receipt and keeps a slow safety poll.
- **Clients.** The webview's `lib/task-delta-client.ts` keeps the cursor and the filter key (`archived` plus the sorted `keep` set) beside the server-truth list. It never overlaps two fetches (one queued re-run is shared), calls `notify(cursor)` on a `tasks-changed` event (an equal cursor is skipped), drops the cursor and discards a stale answer when the filter changes, and merges a legacy bare array as a full list. The filter key counts a kept id only when it needs keeping (archived, or not in the held list): opening, closing or right-clicking an ACTIVE task in the Active view keeps the cursor (the request still carries the full `keep`, so the server's answer is the same). A filter-key change (a view switch, or a kept task that is archived or closed) fetches at once through `filterChanged()`, coalesced with any fetch in flight, so a view switch never waits for the safety poll. Every 5 minutes (`TASK_FULL_RESYNC_MS`, measured from the last snapshot) the next fetch of any kind, push or poll, drops the cursor and takes a full snapshot, so a revision or decoration the delta path missed heals within that bound; the merge keeps row identity, so the resync does not repaint. A rejected fetch never leaves the queued follow-up stuck. The archived-toast sweep covers every archived row the held list contains on each apply (an in-memory walk), as the old per-poll sweep did. Its safety-net poll is `TASK_POLL_CONNECTED_MS` = 15 s while the global stream is connected and `TASK_POLL_DISCONNECTED_MS` = 2 s while it is down; a reconnect makes one catch-up fetch. Ids missing after an apply (a delta's `removedIds` included) close the panel and dismiss toasts as the full list did, and a first fetch never sweeps. The TUI (`cli/tui/task-feed.ts`, used by `useTasks`) does the same 5-minute full resync (`TASK_FEED_FULL_RESYNC_MS`, injectable clock) and keeps its 1.5 s poll, which is now one indexed lookup, and the dashboard forwards `tasks-changed` from its existing global stream.

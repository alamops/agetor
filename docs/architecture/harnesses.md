# Harnesses: command shape, defaults, speed tiers, env overrides, adding a new kind

> Moved from `CLAUDE.md`, where this was the “Agent command shape” section minus its per-kind bullets, plus the “To add a new agent kind” checklist. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

`src/bun/agents.ts` is the single source of truth for how each agent is invoked.
`buildCommand(agent, prompt, { mode, model, effort })` returns the launch argv and any env additions; `spawnAgent(...)` then dispatches:

Each kind's driver has its own doc: [claude-code](harness-claude-code.md), [codex](harness-codex.md), [cursor](harness-cursor.md), [gemini](harness-gemini.md), [fx](harness-fx.md), [antigravity](harness-antigravity.md), [copilot](harness-copilot.md), [opencode](harness-opencode.md).

**opencode is the one kind with two drivers** (`opencodeTransportFor`, `src/shared/opencode.ts`): OpenCode 2.x takes an agetor-owned `opencode serve` per harness, hosted in tmux and driven over HTTP and SSE (`opencode-driver.ts`, which is how a follow-up can steer a running turn and how permission and question cards work), and OpenCode 1.x, or `AGETOR_OPENCODE_TRANSPORT=run`, takes the tmux one-shot `opencode run` driver (`opencode-tmux.ts`). Its modes are Auto, Ask and Plan. A new driver for another kind that also talks to a long-lived local server should copy the server manager's secret handling (an agetor-generated password kept out of argv, a 0600 state file read no-follow) rather than inventing its own; see [harness-opencode.md](harness-opencode.md) and [security.md](security.md).

**Auto-enable built-in harnesses once their CLI is installed** (`src/bun/harness-auto-enable.ts`, `AUTO_ENABLE_KINDS` = codex, cursor, gemini, fx, opencode; claude-code, antigravity and copilot already ship `enabled = 1`): `GET /harnesses` (after `checkAllHarnesses()`, before listing rows) and a boot pass in `index.ts`/`headless.ts` call `applyHarnessAutoEnable(statuses)`, which, for each **built-in** row (`isBuiltin && row.kind === status.kind` — an additional-account harness is never touched) whose status is `available` and that has no `harness_auto_enabled` record, records it and — if it was off — turns it on (`harnesses.setEnabled`) and fires `refreshHarnessModels`.
The record is what makes a **manual Off stick**: a recorded id is never acted on again, and a row that was already on is recorded silently (no toast); an unavailable CLI is left unrecorded so it turns on whenever it shows up.
The one-time `harnesses_auto_enabled` AppEvent (`{ harnessIds, labels, ts }`) is broadcast to `/app/events` subscribers, held (`notified = 0`) until a client is connected and flushed by `flushPendingHarnessAutoEnableNotice` on subscribe; the webview toasts "Turned on … because they're installed — turn them off in Settings".
Everything in the module is synchronous so concurrent callers cannot double-enable or double-toast.

**Off under `NODE_ENV=test` unless `AGETOR_HARNESS_AUTO_ENABLE=1`; `=0` disables it anywhere** — the seam exists so tests that stub `AGETOR_CODEX_BIN=/bin/echo` never silently flip codex on; the headless e2e backend is not under `NODE_ENV=test`, so `e2e/fixtures.ts` sets `AGETOR_HARNESS_AUTO_ENABLE=0` for the same reason.

**Session ids are scoped to the harness that created them** (`findLastSessionIdForHarness(taskId, column, harnessId)` in `orchestrator.ts`, built on `runs.sessionIdsForTask`; the six per-kind `findLast*SessionId` functions it replaced are gone — D-15): every resume — claude-code (live send, continuation, respawn, idle reaper), codex, cursor, gemini, antigravity, fx (`spawnFxRun`), opencode and copilot (`resolveCopilotResume`, whose `findLastCopilotSessionId(taskId, harnessId)` applies the same harness filter) — asks for the newest session id of **its own column on a run whose `agent` resolves (through `resolveHarness`, so a legacy bare-kind row matches that kind's built-in id) to the task's current harness**, so switching a task to a second account of the same kind starts fresh instead of resuming an id the other account's data dir doesn't hold, and switching back resumes the original.
`latestResumableFxPause` applies the same gate, so `resumeFxRecovery`, `noteFxRunSettled` and the auto-resume re-arm ignore a pause that belongs to a different harness.
It iterates across runs, not just the latest, because a row may not have had its harness id stamped.

Defaults preserve hands-off behavior: `null` `task.mode` resolves through `defaultModeFor(kind)` (`AGENT_OPTIONS[kind].modes[0]`) — `auto` for claude-code (`--permission-mode auto`; `--dangerously-skip-permissions` is its `bypass` mode), codex (`--sandbox workspace-write`), cursor (`--force`), gemini (`--yolo`), copilot (`--allow-all` + `COPILOT_ALLOW_ALL=true`) and opencode (`--auto` on `opencode run`; on the server driver the Build agent with every approval answered `once`), and `yolo` (`FX_PERMISSION_MODE=yolo`, Full access) for fx
— **except fx is the one exception to "hands-off"**: its `auto` surfaces an interactive permission card and blocks the turn until answered (see [harness-fx.md](harness-fx.md)), so `yolo` (labelled **Full access** in the picker), not `auto`, is fx's actual hands-off mode — and, since fx's default reviewer (`openai/gpt-5.6-luna`, overridable only via fx's own `FX_REVIEW_MODEL` env var) 403s on standard-plan accounts, holding every tool call under `auto` and forcing extra replan requests that hit the free-tier rate limit sooner, `AGENT_OPTIONS.fx.modes` is now ordered `yolo` ("Full access") first: every picker default (`initialMode` in `NewTaskForm` and `TaskLaunchPickers` (both delegating to `defaultModeFor`), the New Task form, the task-launch dialogs, `agetor add` (both its interactive picker and a scripted add without `--mode`, which seeds the kind's `modes[0]`), and the mode reset when switching a task INTO fx) and `CODE_PLAN_MODE.fx.code` resolve to `yolo`, with `auto`/`ask` staying explicit choices;
every spawn branch in `buildCommand`/`spawnAgent`, `reconcileTaskSession`, `agetor add`, RunPanel's `onAgentChange` and its null-mode dropdown fallback all resolve a **stored** `null` mode through one `defaultModeFor(kind)` = `AGENT_OPTIONS[kind].modes[0]?.id ?? "auto"` — `auto` for every kind but fx, `yolo` (Full access) for fx
— so a null-mode fx row now spawns and displays as Full access (owner decision, superseding the earlier no-escalation rule; `createTask` still stores `null`).
`null` `task.model` similarly defaults rather than crashes: every orchestrator spawn seam resolves it to `DEFAULT_MODEL[harness.kind]` before calling `buildCommand` (`task.model ?? DEFAULT_MODEL[harness.kind]`) — `buildCommand` itself still throws `"model is required for <kind>"` as a defensive check if that resolution is ever skipped — which used to be the routine path for every kind before the fallback landed and would strand the just-inserted run row in `running`, but no longer does: `spawnAgentOrFail` (orchestrator.ts) wraps `spawnAgent` at all six of its call sites and catches a synchronous spawn-time throw (this one included), recording the run `failed` and returning the task to `ready` instead of leaving it stuck — the same recovery already applied uniformly across every agent kind.
Unknown mode/model ids are passed through verbatim so unreleased options "just work" without code changes.
`task.speed` is never null: `createTask` stores a selected profile's speed, else a valid `input.speed`, else `off`, and the agent-switch reset sets it back to `off`.

**Speed tiers** (`Speed` = `off | fast | ultrafast` in `src/shared/types.ts`, replacing the cursor-only boolean `fast`; `docs/plans/fx-0.0.14-and-cursor-updates.md`): `supportedSpeeds(kind, model, effort, option?)` (`src/shared/speed.ts`) offers cursor `["off", "fast"]` when `cursorModelSupportsFast(model, effort)` (Fast is a model variant `cursorModelArg` composes into the model value `cursor-acp.ts` sends through ACP `session/set_config_option`, not an argv `--model` flag), fx `off` plus whichever of `fast`/`ultrafast` the discovered model option flags (discovery only — [harness-fx.md](harness-fx.md)'s `applyFxSpeed` applies them over ACP), and every other kind `["off"]` only.
One `SpeedPicker` segmented group renders it (`launch-speed` in `TaskLaunchPickers`, `new-task-speed` in `NewTaskForm`, `task-speed` in RunPanel's task details, locked by a bound profile like the effort select): it renders nothing when Off is the only option and the value is off, a stored tier the model doesn't offer shows as a disabled "Fast (not offered)"/"Ultrafast (not offered)" segment, and Ultrafast's hint says it costs more per token than Fast.
Cursor clears to Off when the model/effort loses its Fast variant; fx resets to Off only on a user model change whose known tiers exclude the value, never on load (discovery may not be ready).
NewTaskForm remembers the last pick per kind as the `lastSpeed:<kind>` preference.
CLI: `--speed <off|fast|ultrafast>` on `agetor add`/`edit`/`profile add`/`profile edit`, with `--fast`/`--no-fast` as aliases (the later flag wins).

The curated lists shown in the UI live in **`AGENT_OPTIONS`** in `src/shared/types.ts`.
To add a model or mode: extend the relevant `AgentOptions.models` / `AgentOptions.modes` array, then teach `buildCommand` how to translate it (or rely on the verbatim passthrough).
The webview picks it up on next load.

The per-agent env overrides (`AGETOR_<KIND>_BIN` / `AGETOR_<KIND>_ARGS`, `AGETOR_TMUX_BIN`, `AGETOR_HARNESS_AUTO_ENABLE`, `AGETOR_SKIP_CLI_VERSION_FLOOR`, and the always-on-host and headless-notification switches), the stub binaries tests plant for each CLI, and the fake drivers (`AGETOR_<KIND>_DRIVER=fake`) are listed once, in [CLAUDE.md § Agent kinds at a glance](../../CLAUDE.md#agent-kinds-at-a-glance).

## Adding a new agent kind

**To add a new agent kind**, extending the `AgentKind` union is only the start: the compiler flags every `Record<AgentKind, …>` and `never`-checked switch, but several sites are plain `if`/ternary chains or string whitelists it cannot see, and the old advice ("the orchestrator and UI pick it up automatically") shipped silent codex/fx fallthroughs.
Walk this list (derived from the copilot change; `git diff c5cf1a2 --stat` shows the whole footprint) and grep an existing kind (`antigravity` for a tmux one-shot, `copilot` and `opencode` for the newest) across `src/` and `e2e/` to catch the rest (`docs/plans/add-opencode-harness.md` §2a/§2b is the inventory that was walked for opencode):

1. **`src/shared/types.ts`** — the `AgentKind` union; `AGENT_OPTIONS` (models, modes with honest hint copy, efforts); `DEFAULT_MODEL`; `DEFAULT_EFFORT`; `MODEL_EFFORT_SUPPORT`; `MODEL_MODE_DENY`; `CODE_PLAN_MODE`; `MODEL_MIN_CLI_VERSION` (when models need a newer CLI); an optional `Run.<kind>SessionId`; the `Harness.home` doc bullet and `HARNESS_TEMPLATES` entry for a multi-account kind; and a decision on `CATALOG_SCOPED_KINDS` (account-scoped catalogs only), `MODEL_DEFAULT_EFFORT_KINDS` (a "Model default" effort row) and `USAGE_SUPPORTED_KINDS`.
   The tests that iterate every kind (`types.test.ts`, `agents.test.ts`, `agent-profiles.test.ts`, `effort-support.test.ts`, `speed.test.ts`) then hold the new kind to the invariants.
2. **A migration** (`src/bun/migrations/NNN_*.sql` + the `migrations/index.ts` entry + the `migrate.test.ts` "last migration" pin): rebuild `harnesses` with the widened `kind` CHECK (copy EVERY column by name — a forgotten one is silent data loss; `profile_mcp_servers` (073) is the one a 061-style copy predates — and keep the union of kinds other in-flight branches add), seed the built-in row (decide enabled/disabled on purpose), self-heal the other built-ins with `INSERT OR IGNORE`, and `ALTER TABLE runs ADD COLUMN <kind>_session_id`.
   Never edit an applied migration; renumber with `aliases` when a concurrent branch took the number.
3. **`src/bun/db.ts`** — `harnesses.getByIdOrKind` (the synthetic built-in), the `harnesses.insert` kind whitelist, and the `RunRow` / `toRun` / `runs.insert` / `runs.update` session-id column mapping (plus `SESSION_ID_COLUMNS`); a driver that owns subagent rows also needs a run-scoped settle (`subagents.settleRunningForRun`).
4. **`src/bun/agents.ts`** — `resolveBin`, `harnessEnv` (the home-override env var; compile-time `never` check but no runtime throw), `buildCommand`, `spawnAgent` and `SpawnAgentArgs`.
   `buildCommand`/`spawnAgent` throw on an unknown kind and codex is the explicit last branch, so keep new branches ABOVE it; the fake-driver seam (`AGETOR_<KIND>_DRIVER=fake`) and the `AGETOR_<KIND>_BIN/ARGS` overrides live here too.
   The driver itself is its own file (`<kind>-tmux.ts`, or `fx-acp.ts` for a no-tmux protocol) exporting a spawn, a reattach (one-shot kinds only while a turn is in flight), a "session active" check and a drop.
5. **`src/bun/agent-status.ts`** — `INSTALL_HINTS`, `BREW_PACKAGES` (use `--cask …` for a cask) and `upgradeHintFor`; `checkHarness` needs an identity gate when another program shares the binary name (fx, copilot); a `loggedIn` probe only when a cheap passive one exists.
6. **`src/bun/agent-discovery.ts`** — a `discover<Kind>`, an entry in `runRefresh`'s probe list AND its index-aligned `kinds` array, the `runRefreshKind` switch case, and the `__testing` exports; `HarnessTarget.kind`; `model-discovery.ts` (`PER_HARNESS_KINDS`) only for account-scoped catalogs.
7. **`src/bun/orchestrator.ts`** — `sessionIdPatchFor` (exhaustive; never extend a ternary), the `reconcileOrphans` SELECT / session-id key chain / reattach kind gate / reattach call, the `startTask` spawn args, the follow-up path (`sendInput` dispatch, the early CLI-floor gate, a per-task turn queue with drain from `attachDoneHandler`), agent-switch / archive / delete `drop<Kind>Session`, queue clears on switch, archive and delete, plan detection and the subagent sink when the kind has them, `findLastSessionIdForHarness` for the resume id (session ids are scoped to the harness that created them), and `minCliVersionError` when models carry floors.
   The background-agent hold (`isTaskHeldByBackgroundAgents`) keys on `subagents.hasRunning` for EVERY kind, so a driver that records subagent rows must settle them before the turn ends.
8. **`src/bun/server.ts`** — the `POST /harnesses` kind whitelist and its error copy, both `/agent-models` maps, and (plan-capable kinds) `planKindGuard` plus the approve-route branch.
9. **Capability discovery** — `src/bun/commands.ts` (skills, MCP and any new extension kind; user roots and project roots), `src/bun/ref-tree.ts` (`DEFAULT_PATHSPECS`, and `CAPABILITY_READ_PATTERNS` in `commands.ts`, so the discovery works at a git ref), `src/bun/bundle.ts` (`userLevelSkills`).
10. **CLI** — `src/cli/commands/harness.ts` (the `agetor harness shell` login hint); `agetor add` / `edit` / `profile` pickers read `AGENT_OPTIONS`, so verify rather than edit.
11. **Webview** — `AgentIcon.tsx`, `SettingsDialog.tsx` (`isExperimentalKind`, `HARNESS_HOME_COPY`, the add-harness kind list), `OnboardingChecklist.tsx` (`LOGIN_COMMAND`), the `AgentModelMap` literals in `App.tsx`, `TaskLaunchPickers.tsx` and `lib/api.ts`, `NewTaskForm.tsx` (per-kind seed and the Plan-button title), RunPanel / PlanDialog gating for usage chips (the usage-chip scan in `RunPanel.tsx`) and plan cards, and `e2e/fixtures.ts` (stub binary + env).
12. **Tests and docs** — a driver unit test (mapper table, shell wrapper, settle/cancel/reattach through the tmux test seam), an `agents-<kind>.test.ts` (argv per mode × effort × resume, env, exhaustive throws), status/discovery and orchestrator integration tests (fake driver, `mkdtemp` data dir, `rmTestDataDir`), an e2e spec behind an opt-in stub in `e2e/fixtures.ts` (so existing specs keep seeing the kind as not installed), and an opt-in real-binary test;
    `src/bun/agents.test.ts`'s placeholder-model guard forbids the bare model id `"default"`, a kind that mutates harness rows in tests must restore them (`snapshotHarnessState()`, see [persistence.md](persistence.md)), and any hand-built `Task`/`AgentProfile` fixture needs the new field when a required one is added; then a new `docs/architecture/harness-<kind>.md` with its row in the [Topic map](../../CLAUDE.md#topic-map), the kind's row in the table and the env-override and fake-driver list of [CLAUDE.md § Agent kinds at a glance](../../CLAUDE.md#agent-kinds-at-a-glance), and `README.md` (harness table, mermaid diagram, env table, "Adding a harness").

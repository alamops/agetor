# Harness: copilot

> Moved from `CLAUDE.md`, where this was the `copilot` bullet of “Agent command shape”. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

**`copilot`** → driven through `src/bun/copilot-tmux.ts` (GitHub Copilot CLI, binary `copilot`; `docs/plans/github-copilot-harness.md`, grill and investigation beside it).
A near-clone of the antigravity driver with codex's stdin prompt delivery and gemini's self-issued session id.
Each turn is a one-shot `copilot --output-format json --no-color --no-ask-user --session-id <uuid> --model <id> [--reasoning-effort <effort>] --mode interactive|plan [--allow-all] --usage-output-file <dataDir>/copilot-logs/<runId>.usage.json [...AGETOR_COPILOT_ARGS]`, hosted inside a detached per-task tmux session (`-x 200 -y 50`) so a mid-turn run survives an agetor restart.

**Prompt on stdin, guards in the pane's shell**: `buildCopilotShellCommand` (pure, exported) produces `sh -c '<guards> "$@" < <promptfile> > <runlog> 2>&1; echo $? > <exitfile>' sh <argv…>` — argv travels as positional parameters, so the prompt never enters shell text and has no argv-size cap.
The guards run in the pane BEFORE the binary, against the pane's real env (the long-lived tmux server's env may belong to another process): for each of `GH_TOKEN` / `GITHUB_TOKEN` that the harness env map does not set, `case "${V-}" in ghp_*) unset V;; esac;` (Copilot rejects a classic PAT and it would override the user's keychain login; a `gho_`/`github_pat_` token still overrides the login, as Copilot documents), and in every mode except Auto `unset COPILOT_ALLOW_ALL` unless the harness env sets it (`shouldUnsetAllowAll`; an ambient export would otherwise turn Read-only into allow-all, and failing closed is defense in depth against a foreign mode id such as fx's `yolo` — a cross-kind `PATCH` resets the mode, but a write path that bypasses it, or a Start racing the reset, would otherwise reach the spawn).

**Home**: `COPILOT_HOME` is ALWAYS pinned on every spawn by `buildCommand` via `copilotHome({harnessHome, harnessEnv})` (`src/bun/copilot-home.ts`, shared by `buildCommand`, the driver's plan-file reader, capability discovery and the orchestrator's session-dir check so they cannot disagree) — precedence: the harness env map's `COPILOT_HOME`, then `harness.home`, then the agetor process's `COPILOT_HOME`, then `<HOME>/.copilot` (the `pinClaudeConfigDir` precedent), where `<HOME>` — also the base a leading `~` expands against — is the harness env map's `HOME` when it sets one, else the process home.
Copilot has no XDG lookup for this dir (its docs name `~/.copilot` and `COPILOT_HOME` only, and migrate older XDG locations into `~/.copilot`), so `XDG_CONFIG_HOME` is ignored.
`harnessEnv` maps `harness.home` to `COPILOT_HOME` (a dedicated override, so an additional account needs no `HOME` override); the "Additional GitHub Copilot" template (`copilot-additional`, `copilot-2`, `{dataDir}/harnesses/copilot-2`) sets it and its help text says to sign in with `COPILOT_HOME=<path> copilot login`.
That a separate `COPILOT_HOME` isolates a second LOGIN (the keychain entry may be per host+user) is unverified without a second account — if the live smoke shows otherwise, reword the template to set `COPILOT_GITHUB_TOKEN` in the harness env.

**Modes**: `auto` ("Auto") → `--allow-all` plus `COPILOT_ALLOW_ALL=true` in the env (exact value; it also trusts the worktree and works with `--session-id`, whereas `--trust-folder` refuses `--session-id` and is never used; a value the harness env sets wins in every mode); `plan` → `--mode plan` (Copilot writes `$COPILOT_HOME/session-state/<id>/plan.md`); `ask` ("Read-only") → no allow flags at all.
`--mode` is passed on EVERY turn (`plan` for Plan, `interactive` otherwise) because plan mode is sticky across resumes, so a task switched Plan → Auto stops planning on its next turn.

**Read-only is not enforcing**: without allow flags Copilot still auto-approves read-only shell commands (e.g.
`echo`) and silently denies only file edits and commands that change files (tool results come back `isError` "Permission denied…"), and the turn still exits 0, so the run can read `succeeded` — the picker copy says so, and repo MCP servers and hooks stay off in that mode (untrusted folder), while Auto trusts the worktree, so its MCP servers and hooks load and a hanging MCP server stalls the turn (it shows as "Agent is working…" and Stop works).
`CODE_PLAN_MODE.copilot = {code: "auto", plan: "plan"}`, `MODEL_MODE_DENY.copilot = {}`.
**Multi-repository tasks** ([multi-repo-tasks.md](multi-repo-tasks.md)): the turn runs at the task's non-git workspace root and gets each repository checkout that exists at spawn time as `--add-dir <checkout>` (`withTaskRepositoryRoots`). No copilot-specific escalation is needed or added, unlike codex's sandbox: Auto's `--allow-all` plus `COPILOT_ALLOW_ALL=true` already grants full access, including the writes `git commit` makes under each source repository's `.git/worktrees/<id>`, and Read-only and Plan deny writes by design, as for a single-repository task. Copilot CLI 1.0.109's own `--help` (and GitHub's CLI command reference) confirms it: `--allow-all` is equivalent to `--allow-all-tools --allow-all-paths --allow-all-urls`, and `--allow-all-paths` disables file path verification, so those `.git` writes outside the workspace and every `--add-dir` are allowed. Not run live (no GitHub Copilot login on the machine used for the multi-repository live smoke); the opt-in real-binary test below has a multi-repo case (source repositories outside the workspace, `--disallow-temp-dir` so only `--allow-all-paths` can admit the commit; Auto must commit, Read-only must be denied), added and pending a run (`docs/plans/multi-repo-tasks-smoke.md`, "Post-round-15 verification").

**Model and effort**: default model `auto` (`DEFAULT_MODEL.copilot`, Copilot's own router: every plan, a 10% credit discount, never an org-disabled model — copilot joins fx as an exemption from "default to the best model" because both bill per credit); when the task asked for `auto`, the first main-stream `assistant.message.model` yields one status line `GitHub Copilot auto picked <model>` per run.
The curated `AGENT_OPTIONS.copilot.models` are `auto` plus 13 rows (Claude Opus/Sonnet/Haiku 5.5, Fable 5.1, GPT-6.1 Sol, GPT-6 Astra/Luna/Sol, Gemini 4 Argon, Gemini 3.8 Flash, Grok 4.7, Kimi K3, MAI Code 1.1 Flash).
Effort is `DEFAULT_EFFORT.copilot = "auto"` ("Model default"): `auto` or null OMITS `--reasoning-effort`, any other id is passed through.
`MODEL_EFFORT_SUPPORT.copilot` has no `ultra` (Copilot's flag accepts none…max only) and every row ends in `auto`; claude rows borrow claude-code's set, `gpt-6.1-sol`/`gpt-6-astra` codex's minus `ultra`, gemini/grok/kimi rows fx's, and the Copilot-only ids (`auto`, `mai-code-1.1-flash`) get the full ladder.
`auto` stays a legal discovered effort only for `MODEL_DEFAULT_EFFORT_KINDS` = {fx, opencode, copilot} (`supportedEfforts` drops it for every other kind).
An effort a model doesn't accept is reported and ignored by Copilot rather than failing the run, so the mapper surfaces it as a status line (below).
Speed is always `off`.

**Tailing and mapping**: the tailer is `fs.watch` + a 150 ms poll over `dataDir/copilot-logs/<runId>.jsonl` plus the shared death probe (a vanished session emits `SESSION_DIED_STATUS_PREFIX` + `GitHub Copilot session vanished mid-turn`); `mapCopilotEvent(line, lineIndex, ctx)` is pure apart from `ctx` and the subagent sink: `assistant.message` → `assistant` (and a `thinking` chunk first from its `reasoningText` when no `assistant.reasoning` preceded it that turn), `assistant.reasoning` → `thinking` (verified to reach stdout on 1.0.104), `tool.execution_start`/`_complete` → `tool_use`/`tool_result` (an MCP call is named `<server> · <tool>`), `session.error` → `⚠ GitHub Copilot: <message> — <remediation>`, `session.warning` → `⚠ <message>`, `assistant.turn_retry` and retry/effort-flavoured `session.info` → one `↻ …` / `ℹ …` line per distinct text, `session.compaction_start`/`_complete` → `context compacting…` / `context compacted`, `abort` → `turn aborted`, `exit_plan_mode.requested` (ephemeral but handled) → stashes `planContent`;
`user.message`, every other ephemeral delta and unknown types are ignored (the CLI ships near-daily, so the mapper must keep tolerating new types).
A non-JSON line → `stderr`.
Line uuid is `copilot:<event id>` (`:model` / `:thinking` suffixes for derived chunks), so the offset-0 reattach replay dedupes; the fallbacks for an id-less event and a non-JSON line, `copilot:line:<runId>:<n>` and `copilot:raw:<runId>:<n>`, carry the run id because reattach seeds a TASK-wide seen-uuid set and a bare line index would collide with an earlier run of the same task.
The real `result` event carries `exitCode`/`sessionId` at its TOP level (no `data`, no `id`); `data` is a defensive fallback.

**Login**: unauthenticated Copilot exits 1 with empty stdout and a plain-text stderr `Error: No authentication information found.` — the non-JSON line is mapped to `stderr` and, once per run, to `COPILOT_LOGIN_STATUS_TEXT` ("GitHub Copilot isn't logged in — run `copilot login` in a terminal (or set COPILOT_GITHUB_TOKEN in this harness's env)"; `session.error` text matching it does the same); `checkHarness` never knows (`loggedIn` stays `null` — there is no cheap passive auth probe), so the failure is only seen at run time.

**Settlement and cancel**: a turn resolves on `result` or on the exit file, whichever the tailer sees first; before resolving, `finishCopilotTurn` waits up to 2 s for the exit file, drains the log, derives the code (`result.exitCode`, else the exit file, a missing exit file reading as 1), then `finalizeCopilotTurn` runs IN THIS ORDER — usage sentinel, plan chunk (Plan mode on code 0 only), `sink.settleAll` — each isolated so a throwing emitter can't block the next.

**Copilot answers SIGINT/SIGTERM with `abort` + `result.exitCode 0` + rc 0**, so a Stop looks like success: the driver's `kill()` kills the tmux session, settles subagents `orphaned` and resolves 1, and the orchestrator's existing `cancelled` flag records the run `cancelled` whatever the code; an `abort` agetor did not ask for (`ctx.aborted && exitCode === 0`) resolves 1 so it never reads as success.
A tmux launch failure throws (`failed to start GitHub Copilot session: …`), which `spawnAgentOrFail` turns into a failed run.

**Usage**: `--usage-output-file` is parsed by `parseCopilotUsageFile` into the shared `FX_USAGE_STATUS_PREFIX` sentinel (`copilot:usage:<runId>`; token fields summed over `modelMetrics`, a field no model reported omitted), so RunPanel's run-row usage chip (gated on fx/cursor/copilot) shows tokens.
The file's `totalNanoAiu`/`aiCreditsStatus` credit figures are deliberately ignored: the nano-AIU → AI-credits conversion could not be verified against Copilot's own credit display, so no credits number is shown anywhere (re-add it only with a live-verified conversion).

**Plan card**: Copilot has no plan tool call to anchor a card to, so at the end of a SUCCESSFUL Plan-mode turn the driver emits one synthetic `tool_use` `{id: "copilot-plan:<runId>", name: "copilot_plan", input: {plan}}` (line uuid `copilot:plan:<runId>`) — the `planContent` of the turn's `exit_plan_mode.requested`, else `plan.md` under `$COPILOT_HOME/session-state/<sessionId>/` whose mtime is at/after the turn start (`readCopilotPlanFile`, which rejects a session id containing a path separator or `..`); emitted last, it is the run's last `tool_use`, and `detectCopilotPlan` (orchestrator, beside `detectCursorPlan`, same never-throws contract, called from `attachDoneHandler` on a succeeded run) records a `pending` `TaskPlan` through `upsertDetectedPlan`, which RunPanel's existing `PlanCard` substitution (keyed on the tool_use id) renders; `PlanDialog` is editable for cursor and copilot.
`server.ts`' `planKindGuard` (cursor | copilot) fronts both plan routes.

**Approve differs from cursor's**: the copilot branch writes NO file (no `.copilot/plans` in the user's repo, nothing in Copilot's state dir), always embeds the effective plan in the message (`The plan is approved — implement it now. Approved plan:` + plan, or the "approved with edits … follow this version" variant), records `filePath: null` (`approvePlan` takes `string | null`), flips an UNBOUND Plan task to Auto through a direct `tasks.update` (reverted if the send throws or isn't delivered; status line `plan approved — switched this task to Auto so GitHub Copilot can implement it`), and keeps Plan on a profile-bound task with the additive `warning` (`plan approved, but this task's agent runs GitHub Copilot in Plan mode — detach the agent or switch the mode to implement`); `approvalsInFlight` blocks a double approve.

**Subagents**: Copilot reports its subagents inline in the same JSONL — any event with a `parentToolCallId` goes to the injected `CopilotSubagentSink` instead of the main stream, `subagent.started` → `sink.started`, `subagent.completed` (a `cancelled` one reads as failed) / `subagent.failed` → `sink.settled`.
The orchestrator's `makeCopilotSubagentSink(runId, taskId)` inserts a `subagents` row per subagent with the globally unique id `cp-<runId>-<toolCallId>` (tool call ids are only unique within a session), the dedicated `parentKind: "copilot_subagent"` (in `db.ts`'s `PARENT_KINDS` allow-list) and an empty `sourcePath`
— `claude-subagents.ts`' `seedRow` returns early for that kind, so after a copilot → claude-code harness switch the Claude watcher never seeds or tails a copilot row (it seeds every row of the task, whatever wrote it, and would otherwise re-map the copilot log with the Claude mapper) — appends the nested events tagged with that id (`runs.appendEvent(…, subagentId)` + the same `emit` the claude watcher uses), and on `settled`/`settleAll` closes rows (`subagents.settleRunningForRun(runId, status, now)`, run-scoped unlike the task-scoped `orphanRunning`) and calls `maybeReleaseHeldTask`
— so the existing background-agent tab strip lights up with no UI change and a still-running copilot subagent holds the card in `running`; `settleAll` runs before the turn resolves (`completed` on code 0, else `orphaned`), `killCopilotState` settles `orphaned`, `reconcileOrphans` settles a dead copilot run's rows `orphaned`, and its boot held-task pass retires any copilot row still `running` outside a live turn (through `orphanRunningSubagents`, or through each stale run's own sink when the task's current turn was reattached), so no row can hold a task forever.
Every sink method is idempotent (reattach replays from offset 0) and the driver wraps the sink so replayed nested events dedupe against the same seeded uuid set.

**Queue and resume**: `copilot -p` is one-shot, so a follow-up sent mid-turn queues in `copilotTurnQueue` and runs as the next turn from `drainCopilotQueue` (called from `attachDoneHandler`), modelled on codex's: `sendCopilotTurn` / `spawnCopilotTurnNow` re-run Pre-flight 1b (the per-model CLI floor) before minting a run row — a refused turn returns `{ delivered: false, reason }` with nothing written, and a refused QUEUED follow-up moves, with everything behind it, to the backlog tray (raw text, `restashPasteWithheldText`) with a status line — `sendInput`'s early floor gate covers codex and copilot, and `startingTaskIds` is the shared claim.
Copilot ALWAYS gets a `--session-id`: `resolveCopilotResume` resumes `findLastCopilotSessionId(taskId, harnessId)` — filtered on `runs.agent = <harness id>`, because another Copilot harness has a different `COPILOT_HOME` (possibly another account) that cannot see the session — and otherwise `spawnAgent` mints a fresh uuid; the status line is `resuming GitHub Copilot session <id8>…`, `previous GitHub Copilot context is on harness "<other>" — starting a fresh session (context didn't carry over)` (only another harness has one), `previous Copilot session <id8>… not found for this account — starting fresh` (the id's `session-state/<id>` dir is gone from this `COPILOT_HOME`; the check is skipped under the fake driver unless `AGETOR_COPILOT_FAKE_REQUIRE_SESSION_DIR=1`) or `no prior GitHub Copilot session — starting fresh`.
The id lands in the new `runs.copilot_session_id` through `sessionIdPatchFor(kind, id)`, an exhaustive switch that replaces the old ternary whose default arm wrote fx's column.
Boot reconcile selects `copilot_session_id` and reattaches a live per-task tmux session through `reattachCopilotSession` (log re-tailed from offset 0, `seenLineUuids` seeded, subagent sink attached, plan-file mtime gate defaulting to the prompt file's mtime) only WHILE a turn is in flight (one-shot, like codex/gemini); agent-switch, archive and delete `dropCopilotSession`, and switch and delete also clear `copilotTurnQueue` (a queue left behind resurfaces out of order on a later turn).

**Exhaustive dispatch**: `buildCommand` and `spawnAgent` end in an explicit `if (kind !== "codex") { const x: never = kind; throw new Error("unknown harness kind: …") }` (a retired `grok`/`kimi` row now fails cleanly via `spawnAgentOrFail` instead of launching codex) and `sessionIdPatchFor` throws on unknown; `harnessEnv` has the compile-time `never` check but must NOT throw at runtime (an unknown kind sets no home var and warns once), because `checkHarness` calls it for every harness row and a throw would break `GET /harnesses`; `resolveBin` likewise falls back to the kind string.

**Identity and install**: GitHub's CLI is the Homebrew CASK `copilot-cli` (`INSTALL_HINTS.copilot = brew install --cask copilot-cli`, also `npm i -g @github/copilot`), and AWS Copilot ships a binary of the same name (the `aws/tap` formula can shadow the cask) — `checkHarness` refuses a `--version` that doesn't contain `GitHub Copilot CLI` (case-insensitive; GitHub's prints `GitHub Copilot CLI 1.0.104.`, AWS's `copilot version: vX.Y.Z`) as unavailable with the reason "`copilot` isn't GitHub Copilot CLI (AWS Copilot ships a binary of the same name)" plus the install hint, with no extra spawn (skipped when the version probe returned nothing); `BREW_PACKAGES.copilot = "--cask copilot-cli"` so a Homebrew install's upgrade hint is `brew upgrade --cask copilot-cli` (without `--cask` it could upgrade AWS's formula), else `copilot update`.
The npm loader unpacks ~204 MB on first launch, so the first `--version` probe can exceed `probeVersion`'s budget; the row then shows no version and the AWS-binary identity gate is skipped (a null version never gates) until the next 15 s status poll re-probes — documented, not handled.

**CLI floors**: `MODEL_MIN_CLI_VERSION.copilot` holds the first stable version whose changelog mentions each model (kimi-k3 1.0.79, claude-fable-5.1 1.0.83, gpt-6-astra 1.0.85, claude-opus-5.5 / gpt-6-sol / gpt-6-luna 1.0.89, gpt-6.1-sol 1.0.90, claude-haiku-5.5 1.0.94, gemini-4-argon 1.0.98); claude-sonnet-5.5, gemini-3.8-flash, grok-4.7, mai-code-1.1-flash and `auto` have none (fail-open).

**Model discovery**: `discoverCopilot` runs `copilot help config` once per refresh with agetor's own environment plus `COPILOT_OFFLINE=true` (offline, no auth; no per-harness env, since the output depends only on the binary; its optional `env`/`bin` parameters are test seams; a 4 s probe budget for a cold node-loader start) and `parseCopilotModels` reads the `- "<id>"` lines of the `model` block only (other keys have their own value lists; `auto` is not printed, the curated row covers it; 31 ids on 1.0.104).
The list tracks the CLI version, NOT the account's entitlements, so discovery is kind-level and copilot is deliberately not in `CATALOG_SCOPED_KINDS` (discovered-only ids append after the curated rows, curated rows never hide) — the `runRefresh` `kinds` array is index-aligned with its `Promise.allSettled` list, so add the kind to both.

**Capability discovery** (`/` autocomplete and the Extensions picker, at a git ref too): skills from `$COPILOT_HOME/skills` and HOME-relative `~/.agents/skills` (user; an env-map `HOME` wins, since `harness.home` is a `COPILOT_HOME`, not a HOME) and `.github/skills`, `.agents/skills`, `.claude/skills` (project;
no builtins); MCP servers from `$COPILOT_HOME/mcp-config.json` (user) and `.mcp.json` + `.github/mcp.json` (project; `mcpServers`, or `servers` in the VS Code shape); custom agents (flat `*.md` in `$COPILOT_HOME/agents` and `.github/agents`) become the NEW extension kind `"agent"` (insert `@<name>`, name from the frontmatter `name:` else the filename minus `.agent.md`/`.md`
— whichever first reads back through the shared `@` tokenizer as one whole bare token, so a name with whitespace or trailing sentence punctuation falls back to the stem, and an agent with neither usable is skipped; ExtensionPicker's "Agents" group; collapse order `{mcp, skill, plugin, agent}`, project wins over user on a clash).
In ref mode `CAPABILITY_READ_PATTERNS` gains the three `.github/` shapes and `ref-tree.ts`' `DEFAULT_PATHSPECS` gains `.github`; `bundle.ts`' exported `userLevelSkills` covers copilot.
A prompt starting `/<skill>` works in `-p` (verified against 1.0.104: Copilot injects the skill body), so skill inserts stay `/name`.

**Persistence**: migration `077_copilot_harness.sql` (authored as 075 and renumbered when it merged after main's 075/076; `aliases: ["075_copilot_harness"]` keeps a dev DB that applied the old id from re-migrating) rebuilds `harnesses` (no FK points at it) with a CHECK admitting `copilot` and `opencode`, copies all 11 columns explicitly (`profile_mcp_servers` included), seeds the built-in row **ENABLED** (like claude-code and antigravity, owner D2 — every user sees "GitHub Copilot — not installed" until the CLI is present), self-heals the other built-ins with `INSERT OR IGNORE`, and adds `runs.copilot_session_id`; `Run.copilotSessionId` is optional so existing `runs.insert` literals need no change.

**Copilot model ids collide with other kinds' literals** (`gpt-6.1-sol`, `gemini-4-argon`, `claude-opus-5.5`, …), so any future model normalize/retire migration for copilot rows MUST join `harnesses.kind = 'copilot'`, and one meant for other kinds must keep its kind join.
Not in v1 (owner-deferred): the task-list progress badge (it would need Copilot's undocumented session SQLite), the account-quota usage meter (`USAGE_SUPPORTED_KINDS`), Assisted/Autopilot modes, `--max-ai-credits`, an ACP driver, and `--disable-builtin-mcps`.

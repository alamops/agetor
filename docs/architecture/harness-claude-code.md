# Harness: claude-code (tmux REPL driver) and the Claude session lifecycle

> Moved from `CLAUDE.md`, where this was the `claude-code` bullet of “Agent command shape” and “Claude session lifecycle”. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

**`claude-code`** → driven through `src/bun/claude-tmux.ts`.
One tmux session per task hosts the interactive `claude` REPL.
Launch argv looks like `claude [--model claude-opus-5-5] [--dangerously-skip-permissions | --permission-mode <id>]` (no `--print` — `claude -p` would draw from a separate Agent SDK credit starting 2026-06-15, so we use the regular subscription quota via interactive mode).
The initial prompt rides the launch argv as the final positional after `--` (claude's `claude "query"` form) when it fits `CLAUDE_PROMPT_ARGV_MAX_BYTES` (4096 bytes, `agents.ts`); a larger one would push tmux's whole client command past its size cap (`command too long`), so `buildCommand` returns it as `deferredPrompt` and the driver pastes it once claude's composer is up.
That oversized initial prompt and every follow-up are delivered as keystrokes via `tmux load-buffer + paste-buffer + send-keys Enter`.
Structured output comes from tailing `~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl`.
Effort maps to `CLAUDE_CODE_EFFORT_LEVEL` env, and every launch (fresh, `--resume`, every claude-code harness — set in `buildCommand`) also carries `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION=false` (`??=`, so a harness's own env map may set it back to `true`): on 2.1.296 that turns off both prompt suggestions and the startup `Try "…"` sample, which otherwise sit as dim placeholder text on the `❯` row, and the env var beats the user's `promptSuggestionEnabled` setting (`docs/plans/claude-code-placeholder.md`).
Tmux is a hard prereq — `checkAgent` reports unavailable if `tmux -V` fails.
Five claude-specific derived surfaces ride the generic JSONL streams: **(1) Ask cards** — the "Claude is asking" card is scraped from the tmux pane, because Claude Code never writes the `AskUserQuestion` tool_use to the session JSONL while the modal is open (it lands together with its tool_result only once the user answers or declines — verified on 2.1.168, 2.1.170 and 2.1.284), so the pane is the ONLY live source and `readPendingAskQuestionsFromJsonl` is a cheap first attempt that costs nothing if a future CLI flushes early, not a preferred path (the former 2 s JSONL grace wait was removed — its premise was false and it only added latency).
A pane parse is trusted only when `parseModalPane` reports `complete` — the first real option is numbered `1`, the question text is non-empty, AND the `☐`/`☒` header or tab-bar row is visible above it (on the default 80x24 detached pane a tall modal scrolls the tab bar off while option 1 stays visible, which used to register a 4-question modal as ONE question) — and the option list is not windowed (`↑`/`↓` edge markers); a partial card would drive *wrong-option* keystrokes, so it is never registered.
A lossy pane (`isLossyAskPane`: incomplete, a `✂ … lines hidden` collapse marker, or a label/question row reaching the right edge — `paneWrapRisk`, since a wrapped label's continuation lands at the description indent and parses as a fake description) is grown to 200×100 (`GROW_PANE_COLS`) and walked tab by tab with `Right`; the active tab is marked only by ANSI colour, invisible to plain `capture-pane`, so every `Right` is verified by comparing the new tab's body (question + option labels) with the previous one — identical means the key was swallowed, so it is resent once (bounded) before the collection is abandoned.
A question that wraps to two or more rows carries a `│ ` gutter on every row, which the parser strips (a bare `│` row is a paragraph break, so `questionText` may contain `\n` and the card renders it `whitespace-pre-wrap`).
A typed custom answer is driven into claude's native `Type something` row instead of cancelling the modal: the text goes in with `send-keys -l` (one argv element, no shell) and is verified on the pane before `Enter`; in a multi-select question typing auto-checks the row, and `Enter` on it would un-check it, so the advance goes `Down` to `Next`/`Submit` and never `Enter` on that row (an `Enter` on an EMPTY row declines the whole modal); a single-select custom answer replaces any pick, a multi-select one is added to the picks.
Only text that can't be typed — multiline, over 400 characters (`ASK_TYPED_ANSWER_MAX_CHARS`), or carrying control characters (`unsafe-custom`) — custom text for a question with no `Type something` row (`hasTypeRow === false`, the preview layout, where typed characters would act as hotkeys; `no-type-row`), or a pick that can't be driven (unknown option, arity mismatch) falls back to `Escape` on the modal plus a follow-up message (`planAskAnswers` `mode: "message"`);
the same Esc + follow-up fallback runs when the driver refuses or can't verify the typed step (`driveAskAnswers` returns `"typed-abort"` — the route then calls `formatAnswersMessage`, which sends custom-only for a single-select question); before pasting, that fallback goes through `dismissAskModalForMessage` (Escape, verify the modal left the pane, clear any leftover draft from claude's composer) and, when it can't reach a clean composer, does NOT paste
— the route answers `ok:false` with a "answer it in the terminal" reason and the scraper re-collects a still-open modal; the route's JSON carries `delivery: "drive" | "message"` (the path that delivered or attempted the answer), which the card uses to word its failure toast when the response carries no `reason` (a `reason`, when present, is shown as the toast instead);
a response with NO `delivery` means nothing was attempted (the card was already resolved) and reads as neutral "already resolved" feedback rather than an error; and a request for a card that another request is still answering is refused 409 by the route's synchronous in-flight claim (`askAnswersInFlight`, taken before the first delivery await so a double submit can never drive the same keystrokes twice
— the same contract as the plan-approve route), which the card and `agetor answer` report as neutral "already being answered" feedback.
The multi-tab collector registers a card only from a known state (tab 0, cursor on option 1) and verifies the `Left` return trip (`tabBodyKey` vs tab 0, bounded extra `Left`s), so a re-collect can never mis-drive a dirty modal; the boot poller confirms 2.1.284's unnumbered workspace-trust dialog only after seeing it twice, retries the confirm up to 4 times, and reports the outcome.

**(2) TODO tracker** — `src/shared/todo-progress.ts` derives a task list from generic `tool_use`/`tool_result` events, understanding both legacy `TodoWrite` snapshots and the current Task tools (`TaskCreate` appends — task number parsed from its tool_result `"Task #N created successfully"`, sequential fallback; `TaskUpdate` mutates by `taskId`; most-recent family wins).
The RunPanel card derives client-side; the orchestrator persists a `{completed,total}` summary to `tasks.todo_progress` (migration 044, server-managed) for the board card's badge.

**(3) Plan history** — an `ExitPlanMode` tool_use records a `pending` plan (full markdown from `input.plan`) into `tasks.plans` via `task-plans.ts` claude helpers; its tool_result resolves it `approved` (extracting the `"## Approved Plan (edited by user):"` marker into `editedContent`) or `rejected`.
Claude plans are read-only records — approval itself stays the live keystroke-driven `tmux_prompt` flow (`planKindGuard` still blocks claude from the cursor/copilot plan mutation routes).
The driver additionally emits a `status` chunk `PERMISSION_MODE_STATUS_PREFIX + mode` (shared/types.ts sentinel) on each permission-mode change (marker lines + user-line `permissionMode` fallback, deduped per session).
It used to render as a chip pinned below the transcript; **that chip was removed** (it read as a stray "AUTO" pill hanging off the end of a finished conversation) but the events are still emitted and persisted, so **RunPanel's suppression of these status lines is load-bearing, not dead code** — without it every turn start and every Shift+Tab would spam a divider into the scrollback.

**(4) Local slash commands** (`/model`, `/effort`, `/cost`, …) — claude answers these inside its TUI and **never writes an `assistant`/`end_turn`**; the JSONL twin is an isMeta `<local-command-caveat>` line (silenced), a `<command-name>` line and a `<local-command-stdout>` line (both forwarded as `user` chunks — the shared `src/shared/user-message.ts` parser renders them as command / command-output bubbles, and a stdout line carrying sibling tags (e.g.
`<forked-skill-launch>`) renders those as tag blocks via the same parser; a fresh session's first command arrives as `system`/`subtype:"local_command"` and is mapped the same way).
`TurnSlot.slashCommand` records the turn's leading `/token`, and a stdout line for such a slot stages a bannerless `pendingEndTurn` (`isLocalCommandStdoutEvent`) so the run settles instead of hanging until the stuck-turn watchdog cards the idle pane.
Two more scraper nets ride on that: `paneShowsIdleInputBox` (a `STATUS_BAR_RE` status bar as one of the last two non-blank rows — counted after dropping the background-agent roster (`  ⏺ main` / `  ◯ <type>  <name>  … · ↓ Nk tokens`) that 2.1.296 draws BELOW the bar and keeps after the agent finishes (`withoutTrailingAgentRoster`, also skipped by `readPaneMode`;

— every claude modal replaces both; a `❯` row whose only text is Claude's placeholder (a prompt suggestion, the startup `Try "…"` sample, `Message @<agent>…`) counts as bare too: placeholders render entirely SGR-dim (first character inverted only when Claude draws its own cursor cell — with the `tengu_native_cursor` flag on, as on the owner's account, the row stays all-dim and the block is the terminal's real cursor), which plain `capture-pane -p` can't see, so when the plain live row is non-bare the caller takes ONE extra `capture-pane -p -e` (`captureStyledTail`, seam `__forTest.setCaptureStyledTail`), locates the same row by raw line index (`livePromptRowIndex`), trusts it only when its SGR-stripped text equals the plain row (else the pane moved → today's reading), and `isPlaceholderRow` walks its SGR state;

Mid-conversation `/model <id>`/`/effort <id>` pop a `Switch model?`/`Change effort level?` Yes/No confirm when the value actually changes; a user-typed command relays it as a numbered card.

**The Task Details dropdowns never use the typed forms** (smoke on 2.1.246): typed `/model <id>` rewrites the user's *global* claude default, so a model change drives the bare `/model` picker instead — `mirrorModelViaPicker` pastes `/model`, waits for `matchNumberedModal` with `confirmKey: "s"`, arrows to the row whose family (`claudeModelPickerFamily`: Opus / Sonnet / Fable / Haiku;

A local command's JSONL twins are **never continuation content** (`isContinuationContentEvent`): a mirror pushes no turn slot, and adopting its `<command-name>` line as an `origin: continuation` run left a run nothing could settle.
Claude's compaction-summary `user` line (`isCompactSummary` or `isVisibleInTranscriptOnly`) is the third never-content family — idle compaction (~54 min idle, prompt cache about to expire) wrote it with no turn open and it used to open a phantom continuation run that sat `running` for hours.

**(5) Sent-files cards** — a `SendUserFile` tool_use (`{ files: string[], caption?: string, status: "normal" | "proactive", display?: "render" | "attach" }`) renders as a dedicated **`SentFilesCard`** substituting the generic `ToolUseBlock`, the same way `PlanCard` does — rendering-only from the persisted tool_use input, so historical transcripts upgrade too.

On error `is_error:true`, the content is wrapped in `<tool_use_error>…</tool_use_error>` and `toolUseResult` is a plain **string** instead — and **directories are rejected** (`Attachment "…" is not a regular file.`, verified live on 2.1.263), so a folder tile only ever appears on an errored call.

`claude-tmux` forwards `toolUseResult.attachments` additively as `attachments?: [{path,size,isImage,mediaType}]` on the `tool_result` event (shape-validated via `sanitizeToolResultAttachments`, never emitted when empty, never for a string `toolUseResult`, so existing events stay byte-identical).

Two more rules ride on that plumbing: **no paste may ever land in Claude's background-sessions view** (Left on an empty composer; bar `· enter to return · space to reply`, `paneShowsBackgroundSessionsView`) — text there starts a NEW background session, so `queuePaste` presses Escape once and waits for the conversation (`returnFromBackgroundSessionsView`) and otherwise withholds `pre-paste`, and the scraper never cards the view and presses Escape itself once a turn behind it has gone quiet past `STUCK_TURN_FALLBACK_MS`;
and **no paste may ever type Enter into a live claude modal** — `queuePaste` reads the pane first (`paneShowsBlockingPrompt`: numbered / yes-no / slider / ask / footer-armed unparsable — exactly what the scraper would card) and, if a prompt is still up after `PASTE_MODAL_GRACE_MS` (1.5 s), **withholds** the paste with a `paste withheld: …` status and `onPasteFailure({ op: "modal-guard" })` (so `sendTurn` settles its run `failed` instead of silently confirming the modal and losing the message).
The grace is deliberately short: the card click that clears a modal (`dismissTmuxPrompt`) is queued on the *same* per-task `queueTmuxOp` chain and would otherwise wait behind the paste.
Modal-guard withholds are double-sampled (`stillBlocking`) so one transient frame can't fail a run (the two `composer-dirty` withholds act on the frame the clear was verified against); the boot-time deferred prompt keeps the check with a zero grace (`modalGuardGraceMs: 0` — its give-up branch can reach the paste with an un-carded prompt on screen; `skipModalGuard` has no production caller).
A withhold carries a `phase`: `pre-paste` (nothing delivered — the orchestrator re-stashes the text into the backlog), `pre-enter` (the text is already in claude's composer, so the driver remembers `composerHoldsText` and clears it with `COMPOSER_CLEAR_KEYS` = `Escape Escape` before the next idle paste — verified on 2.1.245; there is no safe mid-turn clear, and a double-Esc on an empty box opens the rewind picker, so it's sent only when `paneShowsComposerText`), or `composer-dirty` (the earlier text couldn't be cleared yet).
All three phases — and a genuine tmux failure — re-stash the message into the backlog (deduped, archived-guarded) so nothing typed is ever lost, and `POST /runs/:id/input` awaits the paste outcome (bounded by a 5 s race) so a withheld send returns `{ delivered: false, withheld: true, savedToBacklog: true }` — the composer / diff composer / commit-push / resolve-conflicts sends clear their draft and toast, the tray keeps its item (the server dedupes re-stashes against the whole backlog), and the ask-card free-text answer route threads the same flags; a paste dropped by a `dropSession` mid-chain also fires `onPasteFailure`, so it re-stashes too; the clear is confirmed positively (`paneShowsIdleInputBox` on the live `❯` row, the bottom-most one above the status bar — the transcript echo of the previous line uses the same glyph) and the pane is re-guarded before the paste.
And **claude's own `/model` / `/effort` outcomes sync back to the task row**: the driver keeps `<command-args>` next to `<command-name>` and fires `setLocalSettingChangedHandler` on that command's stdout; the orchestrator's `applyClaudeLocalSetting` maps it via `src/bun/claude-local-setting.ts` (`CLAUDE_MODEL_FLAG` inverse → stdout display name against `AGENT_OPTIONS` labels → raw `claude-*` passthrough;
effort is outcome-first — claude's `Set effort level to …` line is required, the typed arg is never trusted on its own — and validated against `supportedEfforts(model)`; a value agetor can't store (`ultracode`, an unknown display name) leaves an `unrepresentable` breadcrumb instead of vanishing; a model sync cascades RunPanel's effort fallback into the same update, **without** mirroring `/effort` back into the live session
— claude owns its live pair, the row is for the next spawn; `Kept model as …` syncs too, correcting a row the dropdown moved before the user declined the confirm) and calls `tasks.update` **directly** — the PATCH route is the only `reconcileTaskSession` caller, which is what keeps a synced change from being mirrored straight back as another `/model`.

## Claude session lifecycle (one tmux session per task)

- `startTask` on a claude task → `tmux new-session -d -s agetor-<taskId-prefix> -c <cwd> -- claude …`, sends the prompt, and tails the JSONL.
  The run row records `tmux_session`.
- Each subsequent user message from the run panel routes through `sendInput` → `sendTurnInExistingSession`, which branches on whether a turn is already in flight (`task.runId && active.has(task.runId)`):
  - **Idle** (no turn running) → creates a **new run row** and routes through `sendTurn` — same tmux session, fresh "done on next end_turn" listener (one row per user turn for genuinely-sequential turns).
  - **Busy** (a turn is mid-flight) → **folds** the message into the active run via `pasteFollowUp` (claude-tmux): paste the prompt into the live session and record it as a `user` event on the current run — **no new run row, no new turn slot**.
    This keeps **at most one in-flight run per task**, which is the invariant that prevents the old "queue status never recovers" bug: claude's TUI can coalesce several queued messages into *fewer* `end_turn` events than messages, and one slot per message would strand the surplus slots (and their run rows) in `running` forever.
    `pasteFollowUp` also sets `SessionState.holdUntilIdle` so the run does **not** resolve on the intermediate `end_turn` between the current response and the folded reply — otherwise the task would bounce to `review` mid-conversation.
    The run stays `running` (green) and resolves only when claude goes quiet (the `END_TURN_IDLE_FIRE_MS` idle-fire in `flush`) — "the end is the end."
  - **The fold-vs-mint decision is made on fresh state, in one synchronous section** (`docs/plans/handoff-identification-fix.md`, RC2/D12): `sendTurnInExistingSession(taskId, line, rawLine, opts)` takes no task snapshot — its first statements, with no `await` before `pasteFollowUp`/the run insert, are `drainSessionJsonl(taskId)` (claude-tmux: a synchronous read-and-dispatch of whatever the session JSONL gained past the tailer's cursor, so a background-task notification already on disk is adopted as a continuation NOW; it never fires a staged `end_turn`, and is a no-op while the session is mid-dispatch — the `SessionState.dispatchDepth` re-entry guard that `flush`, `flushSync` and the drain all increment), a fresh `tasks.get`, and the unchanged `active.has(task.runId)` fold check.
    A follow-up therefore folds into a continuation adopted during `sendClaudeTurn`'s `sessionLiveness` await instead of minting a second in-flight run.
    The reverse race is closed too: `startContinuationRun` declines adoption (returns `null`) while `startingTaskIds` holds the task, so a notification line `sendTurn`'s own `flushSync` dispatches in the mint window routes to the previous run (`lastChunk`) and the rest of claude's turn lands on the minted run — never a continuation displacing it.
    `maybeReleaseHeldTask` (the held-task release the subagent watcher's settle drives) also drains first, so a notification line on disk adopts its continuation before the release could flip the card to `review` and settle the pre-continuation run.
- The run panel shows a **unified task-level event stream** (every run's events merged in id order via `GET /tasks/:id/events`), so the badge race that used to make a fast claude reply land the new row as `succeeded` before the UI observed the `running` transition is no longer a UX issue — the user sees their message + the assistant response stream live regardless of per-row status.
  The runs list itself is an informational, expandable summary; it doesn't gate the stream view.
  There is **no "queued" run state** — a follow-up sent while the agent works folds into the active run, so the heartbeat is simply "Agent is working…" (green) or off.
- **Stop** (`cancelRun`) sends `Ctrl+C` via `tmux send-keys`.
  The session stays alive for follow-ups; only the in-progress turn aborts.
- **Delete task** (`deleteTask`) calls `dropSession(taskId)` → `tmux kill-session` before tearing down the worktree.
- **Live session death** — a running turn whose tmux session dies *unexpectedly* mid-run (crash, external `kill`, tmux server gone) is caught **while running**, not just at the next boot.
  `attachTailer` arms a `deathTimer` (`startDeathWatch`) whose 400 ms tick is a fork-free `kill(pid, 0)` on the pane's process (`createDeathProbe` in `session-liveness.ts`, pid learned once via `panePidFor` — `list-panes -a` + exact-match in JS, never `display-message -t =…`); the `tmux has-session` fork runs only to *confirm* a vanished pid and as a 10 s periodic re-validation that bounds pid reuse, so a `gone` verdict is always tmux's own, never inferred — but only *while a turn is in flight* (`turnInFlight`), and only after **two consecutive misses** (`DEATH_MISS_THRESHOLD`, so a transient tmux hiccup can't false-trip).
  On death it emits a `SESSION_DIED_STATUS_PREFIX` (`"session ended: "`, in `shared/types.ts`) `status` chunk and settles the in-flight turn; the orchestrator's `makeChunkHandler` pattern-matches the sentinel (exactly like the claude API-error path) and moves the card to **`blocked`** with `reason: "session-died"`, recording the run **`failed`**.
  Codex has the same death-watch in `codex-tmux.ts` (its one-shot session always counts as in-flight) and emits the identical sentinel.
  This is distinct from the boot-time `orphaned`→`ready` path below: an *unexpected mid-run* death needs attention (`blocked`), a *restart* is routine (`ready`).
  No false positives on intentional teardown — Stop keeps the session alive, and `deleteTask`/`dropSession` → `disposeSessionState` clears the `deathTimer` before the kill.
- **Boot reconciliation** *reattaches* to any live `agetor-*` tmux session whose run row is still `status='running'`.
  Reattach reads the JSONL from offset 0 and deduplicates by claude's per-line `uuid` (persisted on `run_events.line_uuid` as the idempotency key, with a partial unique index on `(run_id, line_uuid)`).
  Subagent transcripts are rehydrated by the watcher's task-scoped, cooperative seed (boot reconciliation, step 5 in [task-lifecycle.md](task-lifecycle.md)): `attachTailer` is async and awaits the watcher's `ready`, so a 200-subagent task's seed costs ~200 ms of yielding work instead of minutes of frozen core, and the slow-launch breadcrumb gained a `watcher Nms` stage (emitted right before the `ready` line, so it may now follow a startup-question status line).
  It **never** enumerates-and-kills sessions with no matching running row — that would reap another instance's (or a `bun test` run's) sessions were they to share a tmux socket; unaccounted-for sessions are left alive.
  Runs whose tmux session is gone (or whose JSONL was deleted out from under us) still flip to `orphaned`.
- **Confirm-on-quit**: closing the app while runs are active does NOT kill the tmux sessions.
  `index.ts` hooks Electrobun's `before-quit` event and broadcasts a `quit_request` over `GET /app/events` (the app-level SSE channel); the webview's QuitConfirmDialog asks the user whether to quit anyway.
  On confirm, `POST /app/force-quit` (optional `{completely}`) arms a one-shot flag in `quit-guard.ts` and re-issues `Utils.quit()`.
  The detached tmux sessions stay alive in the background and are picked up by the next launch via the reattach path above — or, with "Keep Agetor running in the background" on, by the background core that takes over within ~1 s of the quit (the event carries `backgroundArmed`; the dialog then says "They'll keep running in the background" and offers "Quit completely", which also stops the background core until next login; see [always-on-host.md](always-on-host.md)).

  **fx carve-out**: fx has no tmux session to leave alive in the first place — `fx-acp.ts` reaps every live `fx acp` child on process `exit` and on SIGINT/SIGTERM/SIGHUP (always installed, always reaping; only the sole listener for a given signal also calls `process.exit` itself — see [harness-fx.md](harness-fx.md)), so quitting kills the fx child outright rather than orphaning it in the background; an fx child that somehow survived would be an unreachable zombie, not a resumable session, since fx has no reattach path at all.

Tests set `AGETOR_DATA_DIR` to a `mkdtemp` directory at the top level of the file, never in `beforeAll` — keep doing that for any new test that imports `./db.ts` or `./orchestrator.ts`, since the db opens (and migrates) on module load and `bun test` runs every file in one process, where the first import of `db.ts` wins (the `NODE_ENV=test` guard comment in `db.ts` has the history).

`tasks.checkout_branch` (migration 063) joins the same skipped-columns list too — the last-seen worktree checkout, written only by `tasks.insert` and `tasks.setCheckoutBranch`'s own targeted, compare-then-write UPDATE (never bumping `updated_at`; a step row's write also updates its pipeline parent) — see `startTask`'s pre-flight 2 in [task-lifecycle.md](task-lifecycle.md) and `docs/plans/codex-terminal-worktree-error.md`.
`tasks.repositories`/`tasks.issue_repo_path` (migration 087) join the same skipped-columns list too — see [Multiple repositories in one task](#multiple-repositories-in-one-task-migration-087) below.

**Migration 072 (`072_task_speed.sql`) is the repo's first `DROP COLUMN`**: it adds `tasks.speed`/`agent_profiles.speed` (`TEXT NOT NULL DEFAULT 'off' CHECK (speed IN ('off','fast','ultrafast'))`), backfills them from the boolean `fast`, drops `fast` from both tables (safe: no index, trigger or view names it, bun's SQLite is 3.51.0, and the older migrations that write `fast` run before 072 on a fresh DB), and rewrites every `lastFast:<kind>` preference to `lastSpeed:<kind>` (`true` → `fast`, else `off`).
It is one-way: an older agetor build can't write tasks or agent profiles against a migrated database (its `INSERT`/`UPDATE` statements still name `fast` and fail), so a rollback is a new migration re-adding `fast` from `speed`, never an edit to 072.
Stored JSON that still carries `fast` — a task's frozen `agent_profile` snapshot, a pipeline run's `snapshot.profiles`, a bundle file — reads leniently: `speed`, else `fast` via `speedFromFast`, else `off`.
`harnesses.profile_mcp_servers` (migration 073, `INTEGER NOT NULL DEFAULT 1`, exposed as `Harness.profileMcpServers`, absent ⇒ on) is the fx-only profile-MCP toggle described in [harness-fx.md](harness-fx.md); migration 074 retires three fx model ids ([harness-fx.md](harness-fx.md)); migration 077 widens the `harnesses.kind` CHECK for `copilot`, seeds it enabled and adds `runs.copilot_session_id` ([harness-copilot.md](harness-copilot.md)).

**Migrations 078–080 (the OpenCode harness; authored as 077–079 while the Copilot branch was still planning 075/076, then renumbered when Copilot merged first as 077 — the old ids stay as `aliases` in `index.ts` so a dev DB that already applied them is not re-migrated):** 078 (`078_opencode_harness.sql`) is a `harnesses` table rebuild (the 061 recipe: create `harnesses_new`, **copy all 11 columns explicitly**
— `profile_mcp_servers` (073) included, which 061's copy predates —, drop, rename) whose `kind` CHECK admits `opencode` **and `copilot`** so it and the Copilot migration's rebuild (077) copy cleanly in either order (neither adds a `harnesses` column, because the other's explicit-column copy would silently drop it), seeds the built-in `opencode` row **disabled**, re-seeds the built-ins' `enabled` defaults (claude-code 1, antigravity 1, copilot 1, the rest 0), and adds `runs.opencode_session_id`; 079 adds `tasks.opencode_server` and `agent_profiles.opencode_server` (`TEXT NOT NULL DEFAULT 'shared' CHECK (… IN ('shared','standalone'))`, in the generic `tasks.update` SET clause), `tasks.imported_opencode`/`imported_opencode_session_id` with the unique partial index `tasks_imported_opencode_session_uidx` (the ownership claim;
**both columns are skipped by the generic SET clause**, written only by `tasks.setImportedOpencode`'s targeted UPDATE, never bumping `updated_at`) and the partial index `runs_opencode_session_id_idx` for the scanner's ownership filter; 080 adds `harness_auto_enabled(harness_id PRIMARY KEY, enabled_at, notified)`
— **deliberately no foreign key to `harnesses` and no column on `harnesses`**: any FK would make the next harnesses rebuild (create/drop/rename) cascade-delete the rows that make a manual Off stick, and a `harnesses` column would be dropped by a parallel branch's explicit-column rebuild.
**Migrations 082 and 083 are the OpenCode server driver's only migrations** ([harness-opencode.md](harness-opencode.md)); 082 is `082_opencode_child_bookkeeping.sql`.
It adds `opencode_stopped_children(child_session_id PRIMARY KEY, task_id, stopped_at)` with an index on `stopped_at`: the child sessions agetor itself interrupted, so the parent's “subagent cancelled” wake that follows reads as the tail of agetor's Stop (decision R4) also after a core restart.
Only `opencode-subagents.ts` touches it, through `opencodeStoppedChildren` in `db.ts` (`noteOpencodeChildStoppedByAgetor` writes, `wasOpencodeChildStoppedByAgetor` reads by primary key); a note counts for 24 h (`OPENCODE_STOPPED_CHILD_TTL_MS`), and older rows are deleted in the same transaction as each write.
It is a table of its own, not a `subagents` column, because the note can come before the child's subagent row exists and a placeholder row would show up as a tab, and it has **no foreign key to `tasks`**: the note must never fail, and a deleted task's rows age out like any other.
082 also adds the partial index `idx_subagents_opencode_status ON subagents(status, task_id) WHERE parent_kind = 'opencode_subagent'`, which the boot linger's `subagents.opencodeOrphanedTaskIdsSince` and the driver's relist (`subagents.settledOpencodeChildSessionIds`) use (both pin it with `INDEXED BY`) instead of scanning `subagents` or loading every row of the task.
083 (`083_opencode_watch_tombstones.sql`, no alias) adds `opencode_watch_tombstones(session_id PRIMARY KEY, harness_id, task_id, expires_at)` with the index `opencode_watch_tombstones_expires_idx` on `expires_at`: the OpenCode sessions a task let go of (delete, archive, harness switch), still watched for 24 h so an execution the server starts on one is interrupted, also after a core restart and after a deleted task's runs are gone.
Only `orchestrator-opencode-server.ts` touches it, through `opencodeWatchTombstones` in `db.ts`: `put` (from `tombstoneOpencodeSessionsOfTask`) upserts one row per session, keeping the later expiry, and in the same transaction deletes expired rows and caps the table at 500 rows (the ones expiring last stay); `live` is read by every watch refresh.
Like 082's table it has **no foreign key to `tasks`**: a deleted task's sessions are the point, and a row ages out like any other.
`tasks.opencode_server` and `agent_profiles.opencode_server` (079) are **retired but kept**: dropping them would need a one-way migration for no user gain, bundles still export and import the field, and routes still accept it, but no UI or CLI surface sets it any more: task create and PATCH, agent-profile routes and bundle import still write the value they are given (validated, stored), and the server driver ignores it (only the `run` driver on v2 reads it through `effectiveOpencodeServer`).
`runs.origin` gains the value `"agent"`: a run the orchestrator minted because OpenCode started an execution on the task's session by itself (a server wake); it is the same text column, so nothing is migrated, and rows before the change read back as before.
The server state is not in SQLite: each harness's URL, password and launch fingerprint are in `dataDir/opencode-servers/<harnessId>.json` (0600), because the server and its state must survive a core and the DB is owned by the core.
Open permission and question cards are not persisted either; the OpenCode server is their source of truth and the driver re-registers them after a restart.
The turn's `server=agetor` breadcrumb is an ordinary status event, not a column.

`harnessAutoEnabled` (`db.ts`: `has`/`record` — INSERT OR IGNORE, keeps the first `enabled_at` —/`pending`/`markNotified`/`all`) is its only accessor.

**Test hygiene for harness rows:** `bun test` runs every file in one process and `db.ts` is a process-wide singleton, so a test that inserts or disables a harness (or records an auto-enable) leaves it for every file that runs after it.
Such a test must `const restoreHarnesses = snapshotHarnessState()` (`src/bun/test-harness-state.ts`, imported after `db.ts`) and call it in `afterAll` — built-ins get their previous `enabled` back, test-only rows and new `harness_auto_enabled` records are removed.

**Archived-history retention** (`src/bun/retention.ts`, `docs/plans/non-blocking-session-restore.md` decisions F–H): `tool_result` payloads over `RETENTION_TRIM_BYTES` (4 KB) on tasks archived at least `archivedHistoryRetentionDays` days (preference, default 30 only when unset or blank, `"off"` disables;
Settings → General → "Archived task history" or `agetor config archivedHistoryRetentionDays <off|1-3650>`; the preference fails closed because the trim is one-way — `PUT /preferences/archivedHistoryRetentionDays` stores an off-word (`off`/`0`/`false`/`no`/`none`/`disabled`, any case) as `"off"` and a day count as its plain integer string (`normalizeArchivedHistoryRetentionValue`), refuses anything else with a 400 naming the accepted values (nothing stored, no pass scheduled), and `parseArchivedHistoryRetentionDays` reads any stored value that is neither as off, never as the default;
`AGETOR_ARCHIVED_HISTORY_RETENTION=0` disables the scheduler outright) are trimmed in place — the **only** in-place rewrite of event history in the codebase, one-way.
A trimmed row stays valid JSON with the marker FIRST — `{"retention":{"trimmed":true,"originalBytes":N,"trimmedAt":ms},"toolUseId":…,"content":<trimmed>,"isError":…,"attachments":…}` (`trimToolResultData` in `src/shared/tool-result-trim.ts`: a string is cut on a code-point boundary + `…`; a block array keeps text blocks in order until the 4 KB budget and replaces image/document/unknown blocks with a `[<type> block removed by retention]` text block;
a plain object is stringified and cut) — so the SQL prefilter `substr(data,1,13) != '{"retention":'` (`TOOL_RESULT_TRIM_SQL`, walking `idx_run_events_run`) skips trimmed rows without parsing (idempotent, crash-resumable); a task whose sweep completed is recorded in the `retention_swept_tasks` table (migration 067, `retentionSweeps` in `db.ts`: `task_id → "<archived_at>:<maxBytes>:<max event id>"`, written per task as its sweep completes
— never after an abort or unarchive — rows for non-candidates pruned each pass, a deleted task's row cascading; its own table rather than a `preferences` blob so it never rides `GET /preferences` / `agetor config ls`) and skipped while that key matches — and the skip path still yields at the top of every task iteration, since a steady-state daily pass skips almost every task (a skip loop with no yield ran ~600 ms cold over 1.2k archived tasks), so untrimmable big rows (non-JSON, envelope-only) aren't re-read daily forever
— a JSONL rebuild (new events) or a re-archive re-sweeps it; the lookup is `runs.maxEventIdForRun` (`INDEXED BY idx_run_events_run`).
`id`, `run_id`, `stream`, `ts`, `subagent_id`, `line_uuid`, `toolUseId`, `isError` and `attachments` are never touched, so unarchive + resume never re-imports a row and the sent-files / TODO parsers keep working.
The pass runs per run in keyset pages sized from the previous page's average row to ~2 MB of data (≤ 200 rows; the first fetch is 8 rows — a fixed 200-row page held the thread for 130 ms on the owner's 4.5 GB DB, the sized pages peak at ~39 ms), one transaction per ~2 MB chunk (which re-checks inside the transaction that the task is still archived past the cutoff — an unarchived task is never trimmed after the fact), yielding every 20 ms; scheduled 90 s after the API is up and then daily (`.unref()`'d, single-flight, `AGETOR_RETENTION_BOOT_DELAY_MS` / `AGETOR_RETENTION_INTERVAL_MS` seams), re-requested 5 s after the preference changes (`requestRetentionPass`, `AGETOR_RETENTION_DEBOUNCE_MS` seam), stopped on shutdown; bookkeeping rides the generic `preferences` store as `retention:lastRunAt` / `retention:lastFreedBytes` / `retention:lastTrimmedRows`.
RunPanel shows a muted `trimmed by retention (original 1.2 MB)` line (`tool-result-trimmed`), as do `agetor logs` and the TUI.

**Compact** (`compactDatabase`: `VACUUM` + `PRAGMA wal_checkpoint(TRUNCATE)`) is manual only — Settings' "Compact database" (confirm with the `(page_count − freelist_count) × page_size × DB_COMPACT_SEC_PER_GB` estimate, then a blocking modal) or `agetor compact [--yes] [--json]` — and is refused (409) while `activeRunCount()` (`active` + `startingTaskIds`) is non-zero or a retention pass runs, because bun:sqlite is synchronous and a VACUUM blocks the core for its whole duration (≈ 7 s/GB).
Routes: `GET /db/stats` (`DbStats`), `POST /db/compact`, `POST /db/retention/run` (400 when the preference is off, 409 while a pass runs).

**Every `run_events` query must SEARCH.** `src/bun/db-run-events-plans.test.ts` runs `EXPLAIN QUERY PLAN` over every `runs.*` / `tasks.*` method that mentions `run_events` (plus the retention SQL) and fails on a `SCAN run_events` or a run-scoped query planned onto `idx_run_events_user_history`; without `sqlite_stat1` SQLite picked that `(stream, id)` index for `lastToolUseData` and the claude API-error probe (`runs.hasPriorApiErrorStatus`) and walked the whole table, so both pin `INDEXED BY idx_run_events_run`.
A new `run_events` method that isn't exercised by that test fails it by name.

## Harness stack tables (migrations 084, 085)

`harness_stacks`, `harness_stack_members`, `harness_limit_state` and
`harness_session_handoffs` are additive; `tasks.harness_state` is another
server-managed column (targeted UPDATE only, no `updated_at`, skipped by the
generic PATCH clause — same rule as `fx_recovery`). `UNIQUE(harness_stack_members.harness_id)`
is the "one stack per account" invariant and `UNIQUE(stack_id, position)` the
order. **No table references `harnesses` by FK**: 084 shipped
`harness_stack_members.harness_id REFERENCES harnesses(id) ON DELETE CASCADE`,
and because `db.ts` turns `foreign_keys` on before `migrate()` (it cannot be
turned off inside a migration's transaction), the documented `harnesses`
rebuild (`DROP TABLE harnesses` = an implicit `DELETE`) would have cascaded
every membership away. Migration 085 rebuilds `harness_stack_members` without
that FK (the cascade from `harness_stacks` stays), and `harnesses.delete`
removes the account's membership row explicitly and re-packs the ranks.
`harness_limit_state` has no FK on purpose: it is account-global and
survives a stack delete. `harness_session_handoffs` cascades with the task; its
`copied_paths_json` is the only allowlist cleanup may remove. Snapshot/restore
for tests covers all three (`test-harness-state.ts`). Model:
[harness-stacks.md](harness-stacks.md).

## Multiple repositories in one task (migration 087)

Migration 087 (`087_task_repositories.sql`) adds two `tasks` columns; the feature is [multi-repo-tasks.md](multi-repo-tasks.md).

- `tasks.repositories` (`TEXT NOT NULL DEFAULT '[]'`) holds the pinned repository set as `TaskRepository[]` JSON. A **single-repository row stores `'[]'`** on purpose: its scalar columns (`branch`, `worktree_path`, `base_ref`, `checkout_branch`, `pr_url`) stay its one source of truth as they update, and `toTask` derives its one-entry array through the shared `repositoriesForTask` (`src/shared/multi-repo.ts`), the same derivation the webview and CLI use. A **multi row stores its entries**: two or more at creation, at least one after repositories are removed (`DELETE /tasks/:id/repositories/:name`, [multi-repo-tasks.md](multi-repo-tasks.md)); its scalars are the workspace mirror: `workdir` is `<dataDir>/worktrees/<task-id>` from creation, `worktree_path` is null until the first start and that root afterwards, and `branch`/`base_ref`/`pr_url`/`checkout_branch` are null. `parseTaskRepositories` validates the stored JSON on read. No backfill.
- `Task.multiRepo` is **derived, never stored**: `toTask` sets it to `true` exactly when the stored set is non-empty (only a multi row stores one), so a one-repository multi row stays multi and keeps its stored entry instead of deriving one from the scalars. It has no column, is not patchable and never bumps `updated_at`. Every multi/single decision reads it through `isMultiRepoTask` (`src/shared/multi-repo.ts`, with a count fallback for an older core's JSON), never `repositories.length`. `tasks.insert` stores the set when `isMultiRepoTask(t)` holds, so a pipeline step copying a one-repository multi parent (`multiRepo: true` on the insert) stores its one entry and stays multi.
- `tasks.issue_repo_path` names the `repositories[].path` whose remote matches `issue_url`; only that repository's PR body gets `Closes #N`.
- **Both columns are server-managed**: skipped by the generic `tasks.update` SET clause, not in `ALLOWED_PATCH_FIELDS`, and never bumping `updated_at`. Their writers are `tasks.insert` (create time, and a pipeline step row copying its parent's set) and four targeted UPDATEs:
  - `tasks.setRepositories(taskId, repos)` persists the materialized paths and branches after a prepare, and the remaining set after a repository removal. On a single row a set of one stores `'[]'`. A multi row is never demoted and never regrows: only incoming entries whose workspace name the row still stores are kept (so a prepare snapshot taken before a removal can't write the removed entry back), any non-empty result is stored, one entry included, and an empty one leaves the row untouched. The caller's array is a snapshot taken before awaits, so a stored `prUrl` or `checkoutBranch` wins over the incoming one (the incoming value is used only when nothing is stored).
  - `tasks.setRepositoryPrUrl(taskId, selector, url)` stamps one entry (matched by name, selected path or worktree path), first write wins; a no-op on a single row (decided by `multiRepo`).
  - `tasks.setRepositoryCheckout(taskId, name, value)` records one entry's last-seen checkout, compare-then-write, and like `setCheckoutBranch` mirrors a pipeline step's write onto its parent's same-named entry in the same transaction. An empty stored set is left alone (a single row's checkout is the scalar column); a one-entry stored set is a multi row and is written.
  - `tasks.clearIssueRepoPath(taskId, repoPath)` sets `issue_repo_path` to NULL only while it still equals `repoPath` (compare-then-write); `removeTaskRepository` calls it for the removed repository, on the task and on each pipeline step row that names it, so no remaining repository's PR claims `Closes #N`.
- `PATCH /tasks/:id` refuses `repositories` (400, pointing at the removal route) and any change to a multi row's `workdir` (400), even before its first start: the workspace root is derived from the set, which can lose entries but never gain them.

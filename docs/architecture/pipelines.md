# Pipelines

> Moved from `CLAUDE.md`, where this was orchestration-flow item 19. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

**Pipelines** (canvas-built, multi-agent-profile step graphs; `docs/plans/pipelines.md`; not to be confused with Claude Code's own `/workflow` background-agent tool — unrelated feature, name-adjacent only): a **pipeline** is a named, reusable graph of **steps** (Settings → Pipelines, or the "Pipelines" header button next to Worktrees), each bound to an Agent profile; running one creates a **pipeline task** (an ordinary board card) that the orchestrator drives through a sequence of hidden **step tasks** — one per executed step, sharing the pipeline task's worktree — each ending its turn with a JSON **handoff** that tells the runner what to do next.

**Vocabulary/storage** (D1/D2): `pipelines` (migration `057_pipelines.sql` — `id, name, name_key UNIQUE, description, graph TEXT, max_steps, created_at, updated_at`, no FK from `tasks.pipeline_id` — `pipelines.delete` is never blocked, mirroring `agentProfiles.delete`, since a started run already owns its own frozen snapshot) holds the *templates*; `058_task_pipeline.sql` adds two independent column pairs to `tasks`, both server-managed, both excluded from the generic `tasks.update` SET clause and from `ALLOWED_PATCH_FIELDS`
— `pipeline_id`/`pipeline_run` live on the **parent** (board) task (`pipeline_run` is the `PipelineRunState` JSON, written only by `tasks.insert`'s initial idle state and `tasks.setPipelineRun`'s own targeted UPDATE, never bumping `updated_at`), and `pipeline_parent_id`/`pipeline_step_id` (indexed) live on a hidden **step** task, written only once by `tasks.insert` at that row's creation and never touched again.

**Run model**: the runner materializes the parent's worktree once via `prepareWorkdir(parent)`, then inserts each step row directly via `tasks.insert` — **never** `createTask` — with the parent's `workdir`/`isolation`/`branch`/`branchSource`/`worktreePath`/`baseRef` copied straight across, so each step's own `prepareWorkdir` hits the reuse-in-place branch (same path, no git call) and `createTask`'s `existingBranch` collision guard never even runs against a step row; the parent's own `agent`/`model`/`effort`/`mode`/`speed`/`maxMode` fields are purely cosmetic (mirror the start step's profile harness, A1) since the parent never spawns an agent — `startTaskInner` branches straight to `startPipelineRun(task)` whenever `task.pipelineId` is set, ahead of every harness/profile pre-flight that only applies to a real spawn.

**Routes** (all `authed`, `server.ts`): `GET /pipelines` → `Pipeline[]` with a server-derived `taskCount` per row (name ASC); `POST /pipelines` → 201 `Pipeline` (400 bad name/description/graph/`maxSteps`, 409 name clash via `PipelineNameError`); `GET /pipelines/:id` → 200/404; `PATCH /pipelines/:id` → 200/404/400/409 (same validation as POST, re-run through `validatePipelineGraph`);
`DELETE /pipelines/:id` → `{ok:true}`/404, never blocked; `POST /tasks` gains a tri-state `pipelineId` (400 on a non-string/non-null wire value; `createTask` itself validates it further — 400 on an unknown id, no resolvable start step, a step with no resolvable agent, or `pipelineId` combined with `agentProfileId`);
`GET /tasks/:id/pipeline` → `{task, steps}` (404 unknown task, 400 `"task is not a pipeline task"`); `POST /tasks/:id/pipeline/advance` (body `{nextStepIds: string[]|null, handoff?, fromTaskId?}`) → `Task` (400 bad body/unknown step id, 404, 409 nothing to advance or the target's task is still genuinely live);
`POST /tasks/:id/pipeline/retry` (optional `{taskId}`) → `Task` (404, 409 not blocked/cancelled); `POST /tasks/:id/pipeline/cancel` → `Task` (404, 409 not running); `POST /tasks/:id/pipeline/restart` → `{runId, pending?}` (404 unknown task, 400 not a pipeline task, 409 for every other `startPipelineRun` failure)
— the **only** way to re-run a `done` pipeline from scratch, since `startPipelineRun` itself now refuses that (see Retry/Restart below); `DELETE /tasks/:id`, `POST /tasks/:id/archive` and (round 4) `POST /tasks/:id/start` 409 (`"step task belongs to a pipeline — act on the pipeline task"` / `"step task is managed by its pipeline — retry the pipeline task instead"`) for a direct step-row request (`isPipelineStepTask` **and not** `isOrphanedPipelineStep`
— an **orphaned** step, whose parent row is gone, e.g. an interrupted delete, bypasses this refusal and can be deleted/archived directly, since there's no parent left to "act on instead"), and a step row's `PATCH /tasks/:id` 409s `"step task's column is managed by its pipeline"` specifically when the patch touches `column`
— every other field (title/prompt/…) stays ordinarily patchable on a step row.
A pipeline PARENT's `column` is equally runner-owned (round 4): `PATCH /tasks/:id` 409s `"pipeline task's column is managed by its run"` when the patch would change it (a same-value resend passes), except a finished run (`pipelineRun.status === "done"`) may be parked in the Done column (`column: "done"`) — the card's Done button, the run view's Done button (`pipeline-run-done`), a drag onto Done, and `agetor move`.
Every other column change still 409s.
The board refuses every other drop of a parent card, and `persist()` only mirrors the column when `run.status` actually changed — so that park survives later bookkeeping, and a Restart (a real status change) pulls the card back — a drag used to desync the mirrored column until an unrelated persist snapped it back.
`GET /tasks` (the 2 s poll) ships a TRIMMED `pipelineRun` per task — `history[].handoff`/`joins[].arrivals[].handoff` nulled, `snapshot.profiles` emptied (`trimPipelineRunForList`, route-layer only in `server.ts`; `tasks.list()`/`tasks.get()` and every other route stay full) — so the board never re-ships every handoff and profile snapshot of every (even archived) pipeline forever; the full state comes from `GET /tasks/:id` / `GET /tasks/:id/pipeline`.
`GET /tasks/:id/interactions/pending` unions a pipeline parent's STEP interactions (via `stepsForParent`), so the `!N` a parent advertises on the board, `agetor ls` and the TUI is answerable by that same id (`agetor answer <parent>`, TUI `g`; `show`/`answer`/the TUI overlay name the step task a card belongs to).

**The runner** (`src/bun/pipeline-runner.ts`) subscribes to `orchestrator.ts`'s `subscribeGlobal` for `run-status` (terminal outcomes) and `column` events (ignoring its own `reason:"pipeline"` writes, to avoid a feedback loop) via `initPipelineRunner()` — **this MUST be called before `reconcileOrphans()`** (both `index.ts` and `headless.ts` call it right there, at boot) so a step's own boot-time `orphaned`→`ready` run-status event reaches the listener and flips its pipeline parent back to `ready`/`cancelled`-with-retry;
it's idempotent (a module-level guard), but **any test that drives a real pipeline run** (not just the pure `src/shared/pipeline.ts` functions) **must call `initPipelineRunner()` itself or step settles never propagate and the run hangs in `"running"` forever** — and waiting on a step task's `column` alone is not proof the runner actually processed a settle (a settle can land after the column write);
a test needs to poll the pipeline task's `pipelineRun.history`/`status` instead.
Right after that boot-time `reconcileOrphans()` finishes, both `index.ts` and `headless.ts` call `reconcilePipelineRuns()` (M16) — a self-heal sweep over every non-archived pipeline parent whose run is `running` (or `blocked` with something still `active`): for each active execution `isTaskRunLive` says is no longer genuinely busy, it re-reads that step task's latest run row and feeds it through the same settle path a live event would (or records `step-failed` "never started" if no run row exists at all) — this catches a step settle the runner's listener genuinely never saw (e.g. a process crash between the settle and the handler completing).
Each entry is handled independently and a thrown exception is caught and recorded as its own `step-failed` block rather than aborting the whole sweep or leaving that one execution stuck forever.
Every mutation of one parent's `pipelineRun` — a manual route call or an async step settle/column event — is serialized through a per-parent promise chain (`runExclusive`, exported as `withPipelineLock`) so two sibling fan-out branches settling moments apart (or a manual advance racing a settle) never race a read-modify-write of the same JSON blob; `deleteTask`/`archiveTask` run their pipeline cascades through this same lock (see Cascades below).
`persist()` is the single choke point every mutator ends on: recomputes `run.status` via `deriveRunStatus` (blocked wins outright, else running if anything's `active`, else preserves an explicit stored `cancelled`/`idle`, else `done`) unless `preserveStatus` is passed (Cancel's own path — it needs `active[]` to survive so a later Retry can re-attempt those exact executions), persists via `tasks.setPipelineRun`, mirrors the parent's board column (`running`→running, `blocked`→blocked, `done`→review, `cancelled`→ready) through `pipelineUpdateColumn`
— a thin `updateColumn(..., reason:"pipeline")` export that's also what the runner's own column listener explicitly ignores — and broadcasts a `GlobalEvent{kind:"pipeline", taskId, status, activeStepIds, stepCount, ts}` (D12) the run view subscribes to for sub-poll-latency animation — delivered through `App.tsx`'s single `subscribeGlobalEvents` handler, which forwards every `pipeline`/`column`/`run-status`/`interaction` event into the module store `src/mainview/lib/pipeline-events.ts` (`publishPipelineGlobalEvent`/`subscribePipelineGlobalEvents`, same spirit as `lib/clone-progress.ts`) that both `PipelineRunView` and RunPanel's pipeline-strip cache subscribe to
— never a second event stream (WKWebView's ~6-connection cap, see [clone-repository.md](clone-repository.md)); the run view also caps its per-poll `listSubagents` fan-out at 2 concurrent (`mapWithConcurrency`) and prunes `liveSubagents` to the current step ids.

**Freeze-at-run-start** (D8): before ever reaching `buildSnapshot`, `startPipelineRun` now runs `validatePipelineGraph` on the stored graph itself (Major 5, round-2 review fixes) — a structurally invalid graph (a hand-edited row, or an edge pointing at a step id that doesn't exist) refuses the run outright with `"pipeline graph is invalid: <reason>"` before anything is captured onto a snapshot, and the same validation runs against a restart-off-a-deleted-pipeline's frozen `run.snapshot.graph` fallback too; `buildSnapshot` itself now takes the already-validated/normalized `(graph, maxSteps, now)` rather than the whole `Pipeline` row, since validating is the caller's job.
On the first Run, `buildSnapshot` resolves that graph plus every `AgentProfileSnapshot` any step (or any step's `subagents.profileIds`) references, refusing to start at all if any step has no `agentProfileId`, a referenced profile no longer exists, or that profile's harness no longer resolves; the frozen `{graph, maxSteps, profiles, capturedAt}` lands on `run.snapshot`, and each inserted step task copies its bound profile's fields straight off the snapshot, plus the **parent's own `references`** (`TaskReference[]`) verbatim, on top of whatever handoff-file reference that step's own launch adds
— `orchestrator.ts`'s `effectiveAgentProfile` has an added guard (`task.pipelineParentId` set → always `{profile: task.agentProfile, source:"snapshot"}`) that keeps a step task out of the live-until-first-run window entirely, so even a step's very first run launches with the frozen snapshot, never a possibly-since-edited live profile.
A worktree-isolated step task's own `startTaskInner` never materializes its own worktree — it's gated on `task.isolation === "worktree"` and refuses with `"step task's worktree is missing — run the pipeline task instead"` when `worktreePath` is unset or no longer exists on disk; only the pipeline task's own Run/Retry/Advance path (via `refreshParentWorktree`, below) (re)materializes the one shared worktree every step reuses — an `isolation:"none"` step legitimately has a `null` `worktreePath` and never reaches that branch at all.

**The `<handoff>` contract** (D3, `src/shared/pipeline.ts`): every step's composed prompt (`composeStepPrompt`) asks the agent to end its final message with exactly one `<handoff>…</handoff>` block of JSON `{schemaVersion:1, purpose, summary, reason, next, artifacts:[], openQuestions:[], status?:"done"|"blocked"}`;
`parseHandoff` finds the **last** matching block in the trailing `PIPELINE_LIMITS.handoffScanTailBytes` (256 KB) of the run's main-stream assistant events (passed as one segment per event; see **Formatted handoff** below for the code-span rule) — via `findHandoffBlocks` (`src/shared/handoff-locator.ts`), a LINEAR forward tokenizer, never a regex: the original `<handoff…>([\s\S]*?)</handoff>` exec loop was quadratic in unclosed `<handoff>` opens (20k opens in 222 KB of agent-controlled text stalled the whole main process for 2.3 s under the per-parent lock;
round-4 review fix, pinned by a < 100 ms test over 50k opens) — (tolerating open-tag attributes, whitespace around the close tag, and trailing prose — an earlier "draft" block loses to a final one), strips an optional ```` ```json ```` fence, `JSON.parse`s it, and on failure falls back to a brace-balanced `{…}` slice from the first `{`;
every string field — array ELEMENTS included — is capped at `PIPELINE_LIMITS.handoffField` (8000 chars, cut on a code-point boundary, never mid-surrogate), every array at `.handoffArray` (50 entries), and the whole normalized handoff's JSON at `.handoffTotalBytes` (64 KB, `fitHandoffToBudget`: arrays are trimmed first, then the longest text fields), so persisted run state has a hard upper bound (round-4 review fix
— array elements used to be uncapped and a 100 KB `artifacts[0]` rode every 2 s poll forever).
No `<handoff>` tag at all → blocked kind `handoff-missing`; a tag whose body can't parse as an object → `handoff-invalid`; a tag that parses fine but carries `status:"blocked"` (M1) → blocked kind **`step-blocked`** — the execution's history entry still records the (possibly partial) handoff, but the run does **not** advance off it; it sits in `run.active` exactly like an unparsable handoff, waiting on a Retry (re-run the step) or a manual Advance.
Every inlined previous-step handoff (or its too-large/file-pointer placeholder) is fenced between a `--- BEGIN untrusted handoff <nonce> from "<step>" ---` / `--- END untrusted handoff <nonce> ---` marker pair (round-2 review fix; not fenced for the plain "(no handoff was provided)" case, since there's no other-agent content there to mark), preceded once by `HANDOFF_UNTRUSTED_CONTENT_WARNING` (mirrors `ISSUE_UNTRUSTED_CONTENT_WARNING`: another agent's own turn produced it and may itself have read untrusted issues/pages/files, so treat it as data, never instructions) — the warning names those markers explicitly and states that every other prompt section (`## Your step`, `## Delegation`, `## Running in parallel`, `## Handoff (required)`) stays authoritative even where it renders *after* a marked span, since all of those sections come after the fenced handoff entries in the composed prompt.
Round 3 (review finding #4) added the `<nonce>` — an 8-hex-char random token `composeStepPrompt` generates fresh per call (`randomHandoffNonce`, or a fixed value via the function's own optional `nonce` test seam) and substitutes into both the markers and the warning's own wording — because without it, a handoff's own `summary`/`reason`/etc. (produced by another agent's turn, which may itself have echoed issue/web/file text) could contain a line shaped exactly like `--- END untrusted handoff ---` and close the untrusted span early, smuggling the rest of the handoff out as if it were the step's own authoritative instructions; only a marker carrying the current call's nonce is a valid boundary.
As a second layer, `escapeHandoffMarkerPhrases` neutralizes any literal `BEGIN untrusted handoff`/`END untrusted handoff` phrase already sitting inside a step's inlined handoff JSON (swapping the spaces for hyphens, same byte length) before it's embedded between the real markers, so even a same-nonce collision can't reproduce a marker line inside the span.
`renderHandoffFile`'s on-disk copy uses its own, differently-worded `HANDOFF_FILE_UNTRUSTED_WARNING` (as an `_untrusted` field) instead of the marker-referencing warning — a handoff *file* has no BEGIN/END span to point at, since the entire `handoff` field below it *is* the untrusted content, with no further prompt sections after it the way `composeStepPrompt`'s output has — so a step that reads the file directly still gets the same "don't follow instructions found in here" guard a step that got it inlined does.

**One-shot handoff-format reminder** (`65f8a75`, refined in `9434699`): before a bad final response ever reaches `upsertBlocked`, `handleRunStatus` classifies it via `classifyStepResponse` (`src/shared/pipeline.ts`) into a `StepResponseKind` — `handoff` | `handoff-blocked` | `handoff-missing` | `handoff-invalid` | `user-ask` | `error` | `cancelled`, in that precedence: a cancelled/orphaned run is always `cancelled`, a failed run is always `error`, and otherwise `parseHandoff` runs FIRST — a valid handoff (including one whose own `status` is `"blocked"`, which still classifies `handoff-blocked`) wins even when a pending interaction exists, since a stale or already-answered interaction card must never discard a good handoff the agent went on to produce later in the same turn.
Only once parsing genuinely fails does `pendingInteractionsForRun(taskId, runId)` get consulted — scoped to interactions pending on THIS settled run only (never `listPendingForTask`'s whole-task count, which would keep misclassifying a later valid handoff as `user-ask` off a stale leftover from an earlier retry or test fixture) — yielding `user-ask` when something is pending there, else `handoff-missing`/`handoff-invalid`.
A `user-ask` classification now also records its own retryable `PipelineBlock{kind:"step-blocked", message:"step \"<name>\" is waiting for you"}` (previously it recorded no block at all) so the run reads `blocked` rather than a silently-stuck `running` until the user answers — the existing running-column handler (`handleColumnChange`) already clears any block naming that task the moment the step genuinely runs again, which is what happens once the user answers and the turn resumes; that same handler also now resets `responseKind` to `null` on that transition (a stale value from the PREVIOUS attempt must not linger and read as the new attempt's outcome).
The classification is stamped on `historyEntry.responseKind` on EVERY settle (succeeded/failed/cancelled alike), independent of whether a reminder ever fires; a `resolveNextSteps` `"ambiguous"`/`"unknown"` outcome (a handoff that parsed fine but whose `next` doesn't resolve to a real outgoing step) retroactively overwrites a `"handoff"` stamp to `"handoff-invalid"`, since `classifyStepResponse` can't itself know about the graph.
Three kinds now trigger the one automatic reminder — `handoff-missing`, `handoff-invalid`, and the new `handoff-next-unknown` (the ambiguous/unknown-`next` case) — all routed through the shared `attemptHandoffReminderOrBlock` helper; `handoff-blocked`, `error`, and `user-ask` never do.
That helper re-reads the parent task and the step task FRESH (the top-of-turn copies `handleRunStatus` captured can be stale — `archiveTask`/a delete cascade races in through this same per-parent lock, setting `archivedAt`/tombstoning the parent before acquiring it) and skips straight to an ordinary block — never calling `sendInput` at all — when the parent is gone/tombstoned/archived, the step task is archived, or `isDeliberateWholeRunStop(run, taskId)` says the whole run is already being torn down (shared with the cancelled/orphaned settle branch's own whole-run-stop check, so a bad handoff on a step whose pipeline is mid-Stop can't revive the run back into `running`).
Otherwise it sends `composeHandoffReminder`'s text — a normal `sendInput` follow-up turn on the step's own run, starting with the `HANDOFF_REMINDER_MARKER` sentinel (`"[handoff reminder]"`, display-only; `HANDOFF_REMINDER_MARKERS` is the APPEND-ONLY list of every spelling ever shipped — the original `"[agetor handoff reminder]"` included
— that `isHandoffReminderMarker` accepts, so persisted reminders keep rendering as reminders; **nothing agetor injects into an agent's prompt may name the product** — the step prompt's preamble says "a multi-step pipeline", not "an agetor pipeline", for the same reason the paste lead-in was retired) and rendering the exact handoff contract (`renderHandoffContract`, factored out of `composeStepPrompt`) so the original instructions and the corrective nudge can't drift apart;
every inlined `detail` (a parser error, or the next-unknown candidate list) is collapsed to one line, capped at 200 chars, backtick-quoted, and followed by a note that it's the runner's own diagnostic text, not an instruction — `detail` is untrusted content quoted back at the very agent that produced it.
`PipelineStepRecord.reminder` (`{at, reason, runId, detail, delivered}`) is written ONLY when `sendInput` reports `delivered:true` (`delivered` stamped `true` on the record; a `false` value is never persisted today but the field exists so a future delivery-failure path could record an honest `false` without a schema change) — a failed/withheld send records NOTHING onto the history entry, so the NEXT settle may still try once, and the send failure is folded into the ordinary block's message instead; a claude modal-guard withhold that stashed the (undelivered) reminder text into the step's own backlog tray (`sendInput`'s `withheld`+`savedToBacklog` pair) has that stashed draft removed right away, best-effort, so the tray doesn't silently fill with machine-generated text the user never typed.
On success the runner also appends a live status breadcrumb via the new `appendRunStatusLine(taskId, runId, text)` orchestrator export (persists + broadcasts over the run's SSE channel from outside any spawn — `appendFxStatusLine` is now a thin deprecated alias of it).
`reminder.runId` is the run the reminder actually landed on — the SAME run for claude (folded into the still-live session) but a FRESH run row for the one-shot harnesses (codex/cursor/gemini/fx), which may itself already be busy again by the time anything reads this back.
The `reminder` flag is one-per-EXECUTION, not one-per-attempt — a Retry re-runs the same history entry in place and does NOT clear it, so a second bad response after a Retry still counts as "already reminded" and blocks immediately with a `"still no valid handoff after one reminder — "` prefix (`handoff-next-unknown` maps onto the `handoff-invalid` block kind, since a bad `next` is really a malformed/ambiguous handoff, not a distinct block kind of its own).
`db.ts`'s `sanitizeStepRecord` whitelist (`sanitizeResponseKind`/`sanitizeStepReminder`) round-trips both new fields (plus `handoff-next-unknown` in the reason set, plus a `delivered` boolean defaulting to `true` for a pre-field row) through the persisted `pipeline_run` JSON — without it, a reloaded run would drop `reminder` on every read and the one-shot gate would send a fresh reminder every poll/settle instead of exactly once.
Fake-driver parity: `FAKE_CLAUDE_HANDOFF_PROMPT_MARKER` gained two-turn suffixes — `missing-then-done`/`invalid-then-done` (and the general `missing-then-<token>`/`invalid-then-<token>`) behave like `missing`/`invalid` on a task's first fake-driver turn and like plain `<token>` on every turn after, tracked by a per-task turn counter (`fakeHandoffTurnCounts`, capped at `FAKE_HANDOFF_TURN_MAP_CAP` = 1000 entries with FIFO eviction) — because the reminder text itself carries no marker, `resolveFakeHandoffPromptSource` falls back to the task's own stored (turn-1) `prompt` (`agents.ts` importing `tasks` from `db.ts` — safe, no cycle, `db.ts` never imports `agents.ts`) whenever the CURRENT turn's prompt carries none, so the scenario a step's original prompt selected keeps resolving the same way across the reminder round-trip.
Display: a reminder is an ordinary `user` event whose first line is the marker, so both `src/shared/user-message.ts`'s `userMessageLines` (CLI `agetor logs`/TUI — labels it `agetor›`, marker line stripped) and RunPanel's `UserMessageBlock` (webview — strips the marker line, renders a small `HandoffReminderBadge` ("Automatic handoff reminder", `handoff-reminder-badge`) above the bubble) intercept it BEFORE their normal command/tagged-message parsing, since the reminder's body legitimately names an unbalanced `<handoff>`/`</handoff>` pair (it quotes the tag it forgot, then repeats the contract) that would otherwise mis-segment as a top-level tag spanning most of the message — it always renders as one plain line/bubble instead.
UI: the run view's history rows grow a `pipeline-run-response-kind` chip (`responseKindLabel` in `src/mainview/lib/pipelines.ts`, tone-mapped success/warning/danger/muted) and, when a reminder was sent, a `pipeline-run-reminder` chip reading "Reminder sent"/"Reminder failed" (`data-delivered`, tone warning/danger) with its timestamp; the still-active step node shows a small spinning-arrow glyph (`pipeline-step-reminded`, via `stepReminded`) while its current execution has been reminded and hasn't settled since.
CLI: `agetor pipeline status <ref>` appends a dim `[<responseKind>]` tag and, when reminded, a yellow `(reminder sent)` or red `(reminder failed)` tag to each history line.
`resolveNextSteps` decides what runs next: a step's `transition:"all"` always fans out to every outgoing target (deduplicated), ignoring `next` entirely; `transition:"choose"` (default) with zero outgoing edges is terminal, exactly one edge is taken unconditionally (`next` ignored), and with several edges `next` (trimmed, case-insensitive) is matched against a target step's name, then its id (exact), then the connecting edge's label — no `next` given is `"ambiguous"`, a `next` matching nothing is `"unknown"`, both surfacing as `handoff-invalid` blocks naming the candidates.
A step's `join:"any"` (default) starts a **fresh execution on every arrival** — how cycles work, the same step can run many times, each a new `history` entry (`PipelineStepRecord.nextStepIds: string[]` records what actually got launched off it — empty for a terminal/failed/cancelled/still-pending execution), bounded by the run's *effective* step cap → blocked kind `step-cap`; `join:"all"` instead accumulates `{fromStepId, seq, handoff}` arrivals per step id in `run.joins` and only launches once every distinct incoming step (per the frozen graph's edges) has arrived this generation — a run with nothing left `active` and no pending human gate (whose Accept can still deliver an arrival) but a still-partial join blocks run-level (`taskId:null`) as `join-incomplete`, naming the missing sources, resolvable only via Retry or manual advance (which launches the join step immediately with whatever handoffs did arrive).

**Step cap and its extension** (M2): `effectiveStepCap(run)` (`src/shared/pipeline.ts`) is `snapshot.maxSteps` (default 25; an integer in 1..200 or REJECTED — 400 at the route, a thrown error from `resolveMaxSteps` at the db layer — never clamped; round-4 review fix, the two layers used to disagree) scaled by `1 + (run.capExtensions ?? 0)` — additive, not multiplicative (one extension is 2x `maxSteps`, two is 3x, not 4x) — rather than the block being a dead end.
A single Retry call increments `run.capExtensions` **at most once** even if the run somehow queued more than one pending `step-cap` block (Minor 10, round-2 review fix) — the formula doesn't change, but one Retry click must not silently apply several extensions at once.

**Blocks are structured, and three kinds are run-level "pending" retries, not per-execution ones**: a run-level block (`taskId`/`stepId` both null — `step-cap`, `profile-missing`, `join-incomplete`) carries a `PipelineBlock.pending: {stepId, arrivals}` payload naming the exact launch a Retry should re-attempt, rather than the runner re-deriving it.

**Retry** (`POST …/pipeline/retry`, and plain Run/`POST /tasks/:id/start` on a `blocked`/`cancelled` run absent `opts.restart`) is the single `performPipelineRetry` path shared by both: refuses an archived parent, re-verifies (`refreshParentWorktree`) and re-propagates the shared worktree onto every still-active step row (`propagateWorktreeToActiveSteps`
— a stale/moved `worktreePath`/`branch` on the parent is copied onto each active step task before anything relaunches), then re-`startTask`s every active execution whose task isn't still genuinely `running` (checked via `isAnyRunOfTaskLive` — any live run of the step task, a displaced one included — not the laggier `column`
— a still-mid-turn fan-out sibling is left alone) and, unless a specific `taskId` was targeted, **also** retries every run-level `pending` block (extending the step cap at most once per call, dropping the now-stale `run.joins` entry for a resolved `join-incomplete`, then re-launching via a freshly-refreshed worktree it need not re-fetch per target
— Minor 15) — this is M2's "dead-end" fix: a `step-cap`/`profile-missing`/`join-incomplete` block with nothing in `run.active` used to have no way forward besides a full restart.

**A `blocked`/`cancelled` run's plain Run is always retried in place this way — never a fresh run** — absent `opts.restart`, `startPipelineRun` routes `blocked`/`cancelled` straight to `performPipelineRetry` regardless of whether anything is currently `active`, so history and the snapshot are always preserved; a `done` run instead refuses on plain Run (`"pipeline already finished — restart it explicitly"`).

**`opts.restart` now means a genuine fresh run for ANY non-running status** — blocked, cancelled, done, or even idle (a harmless no-op there, since idle already falls through to the fresh-run code with nothing to cancel) — not just `done` as before this round of review fixes (Major 3): it re-validates the graph, re-captures the snapshot, resolves the start step, and refreshes the shared worktree
— the same validate/snapshot/resolve/worktree-prepare sequence a fresh idle run goes through, up front — and only *then*, once the restart is known startable, best-effort-cancels whatever in the run being replaced `isTaskRunLive` still says is genuinely live (nothing useful to hand off to a run that's about to discard this history anyway) before discarding `history`/`blocked` wholesale and inserting a brand-new step task rather than reusing the existing one
— a restart of a `blocked` run used to silently fall into the M2 retry-in-place branch above instead of actually starting over.
Round 3 (Minor 3) reordered this: cancelling the still-live executions used to happen *first*, before the fresh run's own graph/profile/worktree preflight — so a restart that turned out to fail (invalid graph, a missing agent profile, a worktree failure) had already killed the very executions it would have replaced, leaving nothing running and nothing new started; now the cancel only fires after every one of those checks has passed.
Only `POST /tasks/:id/pipeline/restart` passes `opts.restart` (run view `pipeline-run-restart` button, now showing for `done`/`cancelled`/`blocked` alike with an inline confirm warning that history will be cleared, or `agetor pipeline restart <ref>`) — a plain Run/`POST /tasks/:id/start` never discards history regardless of status.
Both `POST …/pipeline/advance` and `POST …/pipeline/retry` opt out of the server's idle request timeout (`server.timeout(req, 0)`), exactly like `/tasks/:id/start`, since either route can itself (re-)launch a step and therefore (re-)materialize a worktree.

**Manual advance** (`POST …/pipeline/advance`) refuses (409) an archived parent and — new in M4 — a target execution whose task still has a genuinely live run (`isAnyRunOfTaskLive`, not `column`: you can't hand-pick the next step for a turn that hasn't actually finished); it also re-verifies/re-propagates the shared worktree exactly like Retry before acting.
It targets `fromTaskId` when given, else the sole execution blocked on its own handoff (`handoff-missing`/`handoff-invalid`/**`step-blocked`** — M1 folds all three into the same auto-detect set), else the sole `join-incomplete` run-level block, else the sole active execution sitting in the `review` column — 409 otherwise; `nextStepIds:null` ends that path (history outcome `"advanced-manually"`); a non-null array launches each named step (joins bypassed — a manual advance into a join step runs immediately with whatever arrived).

**Cancel** (`POST …/pipeline/cancel`) `cancelRun`s every currently-running active execution and sets `status:"cancelled"` while deliberately keeping `active[]` populated (`preserveStatus:true`) so a later Retry re-attempts exactly those executions; 409 if nothing's running.

**Step-level Stop is different and deliberately doesn't cancel the whole run** (M5): pressing the ordinary Stop button on one step task's own `RunPanel` (`cancelRun` on that step, not the pipeline-level cancel route) forces the **whole** run to `status:"cancelled"` (and the parent back to `ready`, via `finalizeCancelled`) only when no *other* active execution is still genuinely live;
a Stop on one branch of a fan-out instead records a per-task `step-failed` block on that execution (`"step \"<name>\" was stopped — retry it or advance past it"`, Major 1, round-2 review fix) so the run reads `blocked` the moment the stop is processed — never silently stuck `running` forever with a dead-end execution sitting in `run.active` and no block to surface it
— and keeps reading `blocked` even once every still-live sibling finishes too, since that block just sits there until a Retry (re-runs the stopped step in place) or a manual Advance resolves it (round 3: Advance's own `ADVANCE_BLOCK_KINDS` now accepts a task-level `step-failed` block too — but only once its task genuinely isn't live any more
— so a stopped branch can be skipped past, not just re-run in place).

**A WHOLE-pipeline Stop on a fan-out (`cancelPipelineRun`, the run view's header Stop button) must never leave one of these per-task blocks behind** (Major 1, round 3): `cancelPipelineRun` force-sets `run.status = "cancelled"` via its own `finalizeCancelled` call before any of the siblings it just told to cancel actually settle, so each settling execution's own handler checks `run.status === "cancelled"` on entry
— or, when every *other* still-live sibling is itself mid-cancellation (`isTaskRunCancelling`, a new orchestrator export alongside `isTaskRunLive` that reads the in-memory `active` handle's own `cancelled` flag rather than waiting for the async `active.delete` that follows `kill()`) — as the signal that this settle is part of a deliberate whole-run stop, not an isolated one-step Stop;
either condition routes straight to the idempotent `finalizeCancelled` instead of recording a `step-failed` block, so a fan-out Stop from the run view always ends cleanly `cancelled`, never `blocked` with stray "was stopped" entries from siblings that hadn't all settled yet.
`finalizeCancelled` (shared by `cancelPipelineRun`, this Stop path, and — transitively — `reconcilePipelineRuns`'s missed-settle sweep) only forces `run.status = "cancelled"` when `run.blocked` is empty; otherwise it persists normally so `deriveRunStatus`'s existing blocked-wins-over-cancelled priority keeps the real blocked reason visible instead of silently overwriting it with a bare, unexplained "cancelled" (Minor 6).

**A settle racing an archive** (Major 2): `archiveTask` sets `archivedAt` on the parent row *before* it ever acquires the per-parent pipeline lock a step's settle also needs, so a step can become launch-eligible while its parent is mid-archive; the launch loops in `handleRunStatus`/`advancePipeline` re-read the parent fresh and check `archivedAt` before ever calling `launchStep` or touching the worktree, and an archived parent gets `holdForArchivedParent` instead — a retryable run-level `step-failed` block (`taskId:null`, carrying `pending` with the step and its arrivals) with no step task inserted and no worktree touched, resolvable via Retry once the parent is unarchived; the settling execution's own history entry is still recorded correctly despite the hold.
Every launch loop that can resolve more than one next step from a single settle or manual advance (a `transition:"all"` fan-out, several hand-picked `advancePipeline` targets, or a join that just completed alongside other targets) routes each target through `launchTarget` (Minor 14) rather than calling `launchStep` directly — a throw from one target's launch is caught and recorded as its own retryable `step-failed` block instead of aborting the rest of the batch, so the other targets (already launched or about to be) are unaffected; the batch's shared worktree is refreshed **once** up front instead of once per `launchStep` call (`skipWorktreeRefresh`, Minor 15).
Round 3 sharpened where that caught throw gets recorded: `launchTarget` now distinguishes a throw that happened *before* `launchStep` ever inserted the step's task row from one that happened *after* — checking whether `step.id` gained a new entry in `run.active` across the call — and a pre-insert throw also rolls back the `run.stepCount` bump `launchStep` makes before it ever reaches the insert, so the step-cap accounting can't read as inflated by a step that was never actually created.
A pre-insert throw keeps today's run-level `pending` block (`taskId:null`, Retry re-attempts the launch from scratch); a post-insert throw instead records the block against the already-inserted task (`taskId:<inserted>`, no `pending`) so Retry re-runs that execution in place instead of inserting a duplicate on top of it.
`retryPendingBlocks` (the run-level Retry's sweep over every run-level `pending` block) now goes through this same `launchTarget` rather than calling `launchStep` directly too (Minor 7, round 3) — previously a throw there aborted the rest of that sweep instead of being caught into a retryable block.
Round 3 also narrowed an *un-targeted* run-level Retry (no specific `taskId`): it now only re-`startTask`s an active execution that's actually stuck — one carrying its own `run.blocked` entry, or whose latest `run.history` outcome recorded `failed`/`cancelled` — never one quietly sitting in `review` awaiting a human's manual Advance decision (Minor 9); a Retry aimed at a specific `taskId` (the per-step Retry button) is unaffected and still fires on the named execution unconditionally, as before.
Every non-null previous handoff a step receives is additionally written to `dataDir/pipeline-runs/<parentId>/handoff-<run.startedAt base36>-<seq>-from-<fromSeq>.json` (namespaced by run generation since round 4, so a Restart's reset `seq` can never overwrite the replaced run's files; written only AFTER the step row is inserted, and any partial write is removed before a throw propagates) and attached to the next step's launch as a path-only `TaskReference` (mirrors the issue-thread snapshot pattern); `cascadePipelineDelete` removes the whole directory.
`composeStepPrompt` always tries to inline the previous handoff(s) as JSON, bounded by a **whole-entry** `PIPELINE_LIMITS.handoffInlineMaxBytes` (16 KB) budget across all inlined handoffs combined — a single handoff's JSON is either inlined complete or, once the running total would exceed the budget, dropped entirely in favor of a "(handoff too large to inline — saved to `<path>`)" reference; it is never truncated mid-JSON.
For a **gemini**-bound step specifically, if the *whole* composed prompt (inlined handoffs and all) would exceed gemini's 4 KB one-shot argv cap (`promptByteOverage("gemini", composed)` — gemini has no deferred-paste fallback, unlike claude's persistent REPL), the step is instead re-composed once with `inlineHandoff:false` — dropping **every** previous handoff to a file-path reference in one shot, not a partial trim — since there's no cheaper way to shed exactly enough bytes.

**Persistence leniency**: `parsePipelineRunState` (a run's frozen `pipeline_run` column) deliberately does **not** deep-validate `snapshot.graph` via `validatePipelineGraph` on every read — that graph was captured exactly once, at run-start, by `buildSnapshot`'s own validation call, and nothing ever mutates it afterwards, so re-validating it on every task poll would only re-check something that can't have changed; `sanitizeRunSnapshot` only shape-checks enough to make it safe to hand to the step-resolution helpers (an object with array `steps`/`edges`), collapsing anything less to `null` (an un-runnable snapshot is as good as none).
The **live** `pipelines.graph` column (the editable template, not a frozen run snapshot) is the opposite case: still deep-validated via `validatePipelineGraph` on every read, but a stored value that parses as JSON yet now fails validation (e.g. an older/looser validator wrote it, and today's is stricter) is returned **as-is**, with a `console.warn`, **only when it's still shape-safe** enough to hand to the editor and the step-resolution helpers — a plain object with array `steps`/`edges` and a `startStepId` that's a string, `null`, or `undefined` (round-2 review fix) — the editor reads a shape-safe-but-invalid value straight through, and collapsing every failed-validation value would let an unrelated edit-and-save silently overwrite the user's real graph with nothing.
Round 3 tightened that per-array shape check further (`isShapeSafePipelineStep`/`isShapeSafePipelineEdge` in `db.ts`): each `steps` entry must additionally be a plain object with a string `id` and a `position` that's itself a plain object with finite-number `x`/`y`, and each `edges` entry must be a plain object with string `from`/`to` — `rec.steps.every(...)`/`rec.edges.every(...)` gate `parsePipelineGraph`'s success branch alongside the existing `Array.isArray`/`startStepId` checks, so a bare string in `steps`, a step missing `position`, or an edge missing `from`/`to` now falls through to the same "shape-unsafe" handling as a non-array `steps`/`edges` — never reaching the editor or the step-resolution helpers, which index into `id`/`position`/`from`/`to` unconditionally.
Anything looser than that shape (not a plain object, non-array `steps`/`edges`, a `startStepId` of some other type, or now a malformed step/edge entry) collapses to the empty graph instead, also warned — there's nothing safe to index into otherwise; genuinely unparsable JSON collapses to `{steps:[],edges:[],startStepId:null}` the same way it always did.

**Formatted handoff** (`docs/plans/formatted-handoff.md`, grill `docs/plans/formatted-handoff-grill.md`): the runner and every renderer locate a handoff through ONE shared scanner, `findHandoffBlocks` in `src/shared/handoff-locator.ts` (no dependencies but `PIPELINE_LIMITS`; `pipeline.ts` re-exports `HANDOFF_TAG`).
It has two modes.

**Code-aware** (default): prose is scanned as Markdown, so a tag inside an inline code span (a backtick run closed by a same-length run in the same paragraph, earliest span wins) or a fenced block (≥3 backticks/tildes at any indentation, behind `>` markers too; 4-space indented code is NOT code) is not an open tag;
a paragraph also ends at an ATX heading line (its own one-line paragraph) and after a thematic-break / setext-underline line; an open tag whose body is prose (no `{` or fence after it) waits for its close — a close inside a fence or inline code span leaves it a plain mention, so the fence keeps its state, and when the close lands in prose the block may start only at an open the walk met in prose (never one inside a fence or code span it skipped);
a block whose close tag sits inside a fence opened after its open (a mention ending its line before a fenced example, which `{`-or-fence reads as a body, or a sloppy block whose fence never closed) resumes the scan on the next line still inside that fence, so the fence's closing line can't read as an opener and hide the real block;
once a real open tag is found the scan ignores Markdown until the first close tag, and the block then starts at the LAST open tag before that close that begins its own line, if any (so a stray prose mention that escaped code can't swallow the real block); a mid-line open moves it only when the chosen open is a prose mention (its body doesn't start with `{` or a fence) and it is the first later open whose body does and that doesn't follow a `"`
— a block whose own open already starts its JSON never moves, so a mention inside its JSON can't move it; neither rule considers an open ending past the block's last `{` (a start there leaves nothing to parse — `<handoff>\n{…}\n<handoff>\n</handoff>` keeps its first open); code state resets at every segment start (one segment = one event), so a block may still pair across events
— except that the trailing 256 KB window, when it cuts into a segment, starts with the fence state a linear fence-only walk from that segment's start finds at the cut (so a fence straddling the cut doesn't read its closing line as an opener); and a pending open whose body has a `{` before its close treats a close swallowed by an inline code span as prose.
Every surface's cheap pre-check is the locator's own case-insensitive `mayContainHandoffOpenTag`.

**Legacy** (`codeAware: false`) is the pre-change tokenization byte for byte, kept for the delta-streaming harnesses `HANDOFF_DELTA_STREAM_KINDS` = {gemini, antigravity} (`handoffScanIsCodeAware(kind)`), whose one-event-per-delta split would otherwise break fences.
Everything is linear (pinned by < 100 ms tests over 50k backtick runs, fence lines and tag mentions).

a run that overlapped it doesn't make it stale.

— else `HANDOFF_FROM_OTHER_RUN_STATUS`).
A displaced run's settle never reaches the global bus — `attachDoneHandler` emits `run-status` only for `task.runId` — so the orchestrator reports it to the runner alone through `setDisplacedStepRunSettledHandler` (a setter hook, never a `GlobalEvent`: no toast, notification, TUI or `logs --notify` sees it), and the runner re-settles the step's CURRENT run (`resettleCurrentRun`), so "the run whose settle advanced the step" stays well defined.
A released held step whose settle found no handoff gets a **10 s grace** (`RELEASE_CONTINUATION_GRACE_MS`; "held" is DB-derived — a subagent of the TASK that was running when the run ended and finished after it, matched by time overlap across all of the task's subagent rows, never by `subagent.runId`, which is whichever run was current when the watcher discovered the agent, so a hold spanning a later continuation still gets its grace) before any reminder, since the continuation's notification line may not be on disk yet; the grace precedes the already-reminded block.

**Reminders are idle-only**: `deliverHandoffReminder` passes `sendInput(…, { onlyIfIdle: true })`, which every harness's send function refuses before any side effect while a run of the task is live (claude also while `sessionHasTurn`), answering `{ delivered: false, busy: true }`; a refused reminder records nothing and blocks nothing — the live turn's own settle decides; a refusal with NO live run (claude's session still tracks a queued slot or a continuation awaiting content) is re-settled up to 4 times, backed off (`BUSY_RECHECK_DELAYS_MS`, 2/5/15/30 s), then blocks with `automatic reminder not sent: the agent session still reports a turn in progress`.
A reminder turn that settles before the reminder is stamped (its settle saw the reminder still in flight) is re-settled right after the stamp.
Pipeline Stop, `isDeliberateWholeRunStop`, the settle's live-sibling check, `refreshParentWorktree`'s live check, Advance's stopped-step check and `reconcilePipelineRuns` all use `isAnyRunOfTaskLive`, so a step live only through a displaced run counts as running; Stop goes through `cancelLiveRunOfTask` (the current run, else the newest displaced handle — one run only, since a second Ctrl+C on claude's shared session would exit the REPL), and `isTaskRunCancelling` is true only when every live handle of the task is cancelled.
A whole-run Stop is durable: `run.stopRequestedAt` (set ONLY by `cancelPipelineRun`; cleared by Retry, Advance, Restart and a turn the user starts on one of its steps; always stored, `null` when clear — a legacy `cancelled` row without the key reads as stopped) keeps `deriveRunStatus` at `cancelled` unless something is blocked, and makes `isDeliberateWholeRunStop` true (a bare `status === "cancelled"` no longer does).
A Stop on one step's own panel is that execution's `PipelineStepRecord.stoppedAt` instead — set by its `cancelled` settle, or, for a HELD step (whose turn already succeeded), by the orchestrator's runner-only `setHeldStepStoppedHandler` report from `cancelRun`, which carries the run current when Stop was pressed (stamped as `stoppedRunId`, so a continuation adopted while the record waits for the lock is still a new turn); cleared by a user-started turn on the step and by Retry; `deriveRunStatus` reads `cancelled` while every active execution is stopped.
An orphaned settle sets neither.
A per-step Stop never ends the run out from under a sibling the pipeline is still working on (`workingSiblings`: a live run OR a pending runner decision) — the stopped one gets the M5 "was stopped" block.
A later succeeded settle with no usable handoff on a stopped run or execution (`isStopApplied`) is recorded `cancelled` with no grace or reminder (`settleStoppedExecution` → `closeStoppedExecution`).
On a stopped step, the `running`-column branch cancels an automatic continuation, reminder or fx auto-resume turn (`turnStartedByUser`: no `origin` and not the reminder run, or a continuation opened by text typed in the terminal — `startContinuationRun` writes that opening status line before it emits the column event;
an fx auto-resume run carries `origin: "auto-resume"`) and lets a user-started turn resume the step (and the run, like a one-step Retry). "New turn since the Stop" is decided by run identity: `PipelineStepRecord.stoppedRunId` names the run the latest Stop applied to (a `cancelled` settle's run, a stopped held step's current run, or each active execution's current run when the pipeline's Stop is pressed;
cleared with `stoppedAt`), and any OTHER run is new whatever its status by now — so a user turn that already ended while its event waited for the per-parent lock still resumes; a `running` event for that same run (`pullBackParkedTask` pulling a held card back while its run is still `succeeded`, or the stopped run's own row before its kill lands), or while `isTaskRunCancelling`, changes nothing
— the stop and the recorded outcome stay; a row without the field falls back to "the current run is still running".
A cancelled settle on a pipeline step task never drains the one-shot follow-up queues (codex/cursor/gemini/antigravity/opencode/copilot/fx, plus fx steers the cancelled turn dropped): `drainFollowUpQueues` moves them into the step's backlog tray with a `queued message not sent — this pipeline step was stopped; …` status line instead (`stashQueuedFollowUpsOfStoppedStep`, also used when a Stop lands in the bounded-spawn window), because a drained turn has no `origin` and would read as the user resuming the step, undoing a Stop pressed after the message was typed; `fxSteerDroppedHandler` then reports `false`, so no "sending it as the next turn" line.
An ordinary task's Stop still drains its queue.
The pipeline's Stop also cancels any pending fx auto-resume on its active steps.
Stop also stops an execution the runner is still deciding with nothing live (release grace, wait or busy recheck, reminder mid-send), cancelling its timers; a fired timer's map entry stays until its re-settle claims it under the lock (`resettleFromTimer`), so a Stop queued ahead of that re-settle still finds the decision and the re-settle then does nothing.
`recheckReminder` (before the send, and after a delivered one) abandons the send when ownership is lost or another run is live, and re-settles instead when the look-back already finds a handoff.
`startPipelineRun` persists the fresh run BEFORE launching and launches through `launchTarget` (a throw used to leave the parent `running` over stale run state with the replaced run's executions already killed).

## 11. Human steps (pause / review gates)

A pipeline step may be a **human gate**: `PipelineStep.type: "human"` (missing
means `"agent"`). A gate spawns nothing — no task row, no worktree, no agent —
and exists to pause the run for an owner decision. Rules enforced by
`validatePipelineGraph` (`src/shared/pipeline.ts`):

- never the start step (`startStepId` and the unique-root fallback both
  refuse it);
- exactly one incoming edge (0 or 2+ is an error), so it is never a root; no
  human→human edges;
- no `agentProfileId`, no `subagents`, `join` normalized to `"any"`;
- `transition: "choose" | "all"` still applies to Accept; it may be terminal
  (0 outgoing) or have several outgoing edges.

**Run state.** A pending gate lives in `PipelineRunState.humanSteps`
(`{stepId, seq, startedAt, arrivals}`) and gets its own `history` record with
`taskId: null`. `seq` comes from the run-wide monotonic `seqCounter`;
`stepCount` stays agent-execution-only (what `maxSteps` caps), so a gate never
consumes the step cap. `PipelineJoinArrival.comment` carries trusted
owner feedback to the next step, rendered by `composeStepPrompt` as a
`## Human review feedback` section **outside** the untrusted-handoff markers;
a `Handoff` never carries it.

**Status.** `PipelineRunStatus` gains non-terminal `"review"`: a pending gate
maps to the board's Review column. With a pending gate, `deriveRunStatus`
returns `cancelled` when the whole run was deliberately stopped and otherwise
`review`; with no pending gate, `blocked` outranks a stopped run
(`cancelled`), which in turn outranks `running`, then `done`. A gate with a
live sibling stays Review, and Review outranks a blocked sibling. The step
cap is checked only on agent launches, before a gate.

**Decisions.** `reviewHumanStep` (behind `POST /tasks/:id/pipeline/review`) is
the only mutator, run under `runExclusive(parentId)`. It removes the gate and
records the decision in one critical section, so `stepId`+`seq` is idempotent
(a second submit 409s). Body: `{stepId, seq, decision:"accept"|"return",
comment?, nextStepIds?, mode?}`; 400 for a bad body / blank Return comment /
over-cap comment / bad next target / `mode` on Accept / `nextStepIds` on
Return / `nextStepIds` on a single-edge or `all` gate; 409 for not-a-pipeline,
never-run, archived, no pending gate, stale seq, already decided, resume
unavailable, or launches frozen.

- **Accept** reuses the gate's `transition`: 0 outgoing finishes the run;
  `all` launches every outgoing; `choose` with one launches it; `choose` with
  several requires `nextStepIds` naming outgoing targets. The comment is
  optional and rides the launch as `PipelineJoinArrival.comment` (through
  joins and pending-launch holds, so a Retry after a step-cap/launch failure
  keeps it; `PipelineBlock.pending` persists a Return's `returnToStepId`/
  `returned`/`humanFeedback` too, so a held Return re-applies its forced edge
  on Retry instead of resolving through the graph).
- **Return** targets the gate's sole incoming source (or the step a manual
  Advance entered from). The comment is required, trimmed, capped at
  `PIPELINE_LIMITS.handoffField` (8,000), control characters other than
  `\n`/`\t` refused, `\r\n` normalized. `mode` is `"fresh"` (default; a new
  task/session/seq via `launchStep`) or `"resume"` (a `sendInput` turn on the
  previous step's existing task, re-armed as a new execution under the lock
  first; the send itself runs OUTSIDE the lock — L-R7 — and the lock is
  re-acquired afterward: a refused send rolls the re-arm back and 409s
  (leaving the gate), and a Stop that raced the send cancels the turn it just
  started rather than reviving a cancelled run). While that send is in flight
  the re-armed execution counts as a pending runner decision even though no
  run of it is live yet, so the card's Stop still wins instead of 409ing
  "pipeline is not running"; the stop marks the execution cancelled and the
  post-send confirm cancels the turn the send just started. That turn is never
  read as the user resuming a stopped step: while the send is in flight the
  runner owns it, and the confirm records its run as the one the Stop applied
  to, so a late `running` event cannot revive the run. A second gate naming the
  same source step is refused while its resume send is in flight (409), so two
  sends can never race at one task.
  Either path records `returnToStepId` on the new execution, and
  `settleStepRun` resolves that edge unconditionally — the handoff's `next`
  and the graph's transition are ignored, and a missing/invalid handoff still
  returns to the gate (with a `null` handoff). See
  `docs/plans/pipeline-human-step-resume-spike.md` for the resume proof (fake
  claude and fake codex).

**Stop / Restart / reconcile.** `cancelPipelineRun` accepts a gate-only run:
it records `stopRequestedAt`, dismisses every gate (`cancelled` history
records), drops `run.blocked` so the card reaches Ready, and keeps history. A
plain Run on a `review` run refuses ("accept or return it first"); Restart
(`startPipelineRun({restart:true})`) clears all human state and starts fresh.
`reconcilePipelineRuns` sweeps a review run only when it still has live
`active` executions; a gate-only run is never flipped to done.

**Archived parents.** A gate reached while the parent is archived is recorded
on the run (no column write, no event); the review route refuses the archived
parent with 409, and the gate is reviewable after unarchive. Because `persist`
skips the column mirror while archived, `unarchiveTask` forces the card back to
Review when a gate is still pending (other statuses keep the column the owner
parked, e.g. a finished run left in Done).

**Surfaces.** The run view's `HumanStepPanel` (opened from the human node, the
run-view "Human review" section, the card's Review button, or the review
toast) shows the goal, the gate's "What to check", the last handoff, run
history with transcript links, prior rounds and a worktree diff. The board
card stays in Review and offers **Open** + a primary **Review** button, no
**Done**, and a single secondary danger **Stop** (never two Stop buttons).
The context menu offers **Review pipeline** and no **Mark done**. The CLI has
`agetor pipeline review <ref> --accept|--return` (`--comment`, `--next`,
`--step`, `--mode`), `status`/`show` print pending gates and `(human)` for
a null task id, and `ls` flags a parent row with `pipeline review · N gates`.
A `pipeline` GlobalEvent carries `humanStepSeqs` and
`runStartedAt`; the webview and headless notifier each raise one "Pipeline
needs your review" alert per event that first announces a gate (both keep one
notification per task, so an event opening several gates names the count
instead of silently announcing only the first).

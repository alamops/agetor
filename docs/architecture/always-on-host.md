# Always-on host: login-item supervisor, never-idle core, app handback on quit

> Moved from `CLAUDE.md`, where this was orchestration-flow item 22. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

**Always-on host** (`docs/plans/always-on-host.md`, grill `docs/plans/always-on-host-grill.md` D1–D13 / C1–C22, investigation beside them, manual QA `docs/qa/always-on-host-qa.md`): Settings → General → "Keep Agetor running in the background" registers an `SMAppService` LaunchAgent so a **headless core runs whenever the user is logged in**, app open or not.

**Process model:** launchd (label `sh.alamops.agetor.daemon`, canary `sh.alamops.agetor.canary.daemon`, `LOGIN_ITEM_LABELS` in `daemon-mode.ts`) → `Contents/MacOS/agetor-login-item run` (the Swift helper, `native/login-item/main.swift`, the plist's `BundleProgram`; it sets `AGETOR_LAUNCHED_BY=login-item`, `AGETOR_LOGIN_ITEM_BUNDLE`, `AGETOR_LOGIN_ITEM_LABEL` — and for canary/dev `AGETOR_DATA_DIR=$HOME/.agetor-dev` + `AGETOR_API_PORT=4318` when unset — then `execv`s the bundled bun) → `Contents/Resources/app/daemon/login-daemon.js` (the **supervisor**: no port, no DB, no tmux) → when no live core owns the port, `daemon/headless.js` as a child (the core).
The supervisor is `src/bun/login-daemon.ts` over the **pure** `src/bun/login-daemon-machine.ts` (`step(state, inputs, cfg)`, tick 1 s) and **must never import `db.ts`**, directly or transitively (it would create and migrate `agetor.sqlite` in a data dir that only holds a parked supervisor; a fresh-data-dir isolation test pins this) — only `core-creds`, `daemon-log`, `daemon-mode`, `login-daemon-state`, `core-spawn`.

**Parking** is the supervisor simply *not running a core child* — it never exits to park, so launchd's `KeepAlive {SuccessfulExit:false}` stays clean: exit 0 = stay down until next login (the user stopped it), non-zero = launchd restarts it after its 10 s throttle (a crashing CORE child no longer exits the supervisor: the machine retries it in-process with exponential backoff, 1 s doubling to 60 s, the streak reset by 120 s of healthy uptime or by parking behind a live core), **exit 75** (`SUPERVISOR_EXIT_BUNDLE_CHANGED`) = `Contents/Info.plist`'s `ino:mtimeMs` changed (an in-app update swapped the bundle), so launchd restarts the job from the new bundle.
A core exits **76** (`CORE_EXIT_PARK`, `daemon-mode.ts`) when it loses the bind (to a live core, or — login-item only — to anything, so a busy port reads as a wait, not a crash) or gets `POST /daemon/shutdown {mode:"handoff"}`: the supervisor goes `waiting` (15 s handoff grace, `AGETOR_LOGIN_DAEMON_HANDOFF_GRACE_MS`, growing with the same backoff when 76s repeat with no live core taking over), then `parked` while a live core owns the port (`createLiveCoreCheck`: a creds key (pid + startedAt + port) that has never answered must pass `probeLiveCore`, so a recycled pid never parks the supervisor;
once it has answered, a failed probe is forgiven while its pid is alive and its port still accepts a loopback TCP connect (`portAcceptsConnections` — the kernel completes the handshake while the app's thread is blocked by a native Open panel, a message box or a VACUUM), and only two failed checks in a row with the port refusing drop it;
probes cached 5 s), and boots a core within ~1 s once that core (the app) is gone.
After an update it waits 30 s (`AGETOR_LOGIN_DAEMON_UPDATE_GRACE_MS`) for the new app, triggered by `lastExit:"bundle-changed"` or the **handback marker** `login-daemon-handback.json` `{reason:"update"}` that `updater.ts` `applyUpdate()` writes first (`writeHandbackMarker`, consumed with a max age).
Files in the data dir, all via `login-daemon-state.ts`: `login-daemon.json` (the supervisor's atomic 0600 state — pid, `parked|waiting|running|stopped`, corePid, bundlePath, version, label, `lastExit`; informational only, `liveSupervisor()` = file + `isPidAlive` + a `heartbeatAt` the idle supervisor refreshes every 30 s, stale after 5 min so a recycled pid stops reading as the supervisor), `login-daemon-control.json` (`requestSupervisorStop`/`takeSupervisorStop` `{action:"stop", requestedAt}` — how `agetor daemon stop` and Quit Completely keep a parked/waiting supervisor down; both write it only while `liveSupervisor()` is non-null, and `takeSupervisorStop` honours only a request at most 2 min old written after that supervisor started, so a leftover can't stop the next one) and `login-daemon-handback.json`.
The core child's stdout/stderr go to `<dataDir>/daemon.log` by an `O_APPEND` descriptor, and `daemonLog` rotates that file by copy-truncate (to `daemon.log.1`/`.2` past 5 MB; never a rename, which would leave the child writing into the renamed file) — checked at most every 30 s on a `daemonLog` write, plus `rotateDaemonLogIfNeeded()`, which the supervisor calls every 60 s since the child's output never goes through `daemonLog`.

**The login-item core** (`headless.ts` with `launchedBy() === "login-item"`) **never idle-exits** (`resolveIdleTimeoutMs`: an explicit `AGETOR_DAEMON_IDLE_MS` always wins, else login-item → off, else the CLI daemon's 5 min), writes `launchedBy: "login-item"` into `agetor-core.json` (kind stays `"cli-daemon"`, so older CLIs keep working), removes the creds file only when it owns it, and installs its SIGINT/SIGTERM handlers first.

**App takeover** (`src/bun/app-takeover.ts` `acquireApiPort`, used by `index.ts` BEFORE its boot restore — see boot reconciliation, step 5 in [task-lifecycle.md](task-lifecycle.md)): try the bind; on failure with a live `cli-daemon` in the creds file, `POST /daemon/shutdown {mode:"handoff"}`, wait ≤ 18 s for the port (`TAKEOVER_PORT_FREE_TIMEOUT_MS` = `HANDOFF_LAUNCH_SETTLE_MS` + 10 s: a headless core asked to hand off first waits ≤ 8 s, `headless.ts` `handOffPort` over `waitForLaunchesToSettle`, for the agent launches it is in the middle of
— `launchesInFlight()` = start claims plus claude sessions that haven't written their JSONL or haven't finished pasting a deferred first prompt (`claudeBootsInFlight` — on a `--resume` spawn the JSONL already exists, so the count is held until the paste settles too), whose > 4 KB first-prompt paste or startup-dialog confirm would otherwise die with the process, plus claude tmux op chains still running (`claudeTmuxOpsInFlight`: a follow-up paste between its text and its Enter, an ask-card drive)
— while still serving reads; a stop request or a signal exits at once), bind; with the port held but no readable creds, retry read+bind every 250 ms for ≤ 5 s (the daemon's bind-to-creds-write window, the login race) — and for up to 60 s (`TAKEOVER_BLOCKED_CORE_WAIT_MS`) while the creds' pid is alive and its port accepts a loopback connect (`portAcceptsConnections`, now in `core-creds.ts`) but the probe fails, i.e. a core blocked by a VACUUM or a native panel;
otherwise rethrow the original bind error.

**Launch freeze** (`freezeLaunches()` in `orchestrator.ts`, terminal and idempotent): called before that wait, by headless `shutdown()`, and by the app on every quit it lets through, so nothing starts that the exit would cut off — `startTask` (`{error, code: "launches-frozen"}`, 503 on `POST /tasks/:id/start`), `sendInput` (an idle-only send also reads `busy`) and `resumeFxRecovery` refuse with `LAUNCHES_FROZEN_REASON`
— on entry AND again after the awaits that precede their claim, in the same synchronous section as it, so a freeze that lands mid-call can't slip a new claim past the exit (`sendInputInner` after the floor probe / teardown wait / worktree restore / `@` expansion, which covers every kind but claude; claude's `claudeSendRefusal`, which also refuses a task archived meanwhile, after its `has-session` fork and `pasteFollowUp`;
`resumeFxRecovery` after the fx version probe), fx auto-resume timers stop (re-armed from the DB by the next owner), follow-ups queued in memory behind a running one-shot turn move to their task's backlog tray with a `queued message not sent — Agetor stopped before it could run` status line (a turn settling during the wait stashes instead of draining), and the pipeline runner's `settleStepRun`, `startPipelineRun`, `advancePipeline` and `retryPipelineStep` bail, leaving the settle to the next owner's `reconcilePipelineRuns`.

**Status** (`src/bun/background.ts` over the pure leaf `background-derive.ts`, which the CLI imports offline; for 15 s after a successful register/reregister an enabled item with no live supervisor reads `starting`, not `stopped` — `expectSupervisor` — so the C3 reconcile can't undo "Turn On" before the supervisor's first `login-daemon.json`;
`AGETOR_BACKGROUND_START_GRACE_MS` overrides the window; the Remote Access… box starts a `stopped` host and waits a bounded time for it before writing the pref): `BackgroundState` = `running|parked|starting|stopped|needs-approval|off|unavailable`, derived from the helper's `info`+`status` and `liveSupervisor()`;
`unavailable` (with a `BackgroundUnavailableReason`) for non-darwin, a dev build, an unsigned build, a bundle outside `/Applications`/`~/Applications` (DMG/translocated copies — the registration pins the install path, DTS 745412), a missing helper, a data dir that isn't this channel's (`other-install`) or a helper failure;
`stopped` = registered but no live supervisor (a clean exit leaves SMAppService `enabled`).
Turning it off turns remote access off too, and a status that isn't running/parked/starting resets remote access to off (C3); unregister runs through the helper's `setsid` so a call from inside the job isn't killed with its process group.
`startBackgroundNow` throws `BackgroundStartError` (`not-enabled|already-running|unavailable` → 409).
Every change fans out through `subscribeBackgroundChanges`; `server.ts` subscribes once and broadcasts `background_changed` on `/app/events`.

**Remote access (preview)** is the pref `remoteAccess` (`REMOTE_ACCESS_PREF_KEY`, `on|off`); `remote-access-box.ts` `runRemoteAccessBox` is the native-only way on (Agetor › Remote Access… → `showMessageBox`; it turns the background switch on first and only an `enabled` result writes the pref via `setRemoteAccessOnFromNativeBox`, which only that file may call); an agent writing the pref straight into SQLite is the accepted residual (the reconcile resets it whenever the background isn't enabled).

**Quit:** the Agetor menu has **Remote Access…** and **Quit Agetor Completely** (⌥⌘Q; `application-menu-clicked`, actions `remote-access` / `quit-completely`); `before-quit` computes `backgroundArmed` synchronously from `liveSupervisor()` (`parked` or `waiting`; no helper spawn inside `before-quit`) and, with running tasks, broadcasts `quit_request {…, backgroundArmed, completely}`, whose pure model is `quitDialogModel` (`src/mainview/lib/quit-dialog.ts`): plain → [Quit anyway] [Stay open];
armed → "They'll keep running in the background" [Quit] [Quit completely] [Cancel]; completely → "also stops the background core, so they will stop". "Completely" (the menu flag via `requestQuitCompletely`/`consumeQuitCompletely`, or `POST /app/force-quit {completely:true}` → `armForceQuit({completely})`/`consumeForceQuit()`) calls `requestSupervisorStop` before the quit is allowed;
with no running tasks the quit is allowed straight away and the supervisor boots a core when the app's pid dies.
Either way a quit about to be allowed first goes through `quit-launch-gate.ts` (`createQuitLaunchGate`, wired in `index.ts`'s `before-quit`): it freezes launches and, while `launchesInFlight()` > 0, vetoes the quit, waits ≤ 8 s (`HANDOFF_LAUNCH_SETTLE_MS`), then re-arms the force flag (keeping `completely`) and calls `Utils.quit()` again — the mirror of the headless handoff wait; a Cmd+Q or "Quit Agetor Completely" while it waits is absorbed (its `completely` kept), with no second confirm.

**Headless notifications** (`src/bun/headless-notifications.ts`, pure `headlessNotificationFor(ev, lookup)` + `installHeadlessNotifications()`; gate `shouldPostHeadlessNotifications` = `isHeadlessNotificationsEnabled` AND a notifier helper that `resolveNotifier()` finds — without one there is nothing to show, so no sink is passed and `POST /notifications` stays 501 for the CLI's fallback;
`isHeadlessNotificationsEnabled`: macOS only, `AGETOR_HEADLESS_NOTIFICATIONS=0` off anywhere, `=1` forced on, else on except under `NODE_ENV=test` — `e2e/fixtures.ts` sets `0`): a headless core posts the [one-per-task notifications](notifications.md) through the same `createTaskNotifier` (no plain fallback headless), step events retargeted to the pipeline parent, installs the [notification](notifications.md) removal hooks itself, and passes the sink to `startApiServer({ notifications })` (only when enabled, so `POST /notifications` posts through it
— `agetor logs --notify` against a background core — and a core that never posts keeps answering 501); a pipeline parent's `reason: "pipeline"` block with no step question behind it posts "Pipeline needs you" (kind `blocked`), and one that a pending question displaced is owed and raised once the question is answered and the run is still blocked (`createHeadlessNotificationHandler`, the twin of the webview's `OwedPipelineAlerts`);
`notifier.ts` `resolveNotifier()` falls back to `resolveInstalledAppNotifier()` (`/Applications`, then `~/Applications`) ONLY for a login-item core (`AGETOR_LAUNCHED_BY=login-item`) or an explicit `AGETOR_NOTIFIER_USE_INSTALLED_APP=1`, so a dev or worktree core never posts through the release app's helper (the CLI's own `logs --notify` still calls `resolveInstalledAppNotifier` directly).

**Canary data dir:** `src/bun/channel-defaults.ts` is the **first import** of `index.ts` (ES modules evaluate in import order, so its side effect runs before `db.ts` opens SQLite and before `api-config.ts` reads the port): a canary/dev app (channel from `<exe dir>/../Resources/version.json`, null in every source run) defaults `AGETOR_DATA_DIR=~/.agetor-dev` and `AGETOR_API_PORT=4318` unless already set, matching its launchd job, so signed-build QA never touches `~/.agetor`.

**CLI:** `agetor daemon status` prints a `background:` line (the live core's `GET /background`, else the installed helper + state file offline, never starting a daemon); `daemon start` re-registers a `stopped` background (`helper.reregister()`, waits ≤ 20 s) instead of starting a CLI daemon beside it; `daemon stop` on a login-item core says it starts again at next login; `daemon background [status|off]`; `agetor remote [status|off]` (`commands/remote.ts`, no `on`); the CLI finds the helper with `loginItemHelper(dataDir, {forCli:true})`.

**Build:** `bun run vendor:login-item` (`scripts/build-login-item.ts` → `vendor/login-item/agetor-login-item` + `LaunchAgents/*.plist`, `plutil -lint`'d) and `bun run vendor:daemon` (`scripts/build-daemon-bundle.ts` → `vendor/daemon/{login-daemon,headless}.js`) run in the `build`/`build:canary`/`build:stable` chains before `verify:vendor` (`login-item` is in `verify-vendor-signing.ts`'s `OWNERS`);
`electrobun.config.ts` copies the helper to `Contents/MacOS`, the plists to `Contents/Library/LaunchAgents` and the daemon bundle to `Resources/app/daemon`; `scripts/verify-release.ts` `verifyBackgroundLayout(appPath)` (also `--layout <app>`) checks the helper's Developer ID + hardened runtime + team, both plists (`BundleProgram`, `ProcessType=Interactive`, `KeepAlive.SuccessfulExit=false`, `AssociatedBundleIdentifiers`) and the daemon JS files
— `SMAppService.status` can't verify a plist, so the files are the check.

**Test seams:** `AGETOR_FAKE_LOGIN_ITEM=1` (a file-backed fake helper at `<dataDir>/fake-login-item.json` `{registration, info?, calls[], failNext?}`; it also makes `background.ts` treat the platform as darwin and `POST /background` work headless, so e2e reaches every state), `AGETOR_FAKE_REMOTE_ACCESS=on` (with the fake: seeds the pref on at first read), `AGETOR_LOGIN_ITEM_HELPER` (helper path), `AGETOR_LOGIN_DAEMON_CORE` (core entry the supervisor runs), `AGETOR_LOGIN_DAEMON_TICK_MS` / `AGETOR_LOGIN_DAEMON_HANDOFF_GRACE_MS` / `AGETOR_LOGIN_DAEMON_UPDATE_GRACE_MS`, and the helper-set `AGETOR_LAUNCHED_BY=login-item`, `AGETOR_LOGIN_ITEM_BUNDLE`, `AGETOR_LOGIN_ITEM_LABEL`.

**Rollback rule (C21):** a later build that drops this feature MUST keep the helper in the bundle and call `unregister` on launch — otherwise a user who turned the switch on keeps a launchd job whose `BundleProgram` no longer exists and loops on exit 78.
Turning the switch off is the per-user rollback; there is no feature flag (the switch defaults to off).
Registration is by bundle id, so a canary and the release share one Login Items row (spike A8): toggling it can leave one label `notFound`, which Settings shows honestly as Off.

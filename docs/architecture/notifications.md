# Native notifications — one per task

> Moved from `CLAUDE.md`, where this was orchestration-flow item 21. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

**Native notifications — one per task** (`docs/plans/duplicated-macos-notifications.md`, grill `docs/plans/duplicated-macos-notifications-grill.md`, manual QA `docs/qa/native-notifier-qa.md` "One notification per task"): every OS notification for a task is ONE Notification Center entry, posted by the bundled AgetorNotifier helper (`native/notifier/notifier.swift`, built + ad-hoc-signed by `bun run vendor:notifier`) under the fixed request id `taskNotificationId(taskId)` = `agetor.task.<taskId>` — re-adding a same-id request from a new process replaces the delivered entry and puts it on top (spike-verified, macOS 26).

**Policy** is pure and shared (`src/shared/os-notification.ts`): `NOTIFICATION_KINDS` (`waiting`/`blocked`/`api-error`/`session-ended`/`unknown-command`/`failed` are `needs-you`; `succeeded`/`files-sent`/`pipeline-finished` and no kind are `quiet`), `soundOverUrgencies` (needs-you sounds over a delivered `quiet` or `unknown` entry; quiet never does), `ANSWERED_REMOVAL_KINDS` / `UNBLOCKED_REMOVAL_KINDS`.

**Helper contract** (`notifier.ts` builds every argv; flags beyond the original five are appended so the old order holds): post `--title --message [--subtitle] [--url agetor://task/<id>] [--silent] [--id] [--kind] [--urgency] [--sound-over <u>]…` — with `--id` it reads `getDeliveredNotifications`, plays the sound only when nothing for the task is delivered or the delivered entry's `userInfo.urgency` (absent = `unknown`, i.e. an old-style random-id entry) is in `--sound-over`, removes old-style entries carrying the same `--url`, and stores `url`/`kind`/`urgency` in `userInfo`; without `--id` it is the old UUID post.
`--remove --id <id> [--url] [--if-kind <k>]…` and `--list` (prints each delivered `agetor://` url) **never call `requestAuthorization`** (a removal must never pop the permission prompt) and are flag-gated so the no-arg click relaunch can't be mistaken for them.
Exit codes: 0 ok, 1 remove/list safety timeout or a post whose `center.add` failed (no `posted` ack — agetor falls back to a plain notification), 2 post permission denied/timeout, 64 usage.
Every mode prints an ack on stdout (`posted <id>`, `removed <n>`, a first `--list` line `agetor-notifier list` — `NOTIFIER_LIST_HEADER` and the `notifier*Acked` parsers in `notifier.ts`): a helper built before these modes (a stale `vendor/notifier` under `bun run dev`, which doesn't rebuild it) takes `--remove`/`--list` for a click relaunch, waits 10 s and exits 0 silently, and ignores `--id`, so an exit 0 without its ack — proven by an unacked `--list` (the boot seed, or a probe an unacked post/`--remove` starts, single-flight, since a current helper can also exit 0 early when a notification click reaches it; a failed probe proves nothing) — makes `task-notifier.ts` log once ("rebuild with `bun run vendor:notifier`"), skip every later removal, leave the seed failed and keep posting.

**Bun side** (`src/bun/task-notifier.ts`, wired in `index.ts` as `native.showNotification`/`native.removeTaskNotification`; no Electrobun import, injected `spawn`/`resolveBin` for tests): one FIFO of helper ops per task, at most one helper child per task (D15 — the newest event lands last; different tasks run in parallel); the old fallbacks (no taskId or no helper → `Utils.showNotification`, exit 2 → nothing, any other failure → plain); a **may-be-delivered set** gates removals (a post adds the task, an unconditional remove exiting 0 takes it out unless a newer post was enqueued since; `seed()` at boot fills it from `--list`; until a seed succeeds nothing is skipped), and an unconditional remove drops that task's not-yet-started queued posts.

**Removal triggers**: `POST /tasks/:id/seen` (panel open/switch and "Mark as read"; a step id maps to its pipeline parent via `notificationTargetTaskId`), `POST /tasks/:id/archive` and `DELETE /tasks/:id` (own id only, after success), `PATCH /tasks/:id` moving a card out of `blocked` (a drag or `agetor move` emits no global `column` event;
removes the reason family), `src/bun/notification-hooks.ts` on the global bus (installed by `index.ts` before `startApiServer` in the desktop app, and by `installHeadlessNotifications()` (`headless-notifications.ts`) in a headless core that posts notifications, each into its own task notifier — never both in one process: an `interaction` `resolved` removes the target's `waiting` entry once `pendingInteractionsFor`
— own + steps' — is 0, and a non-step `column` event leaving `blocked` removes the reason family), and `DELETE /notifications/:taskId` (authed, 501 headless, 400 over 512 chars, step → parent) for the webview-only facts: the pipeline run view opened, the window regaining focus with a task's panel or run view open (D6d), and an event arriving while the window is focused (`maybeNotifyOS` clears instead of posting, D7)
— except after a FORCED focused post (a proactive files-sent): `FocusedForcedPosts` (`toast-slots.ts`) keeps that entry through the task's later focused events until the task is opened, marked read, archived or deleted (`dismissTaskToast` forgets it) or an unfocused post replaces it; window focus with the task open (D6d) still clears it.
`POST /notifications` takes an optional `kind` (`isNotificationKind`, invalid dropped).

**In-app** (`src/mainview/lib/toast-slots.ts` + `toasts.ts`): one sonner toast slot per task for every event toast (`showTaskToast` dismisses the prior one; the slot is released on `onDismiss`, `onAutoClose` and from the wrapped "Open" action click — sonner 2.0.8 fires neither callback on an action click, and the id-guarded `release` keeps a displaced toast's late `onDismiss` from freeing its successor);
`hasPendingToast`/`dismissPending` act only on the reason family (a pipeline parent's "Pipeline needs you" suppressed or displaced by a step's retargeted "Waiting on you" is owed — `OwedPipelineAlerts`, `src/mainview/lib/owed-pipeline-alerts.ts` — and App.tsx raises it, OS post included, once no question is left and the run is still blocked on something other than an answered step's own `step-blocked` block or a block naming a step whose row is `running` again (the runner clears those under the parent's lock, after the step's column event), or forgets it once the run leaves `blocked`), `dismissTaskToast` is unconditional and runs on panel open (plus the parent for a step), run-view open, Mark as read, archive/delete and a poll that shows the task archived or gone.

**CLI**: `agetor logs --notify` (`src/cli/notify.ts` `osNotify`) rings the bell, then posts through the connected core's `POST /notifications`, then — on any error, e.g. the headless 501 — the installed app's helper directly (`resolveInstalledAppNotifier`, serialized per process), then osascript.
Not deduped: the `Utils.showNotification` fallback (no identifier control).
The delivered list is scoped per code signature — a dev-built helper can't see release entries — and Developer-ID builds sharing it across releases is unverified.
Tests: `os-notification.test.ts`, `notifier.test.ts`, `task-notifier.test.ts`, `notification-hooks.test.ts`, `notifications.test.ts`, `toast-slots.test.ts`, `src/cli/notify.test.ts`, `e2e/one-notification-per-task.spec.ts`; `interaction-broadcast-wiring.test.ts` pins from a fresh process that the global `interaction` `resolved` event fires — `orchestrator.ts` installs the interaction bridges exactly once (a second `setResolvedBroadcaster` once replaced the global emit), the setters return the previous fn so a test restores it, and `interactions.ts` `__testing.reset()` leaves the broadcasters installed.

**Pipeline human gates.** A `pipeline` GlobalEvent with `status: "review"` carries `humanStepSeqs` (the pending gates' seqs) and `runStartedAt` (the run generation). The webview raises one blocking "Pipeline needs your review" toast — and, unfocused, one OS notification (`kind: "blocked"`) — per event that first announces a gate, deduped per `(runStartedAt, gate.seq)` with `newHumanGateSeqs` (`src/shared/pipeline.ts`); a repeat persist sends nothing, a Restart (new generation) notifies afresh, and a stopped run sends nothing. Both notifiers keep one entry per task, so an event that opens several gates raises one alert naming the count (`humanReviewSubtitle`) rather than a second banner replacing the first. Clicking it opens the run view with the gate focused. `headless-notifications.ts` applies the same dedupe statefully. A review transition does not clear a sibling step's pending-question toast or owed "Pipeline needs you" alert — the run still needs the user; leaving review to `running`/`done`/`cancelled` clears them as before. "Pipeline finished" still fires only on the transition into `done`.

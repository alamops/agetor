# Task lifecycle: create, start, stream, delete, boot reconciliation, PATCH allow-list

> Moved from `CLAUDE.md`, where this was “Orchestration flow” items 1–6. Index of all subsystem docs: the [Topic map in CLAUDE.md](../../CLAUDE.md#topic-map).

1. UI calls `POST /tasks` → `orchestrator.createTask` (async) → row in `tasks` table (column `backlog`).
   `isolation` defaults to `"worktree"`.
   When isolation is on and `workdir` is a git repo, `createTask` **resolves the base ref to a sha at create time** and pins it on the task row.
   Default base is `HEAD`; an explicit `baseRef` ("main", "v1.2.3", a sha…) is honored and validated — bad refs return `{ error }` instead of inserting.
   This pinning is what makes re-runs reproducible: the worktree is always built off the same starting commit even after the source repo moves.
2. UI calls `POST /tasks/:id/start` → `orchestrator.startTask`:
   - **Pre-flight 1 — agent availability** (`agent-status.ts`): if the agent binary isn't on `PATH`, returns a friendly error with an install hint *before* any state mutation.
   - **Pre-flight 1b — per-model minimum CLI version** (`minCliVersionError` in `orchestrator.ts` over `MODEL_MIN_CLI_VERSION` + `cliVersionSatisfies`): a model with a minimum CLI version (codex's GPT-6 rows and copilot's newer models) is refused with an upgrade hint (`upgradeHintFor` in `agent-status.ts` — `brew upgrade <pkg>` for a Homebrew install (`brew upgrade --cask copilot-cli` for copilot), `claude update` / `cursor-agent update` / `copilot update`, else the install command) when the probed version parses below the floor; unparseable versions, and a pre-release build sitting exactly at the floor, never block.
     It is also re-checked by `spawnCodexTurnNow` / `spawnCopilotTurnNow` on every follow-up codex or copilot turn (both are one-shot per turn and the model is PATCH-able between turns) — a refused follow-up returns `{ delivered: false, reason }` with no run row, and a refused *queued* follow-up is moved to the backlog tray with a status line — and by `POST /projects/clone` before cloning; `AGETOR_SKIP_CLI_VERSION_FLOOR=1` disables it.
   - **Pre-flight 2 — workdir isolation** (`worktree.ts`, `prepareWorkdir`): if `task.isolation === "worktree"` and `workdir` is inside a git repo, creates `<dataDir>/worktrees/<task-id>/` (`~/.agetor/worktrees/` by default) on a fresh branch `agetor/<short-id>-<slug>` off the task's pinned `task.baseRef` (HEAD at start time only for a legacy row with no pinned base).
     Idempotent — reused across re-runs, and reuse **never runs `git checkout`**: a worktree that drifted off `task.branch` (an agent or a terminal ran `git checkout -b …`) is reused exactly as it is — a checkout could fail on conflicting edits or silently switch the branch under a live agent (`docs/plans/codex-terminal-worktree-error.md`).
     `task.branch` stays "the branch agetor created"; the branch actually checked out is recorded as the server-managed `Task.checkoutBranch` (`tasks.setCheckoutBranch`, compare-then-write, `null` on a detached HEAD, a step row's write mirrored onto its pipeline parent) at four refresh points — run start (where a drifted start also logs `worktree is on <live> (task branch <b>) — running there`, or a ⚠ PR-head warning for `branchSource: "existing"`), run settle (every harness, fire-and-forget off `attachDoneHandler`), terminal open, and archive (read just before `detachWorktree`)
     — never from the `git-status` GET poll; a failed read is *unknown*, never written as `null` (that would erase the recorded drift): `readCheckoutBranch` distinguishes it, and `prepareWorkdir`'s `checkoutKnown` + `recordableCheckout(prepared)` (→ `undefined` = record nothing) carry it to the run-start, terminal-open, restore and pipeline-refresh call sites.
     Re-attaching a missing worktree (unarchive, `sendInput`'s restore, pipeline refresh) prefers that recorded branch when it still exists — even when `task.branch` itself was deleted — else falls back to `task.branch` with a `warning` status line (a re-attach that has to recreate a deleted `task.branch` from base warns too).
     Delete removes `task.branch` and, when the live (else last-seen) checkout is a different named branch, that one too — never the repo default branch, a PR-head task's own branch, or a branch another task holds (`planTeardownBranches`, `teardownBranchesForTask`); `GET /tasks/:id/teardown-preview` returns that plan so the delete confirm and `agetor rm` name every branch, while `DELETE` stays 204. "Create PR" uses the live branch as head when it differs and isn't the default (`prHeadBranch`; PR-head tasks keep `task.branch`).
     With isolation off it runs in `workdir`; with `isolation === "worktree"` and a `workdir` that isn't inside a git repo it returns an error and the start is refused, rather than running unisolated.
   - Inserts a `runs` row, flips the task to column `running`, persists `branch` + `worktreePath` on the task row, sets `task.runId`.
   - `agents.spawnAgent` dispatches to the kind's driver (`claude-tmux.ts`, `codex-tmux.ts`, `cursor-acp.ts`, `fx-acp.ts`, …) with the command from `buildCommand(agent, prompt)` and the prepared cwd (worktree path, or raw workdir when isolation is off); every process the core launches goes through the `coreSpawn` wrapper (`src/bun/core-spawn.ts`).
   - Every stdout/stderr chunk is appended to `run_events` **and** broadcast to all SSE subscribers.
   - On exit: status row updated, task moves to `review` (exit 0) or back to `ready` (non-zero).
   - An OpenCode 2.x turn is the exception to "spawn a child per turn": the driver talks to the harness's long-lived agetor-owned server, and a follow-up sent while the turn runs is steered into it (`POST /runs/:id/input` → `sendInput` → the active handle's `steer`, no new run) rather than queued. Stop, delete, archive and an agent switch interrupt the OpenCode session (and its background subagents) over HTTP and cancel the task's open permission and question cards. A Reject with no reason skips the action and the turn continues; it does not stop the run. Details: [harness-opencode.md](harness-opencode.md).
3. The run panel subscribes to the authenticated `GET /tasks/:id/events` (every run of the task, merged) through `openEventStream` (`src/mainview/lib/sse-fetch.ts`), not `EventSource`.
   The endpoint replays persisted events first, then streams live ones — this is what lets you close and reopen the run panel without losing scrollback.
4. `DELETE /tasks/:id` → `orchestrator.deleteTask` kills any active run, then `removeWorktree` best-effort tears down `git worktree remove --force` + `git branch -D`.
   If the worktree path still exists afterwards and lives under `dataDir/worktrees/` (our owned namespace), `removeWorktree` does an `rm -rf` fallback — this catches the case where the user changed `task.workdir` after the worktree was materialized, so git in the new workdir doesn't know about the registration.
   Never blocks the delete.
5. **Boot reconciliation**: `index.ts` and `headless.ts` bind the API port FIRST (the bind is the ownership claim: the app takes the port over from a live background/CLI core there, and a core that loses the bind exits before touching any run), then call `orchestrator.reconcileOrphans()` (plus `reconcilePipelineRuns`/`rearmFxAutoResumes`), then `markBootReady()`.
   Until then every route waits on the ready promise (`src/bun/boot-gate.ts`, `startApiServer({ ready })`; a held request whose client aborted meanwhile — the CLI's 15 s timeout — is answered 499 without running its handler) except `/health` and `/info` — `probeLiveCore`'s two calls, so a booting owner never reads as dead — and, on a headless core only, `/daemon/shutdown` (so the app can take the port from a core that is still booting; that exit is crash-equivalent).
   A restore that throws exits 1 rather than strand gated requests.
   A claude reattach whose JSONL is still missing waits until `started_at + CLAUDE_JSONL_APPEAR_GRACE_MS` (35 s = claude-tmux's `CLAUDE_BOOT_TIMEOUT_MS` + 5 s) before treating it as broken, since a session spawned just before a handoff hasn't written it yet and a slow boot may take the spawner's whole boot timeout.
   For each `status='running'` run from a previous process, the orchestrator checks whether the run's tmux session is still alive on this machine.
   If yes it **reattaches** rather than orphaning — for claude-code (via `reattachSession`, keyed on `claude_session_id`), codex (via `reattachCodexSession`, keyed on `codex_session_id`), gemini (via `reattachGeminiSession`, keyed on `gemini_session_id`), antigravity (via `reattachAntigravitySession`, keyed on `antigravity_session_id`), opencode `run` turns (via `reattachOpencodeSession`, keyed on `opencode_session_id`; OpenCode 2.x server turns are the separate path below) and copilot (via `reattachCopilotSession`, keyed on `copilot_session_id`): rebuilds the in-memory session state, re-tails claude's session JSONL or the one-shot kind's per-run log from offset 0, and seeds an in-memory `seenLineUuids` set from `run_events.line_uuid` so events already persisted don't double-emit (the `(run_id, line_uuid)` partial unique index is the DB-side backstop).
   For claude the **subagent watcher** is seeded the same way, per subagent row — and that seed is the one that must stay cheap and must never hold the main thread (`docs/plans/non-blocking-session-restore.md`; on a 4.5 GB DB the old unindexed `WHERE subagent_id = ?` scan froze the whole core for ~1.1 s per subagent, 105 s for a 96-subagent task, while every other panel, the board and the pipeline views sat on `Loading…`).
   `runs.seenLineUuidsForSubagent(taskId, subagentId)` / `runs.hasLineUuidPrefixForSubagent(taskId, subagentId, prefix)` are **task-scoped**: `FROM runs r JOIN run_events e ON e.run_id = r.id WHERE r.task_id = ? AND IFNULL(e.subagent_id, '') = ? AND e.line_uuid IS NOT NULL` — the `IFNULL(subagent_id, '')` spelling must match the partial unique index `run_events_run_sub_line_uuid`'s expression exactly or SQLite falls back to a table scan; task scoping is a strict superset of run scoping (every subagent's events sit under its own task's runs).
   And the rehydrate loop plus the first-cycle replay are **cooperative jobs** (`createSeedJob` / `createCycleJob` in `claude-subagents.ts`, stepped in 20 ms slices with `setImmediate` yields under a lag label): `attachSubagentWatcher` still returns its handle synchronously, the handle's `ready` resolves once the seed is done and `settled` once the first cycle is too (neither rejects), and every caller that needs the seed — the spawn IIFE (the `claude session … ready` status waits for it), `reattachSession`, the held-task re-arm in `reconcileOrphans` — awaits `ready`.
   `cycle()` and the transcript-dir watcher stay inert until the first cycle finished.
   For codex, gemini, antigravity, opencode and copilot this reattach window is only WHILE a turn is in flight — between turns there's no session (each turn is a fresh one-shot), which is correct because there's nothing running to reattach.

   **OpenCode 2.x server turns** ([harness-opencode.md](harness-opencode.md)) have no tmux session of their own (the run's `tmux_session` is null, and `agetor attach` on such a task explains it instead of attaching); the agetor-owned `opencode serve` is the thing that survives.
   Boot therefore calls `adoptOpencodeServers()` before `reconcileOrphans` reads any run: a server whose tmux session is alive and which answers an authenticated info request is reused, and one provably dead (host gone, connection refused, or a 401 that persists across a re-probe) is killed and has its state deleted.
   Servers are judged in parallel under a 5 s budget, and a slow, undecided or merely unresponsive one is kept (marked unhealthy and re-probed by the next `ensure`), so an adoption never kills a server that is mid-turn.
   `reconcileOrphans` then routes each `running` opencode run by the `server=` field of the run's turn breadcrumb (the first status line, `parseOpencodeTurnBreadcrumb`): `server=agetor` goes to `reattachOpencodeServerRun` (`orchestrator-opencode-server.ts`) → `attachOpencodeServerAgent` (`agents.ts`) → `attachOpencodeServerTurn` (`opencode-driver.ts`), which re-subscribes through the hub, seeds from the message snapshot (the mapper's line uuids keep it from duplicating a persisted line), re-registers still-pending permission and question cards and streams the rest into the same run; `shared` and `standalone` (a `run`-driver turn started before an upgrade, or under `AGETOR_OPENCODE_TRANSPORT=run`) keep the tmux reattach above.
   A server reattach with no adopted server for the harness, or a session the server no longer has (one `probeOpencodeSessionsAtBoot` call covers all runs), orphans the run like any other and sends the task to `ready`; an unreachable server lets the driver try and settle the run `failed` with a status line.
   A task whose last turn already settled but whose background subagents still run on the server (a held task) gets a lingering handle (`attachOpencodeServerLinger`) instead of having those rows orphaned.

   **Server wake.** When OpenCode starts an execution on a task's session with no agetor driver listening (a background subagent finished and its result was queued, or a steer landed just after the turn closed), the hub reports it and the orchestrator's `onOpencodeServerWake` runs `decideOpencodeWake`, whose checks are all synchronous.
   A wake is never refused because the user stopped the task or because the card is parked in Done, Backlog or Blocked (owner decision R3): it goes through and pulls the card back to Running from any column.
   It is **refused**, with nothing done, only when launches are frozen or the session is not one the orchestrator watches.
   It is **interrupted** when the task has no card to pull back (gone, archived or tearing down, the harness switched, disabled or no longer on the server transport, or the session no longer the task's): the orchestrator interrupts that execution on the harness's server, bounded and best effort.
   Sessions a task let go of stay watched for 24 h so such a wake is seen: an archived task's last session through its last run, and every session of a deleted, archived or harness-switched task (up to 16 each) through a persisted tombstone written when it is dropped (`opencode_watch_tombstones`, migration 083), which a restarted core reads too. Within that window nothing OpenCode starts on those sessions runs unattended; after it, nothing watches them.
   Delete, archive and a harness switch also interrupt the task's sessions on the server, and then their executing subagents, over HTTP whether or not a local handle exists (`interruptOpencodeSessionsOfDroppedTask`, bounded).
   The cancelled-child wake that agetor's own Stop causes (a background subagent it interrupted makes OpenCode enqueue a `cancelled` notice on the parent) is the tail of that Stop and is interrupted too (R4): agetor notes each child before it interrupts it, durably for 24 h (`opencode_stopped_children`, migration 082), and a wake whose input is only such notices is the tail. The hub hands each wake the inbox items pending when its execution started; when it may have missed an enqueue (after a reconnect, for a newly watched or adopted session) the input is read from the server at once, before any deferral (its inbox, then the messages delivered after the `idle` record of the execution before).
   It **defers** while a start or send holds the task or one of the task's own runs is live, settling or being stopped (the execution is often that turn's tail, and the hub fires in the same dispatch that settled the driver), and decides again when the run has settled; a deferred wake counts as busy for the server's restart gate, idle sweep and quit.
   A Stop that finds a wake waiting interrupts its execution rather than dropping it, and a wake for the execution a Stop was interrupting (it started before the Stop, and OpenCode had not confirmed the interrupt) is interrupted on the retry, never minted. A message steered into a turn that is then stopped does not wake the task: OpenCode parks it, and agetor takes it back out of the inbox and puts it at the front of the follow-up queue as the next turn; one whose removal it cannot prove either way, or any of them when the task can't take a turn now (archived, being torn down, switched harness), goes to the task's backlog tray with a status line, and a deleted task keeps nothing ([harness-opencode.md](harness-opencode.md)).
   Otherwise it claims the task like a start does and mints a run with `origin: "agent"` (its status line says OpenCode continued on its own, or picked up a message it had queued), moves the card to Running, attaches the driver (`reason: "wake"`) and settles to Review or Ready like any run.
   A wake is not a start: it does not run `startTask`'s pre-flights (CLI on `PATH`, login, version floor, worktree).

   **`fx` and `cursor` are the exceptions to this whole reattach mechanism**: neither is tmux-hosted (`fx-acp.ts` and `cursor-acp.ts` each launch an ACP child over piped stdio through `coreSpawn`), so neither has a reattach.
   Any `fx` run still `status='running'` at boot falls straight through the generic "no live session" branch below and flips to `orphaned` → `ready`, same outcome as a dead tmux session, just via a different (and simpler) path.
   A `running` cursor row is orphaned explicitly, before the reattach gate: `reconcileOrphans` first kills a tmux session left under the row's `tmux_session` name by the old stream-json driver (its own task's session, never a sweep), then orphans the row; after the orphan writes, `rebuildOpenCursorAsks` restores the task's still-open question cards from `cursor_asks`.
   Runs whose tmux session is gone are flipped to `status='orphaned'` (a new run status alongside `succeeded` / `failed` / `cancelled`), their parent tasks go back to `column='ready'` with `run_id=NULL`, and a status event is appended.

   **Reconciliation never enumerates-and-kills `agetor-*` sessions.** As of the TCC-disclaim change agetor talks to a **dedicated per-instance tmux socket** (`tmuxSocketName()` in `tmux-resolution.ts`, derived from the data-dir basename — `~/.agetor`→`agetor`, `~/.agetor-dev`→`agetor-dev`, `bun test`→`agetor-test`), so a different agetor instance or a `bun test` run generally lands on its own socket; the blind-sweep ban is kept defensively regardless, since a server someone started by hand on the same socket name (or a dogfooded agetor pointed at the same data dir) could still coexist.
   Every kill agetor issues is keyed to a specific task id from *this* instance's own DB (`killTaskSession`/`dropSession` on delete/archive/agent-switch, the per-row kill of a run whose JSONL vanished, codex's/gemini's own teardown), so it can't touch a sibling instance's sessions; a genuinely-leaked session is left alive rather than risk killing a live one.
   To keep that safe, `spawnClaudeViaTmux` clears its *own* stale session name before `tmux new-session` (idempotent, own-scoped), mirroring codex/gemini.
   Cancellation is tracked via a `cancelled: boolean` flag on the in-memory `active` map entry — the exit handler reads it to decide whether to record `cancelled` vs `failed`.
6. **PATCH /tasks/:id allow-list**: only `title`, `prompt`, `agent`, `workdir`, `column`, `mode`, `model`, `effort`, `speed`, `fast`, `maxMode`, `taskType`, `opencodeServer` are patchable (`ALLOWED_PATCH_FIELDS`, `server.ts`); `opencodeServer` is retired — still validated and accepted so old clients keep working, but the server driver ignores it ([harness-opencode.md](harness-opencode.md)).
   `fast` is a boolean alias of `speed`, kept for older clients: `resolveSpeedInput` (`src/shared/speed.ts`) maps `true` → `"fast"` and `false` → `"off"`, `speed` wins when both are sent, and a bad `speed` or a non-boolean `fast` is a 400 (`speed must be one of off, fast, ultrafast` / `fast must be a boolean`); `POST /tasks`, `POST`/`PATCH /agent-profiles`, `POST /agent-profiles/:id/duplicate` and `POST /projects/clone`'s launch fields take the same alias, and every Task/AgentProfile response carries `speed` plus a derived `fast` (`speed !== "off"`, never read by agetor itself).
   Worktree-derived fields (`branch`, `worktreePath`, `baseRef`), identity fields (`id`, `runId`, `createdAt`, `updatedAt`, `isolation`), and server-managed derived state (`sentFiles`, `todoProgress`, `plans`) are all server-managed too — as are the four pipeline fields (`pipelineId`, `pipelineRun`, `pipelineParentId`, `pipelineStepId`, see [pipelines.md](pipelines.md)): a step row additionally 409s a `column` patch specifically (its column is runner-owned), while every other field on a step row stays ordinarily patchable.
   `workdir` itself is refused (400) once a worktree exists (`task.worktreePath !== null`), so `removeWorktree` never runs git against a repository the worktree wasn't made in; and on a multi-repository row any change to `workdir` is refused, even before the first start (its `worktreePath` is still null then, but `workdir` is the workspace root the repository set is prepared beneath). Re-sending the current value is accepted. The webview has no `workdir` editor (its PATCHes carry only the launch fields); the CLI's `agetor edit --workdir` gets the server's 400.

## Harness-stack prepare and swap

Before `resolveHarness(task.agent)`, a manual Run/message calls
`prepareTaskHarness({ manual: true })`: a no-stack task is untouched; a stack
task whose current account was removed/disabled/logged out moves to the next
usable account and transfers the conversation (a live run is left alone; the
message queues). A limit on a stack task settles through
`handleHarnessLimitSettlement` instead of the normal column path — the old run
is `failed` with `run-status.reason: "harness-swap"`, the task stays
`running`, and a successor run (`origin: "harness-swap"`) continues on the
next account. A message typed in that window is held and drained after the
successor settles. Delete removes copied sessions at the end of a successful
delete (after every throwing teardown step, so a failed delete keeps the
conversation resumable); archive keeps them for the retention sweep. See
[harness-stacks.md](harness-stacks.md).

## Multiple repositories in one task

A task created against two or more repositories stores `Task.repositories[]` and runs at a per-task workspace root `<dataDir>/worktrees/<task-id>` with one linked worktree per repository at `<workspace>/<name>`. It stays a multi-repository task (`Task.multiRepo`, read through `isMultiRepoTask`) when removals leave one repository, so every step below that says "multi" applies to it too. The full feature is [multi-repo-tasks.md](multi-repo-tasks.md); a single-repository task follows the steps above unchanged. Where the lifecycle differs:

- **Create.** `POST /tasks` takes `repositories: [{ path, baseRef? }]`, with no hard cap on the count (grill #14); the per-repository work runs in bounded batches (`MULTI_REPO_CONCURRENCY`). The same path twice with different effective base refs is refused, naming the path. Paths are validated together (every failure named), deduped by git root (a selection that collapses to one root is an ordinary single-repository task), and 2+ entries require `isolation: "worktree"` and no `existingBranch`. Each repository's base ref is pinned to a sha and a branch is pinned per repository against that repository's own refs and every other task's pins (`-N` fallback per repository). The row is inserted with `workdir` = the workspace root, `worktreePath` = null and each entry's `worktreePath` null. A single-repository `existingBranch` create counts a live multi row's entry in the same repository holding that branch as a collision.
- **Start.** `prepareTaskWorkdir` creates or reuses every repository's checkout, all-or-nothing (a failure rolls back what this attempt created and names every failed repository), serialized per task id. Reuse and adoption are proved by git common dir; a recorded checkout that can't be read but holds a `.git` fails its repository and is left untouched. `startTaskInner` records the prepared entries immediately after the prepare, then again in the `persist` transaction, skipping the last-seen checkout of any repository whose live read failed (`unknownCheckouts`). The agent spawns at the workspace root with the `Repositories:` block appended to the launch prompt (`composeRunPrompt`); claude-code, codex and copilot also get `--add-dir <checkout>` per repository on every spawn path. The scalar lazy base-ref pin is skipped (`shouldLazyPinBaseRef`); missing per-repository pins are filled by `pinMissingRepositoryBaseRefs`.
- **Start after a removal.** `startTask` awaits `pendingTeardown` (which also waits for an in-flight repository removal) and then re-reads a multi row, so the prepare never re-creates a checkout that was just removed; a single task's row is used exactly as before. Follow-up restore, unarchive and terminal open already prepare from a row read after that wait.
- **PATCH.** `workdir` can't be changed on a multi row (item 6). `repositories`/`issueRepoPath` are server-managed and not patchable; a PATCH carrying `repositories` gets a 400 that points at the removal route.
- **Removing a repository** (`DELETE /tasks/:id/repositories/:name`, `removeTaskRepository`). Refused with 409 while the task (or, for a pipeline parent, a step) is running, for its last repository, a dirty or unreadable checkout, a single task and a pipeline step; 404 for an unknown task or name. A clean checkout is detached and its branch kept; a missing checkout or source repository just drops the entry. The remaining set is written with `tasks.setRepositories`, `issueRepoPath` is cleared when it named the removed repository, and one status line goes on the latest run. It runs on the teardown FIFO keys and the prepare lock, and works on archived tasks. This is the way out when a repository's source was deleted and every follow-up's restore fails on it. Full contract: [multi-repo-tasks.md](multi-repo-tasks.md).
- **Delete and archive** run per repository and best-effort. A stored checkout path is acted on only when it is exactly `<WORKTREES_DIR>/<task-id or pipeline-parent-id>/<name>`; an entry with no stored path falls back to `<workspace>/<name>` only when git proves it is that repository's checkout. Delete removes each checkout and the branches its per-repository plan names; archive records each live checkout, detaches clean ones and keeps a dirty one with its branch. The workspace root is removed only when it holds nothing but agetor's `.claude/settings.local.json` scratch, through task-dir-fs ([security.md](security.md)). A branch another task holds is never deleted: the walk (`branchesHeldByOtherTasks`, shared by the single and multi plans) counts every other row's `branch`/`checkoutBranch` and each of its `repositories[]` entries' `branch`/`checkoutBranch` in the same repository, archived rows included, pipeline steps excluded, and never resolves a multi row's workspace root as a repository. `GET /tasks/:id/teardown-preview` returns the per-repository plans in `repositories[]`; its top-level `branches` is their union. A repository whose source repository no longer exists (`repoRoot` re-checks the disk and drops a stale cached root) is skipped with a reason: its checkout is left on disk (git can't vouch for it), archive reports `source-missing` for it even when forced, delete leaves it, the preview plans no branches for it, and the other repositories tear down as usual; the workspace root stays because it isn't empty.
- **Unarchive** re-materializes a multi task only when it had materialized at least once and some checkout is now missing; a task archived before it ever started is unarchived with no worktree or branch created (a later start or follow-up prepares it as usual).
- **Boot sweep.** `sweepArchivedTeardowns` re-enqueues an archived multi task whose checkouts are all gone only when its root holds nothing but agetor's scratch; that check runs asynchronously through task-dir-fs, so such a job is enqueued after the sweep returns and is not in its count.
- **Terminals** (`POST /tasks/:id/terminals { repo }`) open at the workspace root or inside one repository's checkout; an unknown `repo` is refused before anything is prepared, and a `null` or non-object body is read as empty.
